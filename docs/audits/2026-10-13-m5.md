## Findings

### High

- **H1 Save As inspected directories on the UI thread.** The Save As
  dialog's result called `files::project_file_for`, which checks
  `Samples/` and scans for neighbouring project files before the
  background save starts. A slow or network folder could stall the
  interface (the disk-work rule). Fixed before this review's second part:
  the check runs in `files::save_now`, on the worker, with a test.
- **H2 The audio thread could free a replaced list**
  (`lumen-engine/src/clips.rs`, `mixer/mod.rs`, `midi/player.rs`,
  `take_new`). With the queue that takes old lists back full (the UI late
  to collect) and two new lists arriving in one block, skipping the older
  one stashed it, and retiring the replaced list then overwrote the stash:
  a `Box` freed in `process()`, which rule 1 forbids. Found in the MIDI
  player; the clip player (M3) and the mixer (M4) had the same shape.
  Reproduced by a new realtime test (heap operation at block 5).

### Medium

- **M1 Modules past about 800 lines of production code**: `widgets/mod.rs`
  (866), `lib.rs` (869), `note_editor/ui.rs` (910) and
  `lumen-devices/src/synth.rs` (824). The preliminary list counted tests
  too; by production code most of its twelve files are well under 800
  (KNOWN_ISSUES has the counts). Also over in production code, found here:
  `testing.rs` (894) and `arrangement/clips.rs` (814).
- **M2 The real synth never ran under the allocation guard.** The
  realtime test's MIDI scenario uses a counting stand-in; `lumen-devices`
  tests and the engine's live tests use the synth without the guard.
- **M3 Crafted files could overflow tick arithmetic.** Validation checked
  only that positions are not negative, so a `.lumen` with a clip, fade,
  loop or note near `i64::MAX` overflowed when added up (a panic in debug
  builds, a wrap in release). The MIDI file reader saturated to
  `i64::MAX` the same way.
- **M4 A note can stick when one track's events overflow a block**
  (`midi/hold.rs`, `TrackState::push`): the event is dropped and counted,
  but the note is forgotten as if its note-off had gone. Needs over 1,024
  events on one track in a block.

### Low

- **L1 Project format in the architecture table was stale** (v7, not v15).
- **L2 README's status was stale** (MIDI shown as to come).
- **L3 `lumen-audio` listed `lumen-rt` as a dev-dependency it never used**;
  ARCHITECTURE.md said it stands alone.
- **L4 Small leftovers:** durations outside `motion.rs` (`light.rs`,
  `widgets/menu.rs`, `widgets/scroll_bar.rs`); literal sizes and strokes in
  `note_editor/`; `#[allow(clippy::too_many_arguments)]` on
  `lumen_project::testing::midi_track`; live notes past 128 held dropped
  uncounted; `LiveState`'s methods `pub` on a `pub(super)` type; a note
  dropped silently when every voice is being stolen at once; settling a
  take is quadratic in the notes of one pitch.
- **L5 The WASAPI open panics if its render thread dies before answering**
  (`lumen-audio/src/wasapi.rs`). Only a panic inside that thread gets
  there, and it takes the callback with it, so there is nothing to hand
  back; left as is.
