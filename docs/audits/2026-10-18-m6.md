# Repository review, 2026-10-18 (end of M6)

The end-of-milestone review (`lumen-review`), run on the slice 7 branch
`m6-s7-compatibility-closeout` after its parts 7a to 7d. The architecture
and design skills, CLAUDE.md §§2–5 and 10, the M6 plan, `ARCHITECTURE.md` and
`KNOWN_ISSUES.md` were read. The review was done as five read-only sweeps
(the plugin host; hosting, catalog and test plugin; the real-time paths of
the engine and devices; the plugin code in the app; persistence, documents
and the naming rule), followed by the mechanical scans the skill lists and
the gates below. Each sweep names the files it read. **How findings were
checked:** items marked *verified* were re-read in the code by the
coordinator after the sweep reported them; items marked *sweep* were read by
the sweep's reviewer at the cited lines and not re-read since. Nothing was
run to reproduce a finding. No code was changed by the review.

## Findings

### High

- **H1 Closing Lumen can freeze the window while plugins load**
  (`lumen-hosting/src/manager.rs:313`, `process.rs:550–555, 653–680`;
  *verified*). `on_exit` calls `Hosting::shutdown` on the UI thread, which
  joins each host's thread in turn. A thread still inside `load()` reads its
  `Quit` only after the load ends, and a load may take its deadline (20 s,
  then 10 s for state, 5 s to configure). Closing with a slow or stuck plugin
  stalls the exit for up to that long, per plugin, in series. Rule: nothing
  blocks; the manager's own header says the UI never waits for a plugin.
- **H2 A settings file written by a newer version is overwritten**
  (`settings.rs:336–345, 361–369`, `launch.rs:89–92`; *verified*). `load`
  answers "leaving the file untouched" and returns defaults; the warning does
  not stop saving, so the first settings change writes the defaults over the
  newer file. Rule: never lose work; settings are versioned. Likely only
  after a downgrade; the fix is to refuse to write while the file is newer
  (or move it aside first).
- **H3 A busy plugin host is given its events twice**
  (`lumen-engine/src/midi/player.rs:726, 784–785`, `lumen-devices/src/hosted.rs:588–604, 637–661`;
  *verified by reading, not reproduced*). `start_host` calls
  `HostedInstrument::begin` with the track's events; when the host is still
  busy they are copied to `pending`, and `play_track` then calls `render`
  with the same events, so the block is rebuilt as `pending` plus the same
  events again. A host that becomes free in between receives each note-on and
  note-off twice; one that stays busy makes `pending` grow by the events each
  chunk. A doubled note-on can leave a plugin voice sounding after one
  note-off (notes must never hang, CLAUDE.md §6.3). The existing test retries
  with new events only.
- **H4 A refused submit counts as a missed block more than once**
  (`hosted.rs:349–351, 434–440`, `mixer/hosts.rs:197, 237–246`; *sweep*, the
  same path as H3). The same block is tried by `begin_early`, `hosts::run` or
  `start_host` and `render`, each adding a miss, so a busy host is given up on
  in about half the one second the contract promises (`FAILED_AFTER_FRAMES`).
- **H5 The host's block thread logs while holding the instance lock**
  (`lumen-plugin-host/src/blocks.rs:105–133, 156`; *verified*). `timing.note`
  formats and writes a line to stderr for the first two blocks after each
  attach and for each block over 3 ms (up to 12 lines), inside the scope of
  the lock that configure and state calls wait on. A failed write panics and
  the thread aborts the host. Rule: no lock held across I/O on the block path.
- **H6 A failed timer arm makes the audio thread's wait unbounded on Windows**
  (`lumen-plugin-host/src/shm/sys/windows.rs:171–175`; *verified*). The
  return of `SetWaitableTimer` is ignored and the wait is
  `WaitForMultipleObjects(…, INFINITE)`; if arming fails, `BlockLink::wait`
  (the callback's one wait, ADR-0069) has no deadline. Not observed; the
  fallback (a plain timed wait on the event) is already used when the timer
  could not be created.
- **H7 The product's name is spelled out in user-visible text**
  (`app/safe_mode.rs:139`, `chain/strip.rs:378, 464`, `browser/panel.rs:195`,
  and the command descriptions in `commands/mod.rs`; *verified*). The
  architecture rule says user-visible text that names the product uses
  `PRODUCT_NAME`. Consequence: a rename leaves these behind. High by the
  rule, trivial in effect.

### Medium

- **M1 Closing and dropping hosts can block on a reader thread**
  (`lumen-plugin-host/src/client.rs:325, 825–834`; *sweep, reasoned not
  run*). `HostProcess::drop` joins the stdout reader after killing the child;
  a plugin's helper process that inherited the pipe would keep the reader
  blocked, as the code already assumes for the stderr reader (left
  detached).
- **M2 A panic in a host thread strands its device and a load permit**
  (`lumen-hosting/src/process.rs:654–656`; *sweep*). `gate.take / load /
  give` is not guarded, nothing catches a panic, and four such panics would
  block every later load. No panic is reachable from plugin data today.
- **M3 Undocumented locks and allocations on the host's block thread**
  (`lumen-plugin-host/src/com.rs:334, 379, 478, 492–513, 593–603`,
  `shm/region.rs:598–613`, `instance.rs:890, 1086`; *sweep*). The plugin
  host's internal mutexes, and Vec growth for the first block of a size or
  after `TakeEdits`, are on the path that runs the plugin. No test runs
  `process_into` or `Blocks::run` under the allocation guard (KNOWN_ISSUES
  says the path does not allocate once grown). The soak covers Lumen's side
  only.
- **M4 The SAFETY note on `unsafe impl Send for Guarded` is untrue as
  written** (`blocks.rs:22–27`, `instance.rs:972–980`; *sweep*): the control
  and editor threads use cloned pointers without the lock, by the VST3 rule
  that is stated only elsewhere.
- **M5 Stale auxiliary outputs after a refused block** (`hosted.rs:331–385,
  622–626`; *sweep*): `ready` is not cleared by `begin`, so a refused block
  repeats the previous block's extra outputs while the main output is silent.
- **M6 Callback deadline is not shared on the retry path** (`hosted.rs:659`;
  *sweep*): a retry that is accepted waits its own 75% of a block, serially
  per instrument.
- **M7 Work on the audio thread proportional to the project**
  (`midi/player.rs:895–914`, `midi/hold.rs:455–567`, `midi/mod.rs`
  `same_as`; *sweep*): a locate, loop wrap or edit chases every note before
  the position and compares whole note lists. Never measured at 100,000
  notes.
- **M8 Allocation-guard gaps for the slice 6 paths** (*sweep*): the
  sidechain pre-FX and post-mixer taps, keyed hosted effects, extra plugin
  outputs, instrument latency, the scrub bypass and the refused-retry paths
  have no test under `count_rt_violations`.
- **M9 Oversized and mixed files** (line counts, production lines where
  known): `app/hosting.rs` 2,386 (one 626-line `update`, parameter, preset,
  editor, output and capture concerns, and `pretend_*` seams in production
  code), `plugin-host/protocol.rs` 1,854, `instance.rs` 1,521, `com.rs`
  1,130, `lumen-hosting/process.rs` 1,194, `chain/card.rs` 1,120,
  `chain/presets.rs` 924, `midi/player.rs` 974 (KNOWN_ISSUES says 764),
  `engine.rs` 809, `devices/hosted.rs` (Guard, Status, Holding,
  `HostedInstrument` in one file). Split before the next milestone grows
  them.
- **M10 Stale and dead suppressions** (`app/hosting.rs:734, 743, 760, 903,
  948, 1142`, `chain/params.rs:440`, `browser/list.rs:206`; *sweep*): six
  `allow(dead_code)` attributes say the strip uses a function; three of the
  functions have callers (the `allow` is stale) and `parameter_total`,
  `ignored_events` and `dirty` have none (delete). Two
  `too_many_arguments` allows with no reason: use parameter structs.
- **M11 Settings additions have no version bump** (`settings.rs:21, 276–282`):
  `record` (M5) and `plugins` (M6) were added with defaults and `VERSION`
  stayed 1. They read back, but the exception is only in comments; record it
  in an ADR or bump. The write has no `sync_all` although the module says a
  crash never leaves it half-written (the project and the plugin cache sync).
- **M12 Documentation drift** (*sweep*): `ARCHITECTURE.md` says "as built: M5
  slice 6" and "format v16" and misses about 25 modules (list in the sweep);
  `PROGRESS.md` still shows several M6 requirements as 🔲 that are built
  (scanning, safe mode, presets, floating editors, crash isolation) and a
  status header that stops at slice 5; `DECISIONS.md`'s index omits 17 of 78
  ADRs (0040, 0048–0051, 0053, 0054, 0056, 0057, 0060–0064, 0073, 0077,
  0078); `KNOWN_ISSUES.md` keeps nine struck-through fixed rows against its
  own rule and at least six M6 rows that the code now contradicts (rows about
  aux buses, the host-death rule, "choosing a device does nothing", the
  fake-host-only engine path, `synth.rs`, and "the device chain" arriving).
- **M13 Third-party product names remain in code and one ADR** (*sweep*):
  about 90 lines in about 50 files name DAWs as references, including the
  user-visible label "Keymap: Ableton" (`app/shortcuts.rs:514`), test names
  (`quantize.rs`, `keyboard.rs`, `e2e/clips.rs`), comments, and
  `DECISIONS.md:4614`. The documentation rule applies to documents; whether
  it reaches code identifiers and a visible preset name is the owner's call.
  The documents are otherwise clean; hardware, driver and legal names are
  allowed technical identifiers.
- **M14 Test gaps** (*sweep*): `lumen-hosting/src/link.rs` (MIDI to host
  mapping, offset clamp), `output_pairs`, the manager's stale-serial filter,
  the sidechain "Source removed" state.

### Low

- **L1 Unfinished off-the-UI-thread work** (*sweep*): one `is_file`, one
  `exists` and one `remove_file` run on the UI thread (`plugins/mod.rs:283`,
  `chain/presets.rs:838`, `app/safe_mode.rs:84`); `Catalog::build` runs on the
  UI thread when stale (already in KNOWN_ISSUES); `Texts` requests to a hung
  host are not coalesced and each costs 300 ms on the host thread
  (`process.rs:703–709`).
- **L2 Design tokens**: two grey literals in `chain/card.rs:535, 551`;
  literal geometry and stroke widths in `card.rs`, `view.rs`,
  `browser/controls.rs`; throttle constants outside `motion.rs`; menu rows in
  `chain/sidechain.rs:426, 452` use `selectable_label` where `choice_row`
  exists.
- **L3 Plugin host details** (*sweep*): controller events past 512 a span are
  dropped without a count; `take_reports` drops its Vec's capacity; module
  entry results are ignored; named objects leak on an error path on Unix; the
  non-Linux Unix signal wait polls with 50 µs sleeps (macOS, noted for tests
  only); Windows stdout isolation swaps only the Win32 handle and is
  untested.
- **L4 Engine details** (*sweep*): an `expect` in `TruePeak::process`; a
  `sources - 1` that panics on a zero-channel `ClipAudio`; one NaN sample
  leaves a node's RMS NaN for the session; All Notes Off ignores the channel
  in the held-note count; a `%` per sample in `Lines::carry` on reshaped
  swaps; an O(n²) sort of up to 1,024 events.
- **L5 Hosting and catalog details** (*sweep*): the event cap relies on
  `Vec::capacity`; discovery is capped at 4,096 modules silently; an unused
  `windows-sys` dev-dependency in `lumen-hosting`; `expect` on a thread spawn
  and a spawn error hidden by `unwrap_or(false)` in Reload; blanket
  `allow(dead_code)` in two test support modules; the test plugin's fault
  table omits `state_refused`, `many_params` and `window_edits`; bounds on
  `shown_params` keys, `folded_devices` and loaded plugin settings lists.
- **L6 Known issues to correct**: "Lumen" as the built-in device's vendor
  label (`chain/view.rs:521`) is a label, not text about the product.

## Recommended order

1. **Safety first (High, small):** H5, H6 (host process), H2 (settings), H1
   (exit), H3 and H4 (busy host), with a test for each that fails without the
   fix (an engine test for H3 that retries with the same events, a soak
   scenario that closes Lumen with a stuck load for H1).
2. **H7 and the stale suppressions (M10)**: mechanical.
3. **Real-time coverage (M8, M3)**: guarded tests for the slice 6 paths and for
   the host's block thread; then M5 and M6 with H3.
4. **Documents (M12, M11)**: bring `ARCHITECTURE.md`, `PROGRESS.md`,
   `DECISIONS.md` and `KNOWN_ISSUES.md` in line, and record the settings
   decision.
5. **Splits (M9)** before M7 builds on `hosting.rs` and `chain/`, starting with
   `hosting.rs` (the per-frame `update` and the parameter, preset and editor
   concerns).
6. **M1, M2, M7 and the Low items**: M1 and M2 when H1 is done (the same
   code); M7 needs a measurement first; the rest as a pass.
7. **M13** after the owner decides how far the naming rule reaches.
