## Findings

### High: breaks a stated rule

- **H1. Audio can only be imported with the mouse.** Files come in by
  dragging from Explorer; there is no Import command, menu item or
  palette entry. The M3 exit flow ("create, add a track, import audio,
  …") cannot be done from the keyboard alone, and import is not
  discoverable from a menu. Breaks CLAUDE.md §5 checklist items 1 and 2,
  and §2 "keyboard and mouse are equal citizens".
  *Fix:* an "Import audio…" command (File area; in the app menu, the
  palette, the empty arrangement and the track menu) that opens the system
  file dialog off the UI thread and imports onto the selected track, or
  new tracks, as a drop does.
- **H2. Clips cannot be selected one at a time from the keyboard.** Ctrl+A
  selects every clip and Esc none, but there is no way to move to one
  clip, so the clip commands (rename, mute, properties, cut, duplicate,
  zoom to selection) are keyboard-only only for "all clips". Breaks §5
  checklist item 1 for clip editing.
  *Fix (proposed):* "Select next clip" and "Select previous clip" on the
  selected track, and onto the track above or below, as commands with
  keys (Tab-free; Ableton has no equivalent, so the keys are a choice for
  the owner). Nudging clips by keyboard stays with the editing tools in
  M7.

### Medium: architecture and maintainability

- **M1. Modules past the size limit.** `lumen-project/src/edit.rs` (830
  lines) and `lumen-app/src/transport.rs` (809) are over the ~800-line
  rule; `widgets.rs` (799) is at it and now mixes sliders, dialogs and the
  keycap menu and tooltip family; `palette.rs` (745) is close. M4 adds to
  the transport and widgets first.
  *Fix:* split `transport.rs` (the bar's controls from the engine-facing
  `Transport`), `widgets.rs` (keycaps, menu rows and tips into
  `widgets/keys.rs`), and `edit.rs` (clipboard and range operations from
  clip moves).
- **M2. The time signature is edited in an inline closure.**
  `transport.rs` changes the meter with `doc.apply(…)` instead of a named,
  tested `Document` method (the tempo moved to `Document::set_tempo` in
  slice 7). Breaks rule 3 of `lumen-architecture`.
- **M3. Tab order puts the detail panel before the arrangement.** egui
  needs side panels declared before the central area, and focus follows
  creation order, so Tab goes transport → browser → detail → arrangement.
  F6 visits the panes in reading order and each pane is in order inside,
  so it is usable; it should be recorded (ADR-0033) rather than fixed now.

### Low: consistency and polish

- **L1. The shortcuts window is cramped at 200% in the smallest window**
  (960 × 540 points): the list shows about two rows under the keyboard.
  It works and scrolls. A collapsible keyboard (or a shorter one when the
  window is short) would help; the follow-up "tall windows at large
  scales" in M3.md already tracks the audio settings window the same way.
- **L2. A drag hint can sit under the clip card** at small sizes (the
  "drag …" chip of the hovered clip shows half behind the pinned card).
- **L3. The GPU pipeline cache is read on the UI thread at start-up**
  (`canvas::pipeline_cache_path`, `open_pipeline_cache`). It is a small
  file before the first frame; move it into the renderer's start-up thread
  when the start-up time is measured for the quality bar (M10).
- **L4. A re-check in audio settings** (`audio_settings.rs`): the ASIO
  branch calls `audio::backend` twice and `expect`s the second; matching
  the first result is simpler.

## Recommended order

1. H1 (Import audio…), with an E2E scenario driven from the keyboard.
2. M2 (time signature as a `Document` method) and L4: small and local.
3. M1 (splits), before M4 builds on the transport and widgets.
4. H2 after the owner chooses the keys (clip navigation is a new
   interaction).
5. M3 recorded in ADR-0033; L1, L2 and L3 into `KNOWN_ISSUES.md` with
   owners (M10 accessibility and polish, M10 start-up time).
