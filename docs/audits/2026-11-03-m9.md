  The other crates were scanned, not read line by line. This is a broad
  sweep, not a proof of every path.
- **The combined walkthrough** is the new E2E
  `walkthrough_song::record_edit_save_crash_recover_reopen_and_export_a_song`.
  It starts from an empty song and is driven by keys, clicks and dropped
  files, on the input test device's ramp:
  1. add two audio tracks (Ctrl+T) and name them (F2);
  2. import a loop;
  3. record a take on Vox: one clip, and Undo and Redo take it away and put
     the same clip back;
  4. split it;
  5. save (Ctrl+S, answering the Save dialog), which copies the take into
     `Samples/Recorded`;
  6. record on Gtr and crash in the middle, after an autosave;
  7. recover: the split clips are exactly as saved, the repaired take starts
     where recording began and holds at least every frame counted before
     the crash, the project is still `Song.lumen`, and it is unsaved;
  8. Ctrl+S: the recovered take is copied in, and every file the session
     plays is inside the project folder;
  9. reopen: same tracks and media, nothing missing, both takes unbroken
     ramps at least as long as what was recorded;
  10. export the master and the track stems (each stem audible); neither
      changes the project or its history.

  The test crashes only where an autosave has already run with the take
  open. It does not cover the crash windows in H3 and H4.

  It passes in 8 s. MT-M9-1 is the same song on the owner's hardware with a
  real crash.

## Findings

| ID | Severity | Finding and consequence |
|---|---|---|
| H1 | High | **Take recovery and the record start touch the disk on the UI thread** (architecture rule 4). `App::recover_takes` (`app/audio_record.rs:199`) does three things on the interface's thread: it lists `Recordings`; it repairs each take (`lumen_media::take::repair`: open, `set_len`, header write and `sync_all`); and it deletes the sidecars. Record (F9) also stats candidate file names (`free_file`, line 83) and deletes failed takes there (`remove`, line 92). Take placement reads each file's size there too (`fs::metadata`, line 444). Usually these take milliseconds. On a sleeping or network drive, or for a `sync_all` of a long take, the window freezes at the moment of recovery or at F9. Fix: run the repair and listing on the take worker, and hand the results back to `place_audio_takes` through its channel. The worker can choose the free file names when it opens the files. |
| H2 | High | **A save can point two recordings at one file** (rule 2, never lose work). `files::copy_target` (`files.rs:492` to `522`, the copy skipped at `:343`) treats a target with the same name and the same size as the same file, already copied. That holds for the planned targets of one save and for files already in the folder. Two different takes with the same name and length (for example `Vox 1.wav` from two projects, or a take re-recorded for the same length) collapse into one: both media entries are repointed to the first, and the second recording's audio is no longer used by the project. Equal lengths are common for takes stopped by a loop or punch end. Fix: reuse only when the content is proven equal (the same source path, or a hash), otherwise choose a free name; add tests for two different equal-size files in one save and against a file already there. |
| H3 | High | **The `.take` sidecar is deleted before the take is safely in a project.** On a finished take, `take_worker.rs:524` to `530` deletes the sidecar as soon as the file is closed, before the UI places the clip and before any save or autosave records it. Recovery deletes sidecars too (`app/audio_record.rs:232`, after the repair) before the recovered project is saved. A crash just after Stop, or a second crash just after Recover, leaves the whole take in `Recordings` with no clip, no sidecar and no recovery offer: the earlier autosave does not know it. Fix: keep the sidecar (marked finished) until a save or autosave that holds the clip has been written, and make replaying it idempotent; E2E crashes after Stop before the autosave, and after Recover before Save. |
| H4 | High | **A take recorded in a project with no unsaved changes has no recovery after a crash** (previously listed here as an owner decision; KNOWN_ISSUES, M9 R2). `app/recovery.rs:21` passes only `document.is_dirty()` to the autosave, and `autosave.rs` writes nothing for a clean project. Saving a project with an armed track, reopening it and pressing F9 starts a take with no edit, so no autosave runs and a crash leaves no banner. The take file is safe in `Recordings`, but Lumen never offers it. This contradicts the milestone's recovery goal. Fix: starting a take registers the session for recovery whatever the project's state (an autosave, or a recovery note naming the project and its takes). |
| H5 | High | **The sidecar is rewritten in place.** `take_worker.rs:495` to `509` rewrites the live `.take` file with `fs::write` (truncate, then write) when its loop-wrap notes change, and the recovery reader skips JSON it cannot parse (`.ok()?`, `:214`). A crash during that rewrite leaves a valid take that recovery cannot find. Fix: write a temporary file and rename it over the old one, as project saves do; a test recovers from a torn sidecar. |
| H6 | High | **A take that finishes after the 20 s wait can be credited to the next take.** `poll_audio_takes` (`app/audio_record.rs:350` to `377`) stops waiting after `FINISH_WAIT` and clears `finishing`, but the worker's late answer stays in its shared `done` channel (`take_worker.rs:594`). Answers carry no recording number, so the next Stop can read the old answer and place the wrong files, and the late take is never placed. Rare (a disk that stalls for 20 s), but it misplaces audio. Fix: number each recording, drain late answers for the take they belong to, and keep its sidecar so recovery still finds it; a test delays one finish past the wait and records again. |
| M1 | Medium | **Files M9 grew past about 800 lines of production code** (the skill's split threshold): `app/welcome.rs` (883, no tests inline), `preferences/audio.rs` (969 before its tests) and `audio.rs` (1,045 before its tests). `browser/media_tab.rs` (757) is under the threshold but close, and mixes the pool's list, its actions and relink. `take_worker.rs`, `files.rs` and `settings.rs` pass 800 only with their inline tests. Each mixes more than one concern: the first-run window's three pages and its scan; the device rows, latency and the loopback card; the device system and its worker hand-off. The next milestone touches `audio.rs` and the clip detail panel, so split by concern first. |
| M2 | Medium | **The crate layering is kept by convention, not by a test**, and its written form is out of date. ARCHITECTURE.md's layering rule (`Rules every crate follows`) names neither `lumen-rt`, `lumen-hosting`, `lumen-plugin-host` nor `lumen-plugin-catalog`. A new dependency that points up (for example the engine on `lumen-project`) would compile and pass every gate today. Fix: a workspace test that reads `cargo metadata` and checks each crate's Lumen dependencies against an allowed list, as `third_party_names.rs` does for wording; bring the written rule up to date with it. |
| M3 | Medium | **Three model-side modules of the app depend on interface modules.** `document/` calls `arrangement::auto_scale::own_value` (`document/mappings.rs:122`, `:174`; `document/overrides.rs:54`), a pure function of a track that lives in the arrangement, and takes new tracks' colours from `theme::CLIP_COLORS` (`document/mod.rs:66`). `settings.rs` stores `browser::Saved`, `browser::Tab`, `browser::files::Place` and `theme::Appearance`. So the edit layer and the settings file change when the interface does. Fix: move `own_value` beside the `Document` methods that use it (or into `lumen-project`), keep the default track colours as model data that `theme` reads, and give the settings file its own plain types that the browser converts. |
| M4 | Medium | **`lumen-app`'s modules are flat and `App` is extended from outside `app/`.** `src/` has 89 entries at the top level. Modules of one concern sit side by side without a folder: recording (`audio_input`, `recorder`, `take_worker`, `record_span`, `record_settings`, `auto_record`, `loop_passes`), export (`export`, `export_live`, `export_render`, `render_audio`) and MIDI (`midi`, `midi_export`, `midi_files`, `midi_out`, `midi_play`, `midi_runs`). And 24 `impl App` blocks live in components (`note_editor/`, 8 files; `chain/actions.rs` and `editor.rs`; `browser/files/mod.rs`), so those components can read and change any of `App`'s state; the skill's structure (`App`'s behaviour in `app/` by concern) does not say this is allowed. Nothing is wrong at run time, but it makes each concern's edges hard to see and to test alone. Fix: group by concern into folders (`recording/`, `export/`, `midi/`), moving files without changing code. New components take what they need as arguments; the existing `impl App` blocks move to `app/` when their component is next changed. Record the rule in the architecture skill. |
| L1 | Low | **A stale suppression:** `lib.rs:63` keeps `#[allow(dead_code, reason = "the app starts the disk thread in R6 step 4")]` on `mod disk`. R6 is merged and `disk` is used (`media/streaming.rs`, `transport/hold.rs`), so the reason is false and the allow may hide dead code. Remove it, and delete whatever clippy then reports. |
| L2 | Low | **`docs/KNOWN_ISSUES.md` holds rows M9 fixed.** "Playing audio from disk is still off by default" contradicts the code (`Playback::default` has `from_disk: true`, with a settings test) and `PROGRESS.md`. "The browser shows only the Devices tab" was fixed in R7c (ADR-0116). "The app menu is taller than a 960 × 540 window" may also be fixed: `widgets::Menu` scrolls a menu taller than the window (M7b audit L1), but the row was written after that change. Check it with a capture at the minimum window before removing it. |
| L3 | Low | **`docs/PROGRESS.md` had drifted** (owner report). The "Now" section and the M9 row predated R7. Mono and stereo material, the app icon, and offline render equal to real-time were 🔲 though built or tested. The format row said v2. Two rows were ✅ while their manual tests wait (Preferences, single instance). **Fixed in this branch** at the owner's request; the mini milestone (9.5) is added as proposed. |
| L4 | Low | **Logging with "Reveal logs" is an [M] item of §7 with no slice.** Crash reports exist. The only log is the `LUMEN_TRACE` developer trace (`trace.rs`). It was listed as "later" since M3 and no milestone plan holds it. Proposed home: M10. |

H2 to H6 were found by the review's second reader (the iterate
round on this branch), not by the first sweep.

### Decision for the owner (not a defect)

- **Opening a project while the song plays** keeps playing over the new
  project (KNOWN_ISSUES, M7 review H1, unscheduled). R8's hand-over now opens
  projects from Explorer as well, so this happens more often. The proposed
  fix: stop the transport when a project opens.

## Recommended order

1. H2: never reuse a save target on name and size alone (a wrong file in a
   saved project is the worst outcome here).
2. H3 to H6 together, as one recovery slice: keep sidecars until a
   save holds the take, write them atomically, register a take for recovery
   whatever the project's state, and number recordings. Each with an E2E that
   crashes in the window it closes.
3. H1: move take recovery and the record-start file work to the take
   worker, with an E2E that recovers through a slowed disk call (a test hook
   on the worker). It fits the same slice.
4. L1 and L2: remove the stale allow and the fixed known-issue rows after
   the capture check.
5. M2: the layering test (small, and it guards everything after it). M3 and M4 when the files are next changed; M4's folder moves can go with the recovery slice, which works in the recording files.
6. M1: split `audio.rs` and the clip-detail code before the mini
   milestone, which works in both. Split `welcome.rs`,
   `preferences/audio.rs` and `browser/media_tab.rs` when they are next
   changed.
7. The owner decision above, if the owner agrees, as a small fix before
   the mini milestone.
8. L4: plan logging and Reveal logs in M10.
