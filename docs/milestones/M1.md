# Milestone 1 — Foundations & Architecture: plan

**Status:** Prototyping complete, paused for decisions · **Started:** 2026-10-05
Results: the interim report in [`docs/PROGRESS.md`](../PROGRESS.md#milestone-1--interim-report-2026-10-05)
and evidence in [`docs/DECISIONS.md`](../DECISIONS.md).

Milestone 1 removes the highest-risk architectural uncertainty before any DAW
feature is built. It ships a repository, CI, test and benchmark harnesses, and
a set of small prototypes, each built to answer one question with a
measurement. The prototypes do not count as product features.

Code under `prototypes/` is throwaway-quality: it exists to measure, and it is
deleted or rewritten when its question is answered. Code under `crates/` is
meant to grow into production code.

## 2. Risk register

Ranked by how expensive it would be to discover the problem late.

| ID | Risk | Impact if late | Validated by |
|---|---|---|---|
| R1 | The UI framework cannot keep 120 fps (or the 60 fps minimum) on dense views at quality-bar scale (200 tracks, 20,000 clips, 100,000 notes). | Rewrite of every view | **P-UI** |
| R2 | The UI framework lacks accessibility, multi-window, high-DPI or text features the spec requires. | Rewrite or permanent gaps | **P-UI** |
| R3 | No viable ASIO path in Rust without a heavy C++ toolchain or a licensing problem; driver quirks (reset requests, sample formats, missing hardware) handled poorly. | Windows (first-class platform) blocked | **P-ASIO** |
| R4 | Out-of-process plugin hosting costs too much per audio block at 64–128 samples to be the default. 1.0 requires separate-process isolation. | Isolation requirement unmeetable, or engine redesign | **P-ISO** |
| R5 | Plugin crashes or hangs cannot be detected without stalling the audio thread. | Glitches or lost audio under plugin failure | **P-ISO** |

## 3. Prototypes

Each prototype states a hypothesis, the smallest build that tests it, and
pass criteria fixed before measuring. Results are recorded in
`docs/DECISIONS.md` next to the decision they inform.

### P-UI — dense-view rendering in the candidate UI stack
- **Question:** Can egui/eframe on wgpu, with viewport culling and level-of-detail, render the arrangement (200 tracks, 20,000 clips, waveforms) and a piano roll (100,000 notes) fast enough, idle at near-zero CPU, start fast, and expose accessible names?
- **Build:** `prototypes/ui-stress`: one window with a transport strip, track headers, arrangement canvas and piano-roll panel; synthetic data; scripted pan/zoom benchmark with uncapped presentation; prints frame-time statistics.
- **Pass (on this machine, which is faster than the mid-range target):** CPU frame time p99 ≤ 8.3 ms in every scenario, including zoomed fully out (120 fps capable); headroom goal p95 ≤ 4.2 ms. Idle CPU under 0.5% of one core over 10 s. Process start to first frame under 1 s. Named controls visible through Windows UI Automation.
- **If it fails:** first test the escape hatch (a custom wgpu instanced renderer inside an egui paint callback) before considering another framework.

### P-ENGINE — real-time core
- **Question:** Can the engine core be allocation-free, deterministic for any block size, and cheap enough for 64 tracks at 128 samples?
- **Build:** `prototypes/engine-core`: lock-free command queue, graph built off the audio thread and hot-swapped on it (old graphs freed off-thread), sample-accurate events, simple DSP per track.
- **Pass:** zero heap operations in `process`, including graph swaps (enforced by `lumen-rt` tests). Bit-identical output for block sizes 1, 3, 64, 128, 333, 512 and 4096. 64 tracks at 128 frames under 5% of the 2.67 ms budget, single-threaded (the engine's own overhead, not plugins).

### P-ASIO — native ASIO host in Rust
- **Question:** Can Lumen host ASIO drivers directly over COM from Rust, with no Steinberg SDK and no C++ toolchain: enumerate, query (channel names, latencies, buffer sizes, rates), stream with stable callbacks, and survive bad drivers?
- **Build:** `prototypes/asio-probe`: `list` reads the registry; `query` opens each driver in a sandboxed child process with a timeout; `stream` runs N seconds of silence or a quiet tone, optionally with the P-ENGINE 64-track load in the callback, and reports callback timing.
- **Pass:** query succeeds on at least two real drivers (Focusrite, FlexASIO). 30 s stream with 0 discontinuities in the driver's sample position. Callback CPU p99 well under the buffer period. Drivers without hardware fail cleanly without hanging the parent.
- **Manual (MANUAL_TESTS.md):** buffer-size change in the driver panel while streaming, which triggers `kAsioResetRequest`.
- **Licensing:** the prototype uses clean-room interface definitions and is not distributed. Shipping it needs the decision in ADR-0006.

### P-ISO — plugin process isolation transport
- **Question:** Is a shared-memory plus OS-event transport fast enough to make separate-process plugin hosting the default, and can crashes and hangs be survived within one block?
- **Build:** `prototypes/isolation-ipc`: a parent with a simulated audio thread (real-time pacing, MMCSS priority) and N child "plugin host" processes running a trivial DSP over shared memory. Measures round trips, then injects a crash and a hang.
- **Pass:** single host round trip at 128 frames paced in real time p99 ≤ 50 µs; fan-out to 8 hosts p99 ≤ 150 µs. The parent never waits past its deadline. A crashed or hung host is detected, its output replaced with silence, and the host restarted off the audio thread while audio continues.

### P-VST3 — scanning real plugins
- **Question:** Are the `vst3` crate's bindings (MIT/Apache, pre-generated) enough to load real modules, and is out-of-process scanning with a `moduleinfo.json` fast path robust and fast?
- **Build:** `prototypes/vst3-scan`: discovers bundles and legacy single-file modules; reads `moduleinfo.json` where present; otherwise scans in a sandboxed child (load module, `InitDll`, `GetPluginFactory`, class info, `ExitDll`) with a timeout. Includes deliberately crashing and hanging test modules.
- **Pass:** every installed module is either enumerated or cleanly classified (timeout, crash, no factory) without the parent failing. Misbehaving test modules are isolated. Per-module timings recorded.
- **Deferred to M6:** instantiation, processing, state, editors.

### P-FORMAT — project format and time base
- **Question:** Do versioned JSON, migrations over untyped JSON, and atomic saves give human-readable, crash-safe, forward-migratable projects at quality-bar scale? Is an integer tick time base exact?
- **Build:** `crates/lumen-project`: minimal model, versioned envelope, migration registry, atomic save with backups, relative media paths; tests and benchmark.
- **Pass:** round-trip property tests, golden-fixture migration tests, corrupt or truncated input returns an error and never panics, newer-version files are refused clearly, an interrupted save leaves the previous file intact. A 200-track / 20,000-clip / 100,000-note project saves and loads in under 300 ms each on this machine.

## 5. Out of scope for M1
- Any DAW feature: transport, timeline editing, mixer, MIDI, etc.
- Instantiating and processing real VST3 plugins, and plugin editor windows (M6).
- WASAPI, CoreAudio and Linux backends (M2). Only their abstraction is designed here.
- macOS and Linux hardware testing. CI covers compilation and unit tests only.
