# Milestone 9.5 — Audio clip editing and warp: plan

**Status.** Planned on 2026-11-04 on branch `m9.5-plan`. The owner chose
every recommendation on 2026-11-04, then BS B, TL C and KC C (§2). S0 and S1
are built (§3, ADR-0120 and ADR-0121); T waits for the owner's ear, and
MT-CLIP-1 for the owner. S2 is planned in §9 and waits for the owner's choices.

The owner asked for this mini milestone on 2026-11-03, before M8. It carries
M7's planned E7 (the audio clip editor) and E8 (warp and time-stretch), which
are described in `docs/milestones/M7.md` §5. This file replaces that section
as the plan. M7.md §5 keeps a pointer here.

**Changes from the M9 report's pitch** (`docs/PROGRESS.md`, M9 "Proposed
next"):

- **L is re-lettered.** The report had A (the wave above the properties), B
  (beside) and C (a strip under the wave). A block
  of properties above or below the wave would take 100 pt or more of a 330 pt
  panel. The variants are now A (the column, as today), B (a one-row strip
  under the editor's header) and C (a drawer).
- **TS1 B, Lumen's own stretch engine, is dropped as a variant.** It stays
  the fallback if no candidate passes S0. Lumen's own Rhythmic slicer (M) is
  the part worth writing ourselves.

**Goal.** The Clip tab gives an audio clip what the piano roll gives a MIDI
clip: a large, zoomable view where every clip edit can be done by hand. Audio
clips follow the project tempo, and each one can be warped and transposed.

**Exit criterion.** Someone can import a drum loop at 92 BPM into a 120 BPM
song and hear it in time with no extra steps. They can then:

- fix one late hit with a warp marker;
- transpose a vocal phrase up 2 semitones;
- trim, fade and slip both clips in the Clip tab;
- export.

The exported file must match what was heard.

**Requirements covered:**

- CLAUDE.md §6.2: clip properties (pitch [M]), warp and time-stretch [S],
  and a waveform that is "crisp and fast at every zoom level" [M];
- §6.5: clip envelopes for audio pitch [M];
- §6.6: the clip edits listed there, made inside the editor as well;
- §7 Clip editing: "Warp/time-stretch, transient and tempo detection, pitch
  shift" [S].

**Closes these rows in `docs/KNOWN_ISSUES.md`:**

- 2026-10-07, "Audio clips do not follow tempo";
- 2026-10-19, "There is no audio pitch envelope", together with the static
  pitch deferral Y1;
- 2026-10-23, "Reverse and polarity have no badge on the clip", but only if
  the owner chooses B (§2) below.

**Not in 9.5:**

- audio quantize through warp markers (§2, AQ);
- take lanes and comping;
- spectral editing;
- pencil repair of single samples;
- formant control;
- warp markers edited on the arrangement (they are shown there, P);
- a global "warp all clips" pass over a project, and tempo detection of a
  whole song (detection works on one clip at a time).

## 1. What the Clip tab lacks today, and the target

| Area | Today (ADR-0108 DP1) | 9.5 |
|---|---|---|
| Wave | The clip alone, painted column by column on the CPU, fixed in size | The whole source from the arrangement's GPU peak pyramid (ADR-0027). The clip's window is bright and the rest is dimmed. Samples become dots and lines at the deepest zoom |
| Navigation | None | The note editor's gestures for zoom and scroll, with the zoom kept at the pointer. Zoom to clip, Fit source, follow playhead. The playhead and the edit cursor. Click the ruler to move the playhead there (playing carries on from there) |
| Edits | None in the panel. Every edit is made on the arrangement | Trim, slip (drag the dimmed source), fades and their shapes, the clip gain line, the gain, pan and pitch envelopes, the loop brace, and a range selection that the arrangement's range commands act on |
| Snap | None | The grid, with Alt to bypass it. An optional snap to zero crossings. Snap to transients while warping |
| Properties | The clip card's rows | Grouped into Clip, Warp, Pitch, Fades, Processing and File. File shows format, rate, channels, length, size and path, plus the missing state with Relink and Reveal |
| Tempo | A clip plays at its own speed, so a tempo change moves the audio against the bars | The clip follows the tempo in one of four modes (§2, M). An unwarped clip plays as it does today |
| Pitch | None | A static transpose in semitones and cents, and a pitch envelope |

**Standard behaviours this covers**, described by behaviour:

- **Editing on the wave.**
  - The clip's own loop brace and its start position are set on the editor's
    ruler.
  - A fade's handle and bend dot act as on the arrangement (§9 FD asks about
    the double-click, which this list first had cycling the shape).
  - Dragging the gain line shows its value in dB in a live chip. Shift
    adjusts it finely, and a double-click resets it to 0 dB.
- **Hearing.**
  - Clicking the ruler moves the playhead there; while playing, playback
    carries on from there (as in the note editor).
  - Scrubbing on the ruler works as it does on the arrangement
    (`lumen-engine::scrub`).
  - **Loop clip** plays the clip on repeat while it is edited.
  - A range picked on the wave can be played alone (with Loop clip, §9 LC).
  - **Original** is held to hear the clip without warp or transpose (A/B).
    It applies only while held and never changes the clip. It arrives in S4b.
- **Warping.**
  - Tab and Shift+Tab move between warp markers. The arrow keys nudge the
    selected marker by the grid, and Alt with an arrow key nudges it finely.
    Delete removes the marker.
  - Dragging a marker stretches only the audio between its two neighbours.
    The rest of the clip does not move, because every other marker stays
    pinned.
  - The stretch of each span is shown as a percentage while dragging. It is
    limited to 25% to 400% of the original speed. At the limit the marker
    stops and the chip turns to the warning colour.
  - A **Sensitivity** control (0 to 100) sets which transients are offered
    as ghost markers. Detection runs once, and only the threshold changes.
  - A clip's original tempo is shown and can be edited, with ×2 and ÷2
    buttons.
  - "Set project tempo from clip" makes the song follow the loop instead of
    the loop following the song.
  - "Warp from here" sets the clip's first downbeat. Transients are detected
    once, on a worker, and kept in the cache beside the peaks.
- **Keyboard and accessibility** (CLAUDE.md §5, DESIGN.md §9):
  - Tab moves the focus through the editor's handles in time order: trim
    start, fade in, gain line, the envelope points, the markers, fade out,
    and trim end.
  - The arrow keys move the focused handle by the grid, Alt moves it finely,
    and Enter types a value.
  - Every handle and marker has an accessible name, for example "Warp marker
    at bar 4 beat 2, 112%".
  - Zoom uses the arrangement's keys (Z, X, and Ctrl with plus and minus).
    Slip is Ctrl with Alt and an arrow key.

### S: shape of the milestone

- **A (rec).** E7 and then E8, in one mini milestone, as the owner asked on

- **B.** E7 now, and E8 later.

### L: the Clip tab's layout (specimens)

- **A, column.** Today's 296 pt properties column on the left, with the
  editor beside it. The layout is familiar, but the wave loses about a
  quarter of the width. At the panel's usual height the column scrolls (Clip and
  Warp show; Fades, Processing and File are below).
- **B, strip (rec).** The editor uses the full width. Under the editor's
  header is one 32 pt row with the properties used most:
  - gain;
  - transpose;
  - warp on or off, the mode and the original tempo;
  - the fade lengths;
  - reverse, polarity and normalize.

  A **File** chip at the end of the row opens a popover with the file's
  details. Warp markers and envelopes get the whole width, and the panel
  stays usable at its lowest height. When the row is too narrow (a small
  window, or 200% scale), the groups at its right fold into a **More** menu,
  Processing first, then Fades. The row never wraps and never scrolls.
- **C, drawer.** The editor uses the full width. A **Properties** button
  opens a 264 pt drawer at the right with every section. The drawer is
  closed by default and remembers its state. It is the most complete
  layout, but the drawer covers the wave when it is open.

### W: whether new clips are warped

- **A (rec).** Warp is on for clips that are loops, and off for the rest.
  - **On for:** a clip recorded in Lumen (its tempo is the song's tempo when
    it was recorded), and an imported file whose tempo is known. The tempo is
    known from the file's own tempo tag, from a BPM in its name, or from
    confident detection of a file that lasts a whole number of bars from 1 to
    32.
  - **Off for:** one-shots and long files. Those play at their own speed.
  - **The setting:** Preferences › Recording and import › "Follow tempo",
    with the values *Loops* (the default), *Always* and *Never*.
- **B.** Warp is never on until the user asks for it on a clip.
- **C.** Warp is always on.

Under every variant, a warped clip plays its source bit for bit wherever
it plays at the tempo it was made at. The ratio is checked span by span, so
a tempo ramp or a later tempo change stretches only the spans it touches
(D3). A project made before 9.5 keeps every clip unwarped, so it sounds as
it did.

### G: how a warp marker is made (specimen of B)

- **A.** Double-click on the wave to add a marker, then drag the marker. The
  transients are drawn as faint ticks.
- **B (rec).** Hovering over the wave shows a ghost marker at the nearest
  transient, or at the pointer when there is none near. Dragging the ghost
  makes a marker and moves it in one gesture. Double-click adds a marker
  without moving it, and double-clicking a marker deletes it. Shift and drag
  moves the audio under a marker without moving the marker.
  - Both variants stretch only the audio between a marker and its
    neighbours.
  - Both make one undo step per drag.

### P: where markers are drawn (specimens)

- **A, a warp strip (rec).** A 14 pt strip sits between the ruler and the
  wave. Markers are flags in this strip with a hairline down through the
  wave. The strip is where markers are grabbed, so they never conflict with
  the trim, fade and gain handles on the wave.
- **B, pins on the ruler.** Markers are pins on the bar ruler. This saves
  14 pt, but the ruler's click (play from here) and its loop brace then share
  their room with the markers.
- Under both variants, the arrangement shows a warped clip's markers as
  ticks on the clip at deep zoom. They can be read there but not edited.

### M: warp modes

- **A (rec).** Four modes:
  - **Repitch:** the speed follows the tempo and the pitch moves with it,
    like tape. It uses rubato's resampler with the ratio set for each chunk
    from the warp map, so ramps and markers glide. It needs no new engine.
    Transpose is disabled in this mode on purpose: a tape-style transpose
    would change the speed as well, and the clip would stop fitting its bars.
    The field says "Set by tempo in Repitch".
  - **Rhythmic:** Lumen's own slicer. The audio is cut at transients, and
    each slice plays at its own speed with a short fade. It has no smearing
    on drums.
  - **Melodic:** the library's settings for monophonic material.
  - **Full mix:** the library's best mode for polyphonic material.
- **B.** Repitch and one stretch mode. The engine's quality is then the only
  setting. This is simpler, but drums would smear.

### E: where the stretching runs

The decision is technical, but it changes what is heard, so it is pitched.
**It is chosen now and confirmed after S0**, which measures each candidate's
start-up delay, its cost and its block-size behaviour. If S0 contradicts the
recommendation, the plan comes back to the owner.

What each variant means for the person playing:

- **A, prepared ahead (rec).** Stretched audio is prepared a moment ahead of
  the playhead on a background thread. It is stored the way R6 stores files
  read from disk (ADR-0109).
  - **The song stays light.** A stretched clip costs the audio the same as a
    clip read from disk, however many are stretched.
  - **An edit made while playing** (a marker drag, a tempo change) is heard
    after a short delay. The audio prepared before the edit keeps playing
    until the new version is ready, then crossfades to it. Nothing drops
    out. S0 measures the delay, which is expected to be 50 to 150 ms.
  - **Starting from a new place** (a ruler click, a jump, scrubbing) in a
    stretched clip comes in after the same short delay, with a fade. The
    places a jump usually goes are prepared in advance: the loop's start,
    markers, the play marker and the cue.
  - **Export** uses the same code and gives the same bits as playback.
- **B, live.** Every stretched clip is stretched as it plays, on the audio
  thread.
  - Edits, clicks and jumps are heard at once.
  - Every stretched clip costs time in the audio's budget. Sixty-four of
    them may not fit at 128 samples (CLAUDE.md §4).
  - The library must be proved never to allocate or wait while it plays, and
    to give the same output whatever the block size. Otherwise export
    differs from playback.
- **C, hybrid.** Playback is as in A, but the first moment after a click or
  jump is stretched live until the prepared audio catches up. Clicks come in
  at once, at the cost of both A's and B's code.

How A works (for review, not a choice):

- **Placement.** The thread is `lumen-app::stretch`, beside `lumen-app::disk`
  (which fills the page pool today). The stretching itself (the library, the
  slicer and the chunk renderer) is in `lumen-media`. `lumen-engine` gains
  only page tables keyed by the clip, so it takes no dependency on
  `lumen-media`. `tests/layering.rs` keeps that graph.
- **Pages keyed by clip, not file.** A stretched clip's audio depends on the
  clip, its markers, mode, pitch and the tempo map, so its pages belong to
  the clip and carry a version. An edit makes a new version. The old pages
  play until the new ones cover the playhead, then the 3 ms crossfade the
  preview already uses (ADR-0116) joins them.
- **Pool budget.** The pool is 96 MB (3,072 pages). Two seconds ahead for 64
  stereo stretched tracks at 48 kHz is about 50 MB. Stretched clips get at
  most half the pool, and the plan keeps the nearest half second of every
  playing clip first. A tempo edit re-prepares every stretched clip, nearest
  first. `warped_64` measures how long that takes.
- **Same bits offline and live.** Audio is prepared in fixed chunks aligned
  to the clip's start. S0 (ADR-0120) measured 4,096-frame chunks at about six
  times the cost of streaming (18% of a core per clip with C) and 2 s chunks at
  2.9%; with 2 s chunks a jump waits about 60 ms (C). **The chunk length and
  what happens right after a jump go back to the owner before S4b.** Each chunk is rendered from a fixed
  pre-roll of source audio before it, never from what the thread did last. A
  jump, an abandoned pass and continuous play therefore give the same bits.
  Export renders the same chunks in order. A test plays a clip continuously,
  then with jumps, and compares the bits. S0 checks every candidate for this
  property.

### T: the time-stretch engine (TS1)

T is chosen by ear after slice S0 (§3). The shortlist is every library with
Rust bindings whose licence fits GPL-3.0-or-later (ADR-0039) and the sale of
the packaged binary:

| Candidate | Licence | Language | Notes |
|---|---|---|---|
| Signalsmith Stretch (`signalsmith-stretch` or `ssstretch`) | MIT | C++ (header-only) and a Rust binding | Polyphonic quality, simple API, time and pitch in one call. The bindings are young (0.1.x), so we may keep our own thin binding |
| Rubber Band (`rubberband`) | GPL-2.0-or-later (a commercial licence also exists) | C++ and a Rust binding | Two engines (a faster one and a finer one). Compatible with Lumen's GPL-3.0-or-later. Selling the binary stays allowed, as it is for Lumen itself |
| Bungee (`bungee-rs`) | MPL-2.0 | C++ and a Rust binding | Built for random access and changing speeds |
| `timestretch` | MIT | Pure Rust | No C++ build step. Its maturity and quality are unknown, so it is tried as the no-C++ option |

- No library is compiled from C++ in the workspace today, so a C++ candidate
  adds a C++ compiler to the build on all three platforms. MSVC is already
  installed on Windows with the Rust toolchain.
- **Licence facts.**
  - Every candidate can be shipped in the sold, GPL-3.0-or-later Lumen.
  - Lumen is already GPL (ADR-0039), so a GPL candidate takes away nothing
    that Lumen has today. It would only stand in the way if Lumen ever went
    back to closed source, which ADR-0039 gave up.
  - ADR-0013 lets only permissive licences in without a record. A GPL or MPL
    candidate needs a recorded exception in ADR-0013 and `deny.toml`, as
    symphonia has. **That exception is the owner call**, made with T.
  - Whatever is chosen, a licence notice is added to the third-party listing
    (CLAUDE.md §7).
- **Recommendation:** decide by ear and by the measurements in S0. If two
  candidates sound alike, prefer the MIT one (no exception needed), then the
  one with random access (it suits A's chunks).

### B: badges on the arrangement's clips (specimens)

### TL: one header for both clip editors (specimens)

The owner asked that the two clip editors stay consistent (2026-11-04). The
audio editor therefore does not get a header of its own. S1 moves the note
editor's toolbar (`note_editor/toolbar.rs`) into one clip-editor header that
both editors draw, and DESIGN.md's "The clip editor's look" becomes the look
of both. The header has these parts in this order:

- the clip's title;
- the tool control (Pointer and Draw, with their icons and the Draw key);
- the grid chip;
- the editor's own action: Quantize for notes, Zero crossings for audio;
- at the right, the view toggle (Lane for notes; for audio, the Gain, Pan
  and Pitch envelope pills), then Pop out or Dock.

An E2E check draws both editors and compares the header's parts and their
places. Only the tool control's lit state is a choice. Its looks today are:

- the note editor: the accent, always;
- the arrangement's tool switch: the accent only while the tool is not
  Pointer (K1);
- the first audio specimen: grey.

The variants:

- **A, blue always.** The chosen tool is filled with the accent, as in the
  note editor today. The audio editor adopts it.
- **B, grey always.** The chosen tool is the grey raised thumb of every other
  segmented control. The note editor changes to match.
- **C, grey for Pointer, blue for Draw (rec).** Pointer, the resting tool, is
  grey, and Draw is lit blue while it is chosen. This is the arrangement's
  rule, so all three tool controls follow one rule. The note editor changes
  to match.

### KC: the Draw key in the tool control (specimens)

The owner found the B key beside Draw untidy (2026-11-04). The specimen of
TL drew it as a filled box. The app draws a lighter cap (`widgets::toggle`
`paint_cap`): a hairline outline at 45% and the letter at 75% of the label's
colour. Under every variant the key stays in the tooltip (as a K5 keycap) and
in the command palette.

- **A, outlined cap.** Today's cap as the app draws it.
- **B, letter only (rec).** The letter alone in the mono face at 60% of the
  label's colour, with no outline. It stays clean on the blue fill, and there
  is no box to line up.
- **C, tooltip only.** Nothing in the control; the key shows when hovering.
  The cleanest control, but the key is found only by hovering.

The answer applies to every `Choice::hint` in a segmented control, not only
to the clip editors, so the app stays consistent.

### BS: badges on very small clips (specimens)

The owner asked how the badges look on a very small clip (2026-11-04). Today
a clip's name shows only when the clip is at least 24 pt wide (DESIGN.md
§7a). On a short track the title bar is the whole clip.

- **A, marks go first.** The marks give way, then the name shortens. Below
  24 pt nothing shows, so a tiny warped clip looks like any other.
- **B, fold into one dot (rec).**
  - When the marks and four letters of the name do not both fit, the marks
    fold into one dot at the right of the title bar.
  - The name shortens before the dot goes.
  - Below 24 pt the dot stays alone, centred, down to 10 pt wide. Below
    10 pt the clip is too thin to show anything.
  - At any size, hovering over the dot or the clip lists what is set, and
    the info line says the same.
- **C, warp mark last.** The marks drop one by one (polarity, reverse,
  transpose), and the warp mark goes last. Below 24 pt nothing shows.

## 4. Decisions taken unless the owner objects

| # | Decision |
|---|---|
| D1 | A warp map is a list of (source seconds, ticks) pairs. The ticks are measured from the clip's content origin, the origin that `loop_phase` uses. Positions are stored in `Ticks`, so a tempo change moves the audio with the bars and never moves the bars under it. Between two markers the source time follows the song's time linearly, and before the first or after the last marker the clip's original tempo applies |
| D2 | A clip that is not warped keeps today's fields and today's code path (`offset`, `audio_phase_seconds`, `loop_phase`). It renders bit-identical to the build before 9.5, and a golden render proves it |
| D3 | The ratio is worked out span by span. A span whose ratio is exactly 1 with no pitch change is copied from the source, not stretched. A take recorded at a steady tempo is therefore free until the tempo changes |
| D4 | The stretching (the library, the slicer and the chunk renderer) is in `lumen-media`. The thread that prepares the pages is `lumen-app::stretch`, beside `lumen-app::disk`. `lumen-engine` gains page tables keyed by the clip and no dependency on `lumen-media`. `tests/layering.rs` keeps that graph |
| D5 | Detection results (transients and the tempo estimate) are a cache kind keyed like peaks (ADR-0109). They are never saved in the project, and markers are |
| D6 | Reverse with warp: the markers are mirrored, so a reversed warped clip stays in time |
| D7 | Freeze and bounce render warped clips through the same renderer, so a frozen clip sounds the same as the warped clip it replaces |
| D8 | A take recorded while the tempo changes (a ramp, or a tempo lane) gets warp on, with a marker at each tempo point, so it plays as it was recorded. If the tempo is then edited, it follows |
| D9 | Join (consolidate) of pieces of one file whose maps meet at the seam rebuilds the one clip with the joined map and renders nothing, so split followed by Join returns the original (CLAUDE.md §6.6). Any other Join of warped clips renders the warped audio to a new file, as Join of processed audio does today (M7). The new clip has warp on at the song's tempo, with no markers |

**What each `Clip` field means for a warped clip** (S4a; the fields are in
`crates/lumen-project/src/model/clip.rs`):

| Field | Warped clip |
|---|---|
| `start`, `length` | As today, in ticks |
| `offset`, `audio_phase_seconds` | Not used for position while warp is on: the map gives it. They are kept, so turning warp off puts the clip back where it was |
| `loop_length`, `loop_phase` | As today, in ticks. The map covers one loop period and repeats with it. Markers past the loop length are kept but not heard, as notes are in a looped MIDI clip |
| `fade_in`, `fade_out`, `crossfade` | On the clip's timeline, as today. Markers never move them. A crossfade reads the incoming clip's hidden audio through its map, extended at its first span's ratio |

## 6. Open risks

1. **Every audio edit has to learn warp (S4).** The edits are split, Join,
   consolidate, reverse, crossfades, the loop fields, bounce, freeze and the
   trims. This is the largest hidden cost in 9.5. The model's property tests
   cover each edit with warp on.
2. **The C++ build step.** A C++ candidate adds a compiler to CI on all three
   platforms, plus the macOS cross-target clippy.
3. **Licence.** If the best-sounding candidate is GPL-2.0-or-later, Lumen
   stays GPL unless a commercial licence is bought. That is the owner's call
   before code.
4. **Starting from a click under E A.** A click or jump to a place nothing
   prepared comes in after a short delay, with a fade. S0 measures the delay
   for each candidate. If it is over about 150 ms, E C (the hybrid) is
   pitched again before S4b.
5. **A tempo edit with many stretched clips.** Every stretched clip is
   prepared again, nearest the playhead first. `warped_64` measures how long
   the slowest clip takes to catch up.
6. **Detection quality.** Tempo detection is wrong by a factor of 2 now and
   then. The original tempo is always shown, and ×2 and ÷2 fix it in one
   click.

## 7. Alternatives rejected

- **Storing warp as a stretched copy of the file** (rendered once, played as
  audio). Every marker drag would re-render, and the edit could not be heard
  until the render finished.
- **Markers in samples of the project timeline** instead of beats. A tempo
  change would leave every marker behind (the reason automation points are
  stored in ticks, M7).
- **A separate audio editor window.** The Clip tab already hosts the piano
  roll. Pop out and Dock (M5) give the editor its own window when that is
  wanted.

### 9.1 The choices

Each has a recommendation, marked "rec". HS, LB and the header at its real widths
are shown on the specimen page sent with this plan.

**HS: when the handles show (specimen).**

- **A (rec), always there, quiet.** The fade curves, their handles, the gain
  line and the trim grips are always drawn, in hairlines and small marks, and
  light up under the pointer. This panel exists to edit the clip, so what can
  be grabbed is plain before the pointer gets there.
- **B, under the pointer.** As on the arrangement: fades are quiet curves, and
  the handles, the gain line and the grips appear when the pointer is over the
  editor. The wave is cleaner to read, and what can be grabbed is found by
  moving over it.

**WD: what a drag on the wave does.**

- **A (rec).** Dragging the part of the wave the clip plays at that point in the
  song picks a time range, which is the arrangement's rule for a clip's body.
  Dragging the dimmed file slips: the file slides under the window. Ctrl+Alt and
  a drag slips anywhere, which is the arrangement's gesture, and is the way to
  slip when Zoom to clip leaves only a sliver of the file showing. The cursor
  and the info line tell the two apart.
- **B.** Dragging the bright part slips, and Shift and a drag picks a range.
  Slipping is one gesture shorter. A plain drag then changes what plays, where
  on the arrangement the same drag only selects.
- **C.** Dragging the dimmed file does nothing, and only Ctrl+Alt slips, exactly
  as on the arrangement. This is the most consistent and the hardest to find,
  and it drops the plan's §1 "drag the dimmed source".

**FD: double-clicking a fade's handle.** §1 said it cycles the shape. The
arrangement removes the fade, and CLAUDE.md §5 asks for the same behaviour in
every editor and for a double-click to reset.

- **A (rec).** As on the arrangement: double-clicking the handle removes the
  fade, double-clicking the bend dot straightens it, and right-click lists the
  shapes.
- **B.** As §1, in this editor only. Shapes are one gesture away, and the same
  double-click then does two things in the app.
- **C.** Cycling in both places. Removing a fade then means dragging it to
  nothing, and a gesture in use since M3 changes.

**CU: a click on the wave.**

- **A (rec), an edit cursor.** A click on the part the clip plays there puts a
  thin cursor at that place (on the grid; Alt places it freely), and the playhead
  stays where it is, playing or not. While the editor's keys are live, Ctrl+E
  splits at the cursor if there is one, and otherwise at the playhead. It belongs
  to the editor, is not saved, and goes when another clip opens or a range is
  picked. A click anywhere else on the wave clears it. From the keyboard it is
  placed and moved on the focused wave (D28).
- **B, the playhead.** A click moves the playhead, as the ruler does. There is
  one marker to think about, and Ctrl+E already splits there. A click during
  playback then jumps the song, and the edit cursor row in `docs/PROGRESS.md`
  stays open.

**LC: Loop clip.**

- **A (rec), in the song.** A toggle in the header. While it is on, playback
  repeats one pass of the clip, or the range picked on it, with the other tracks
  heard. One pass runs from the clip's start for its length, or for one turn of
  its loop if that is shorter, so it holds every frame of the loop even when the
  clip starts part way through. Nothing is saved or undoable: the project's loop
  stays as it was, and what the engine plays is overridden
  (`Transport::follow_loop`). Turning it on moves the playhead to the interval's
  start if it is outside and does not start playback. It turns off with its
  button, when another clip opens, and when recording starts.
- **B, the clip alone.** As A, with the other tracks silent. This needs a second
  kind of solo beside the one in every track's header, and hides how the edit
  sits in the song.
- **C, the song's loop.** It writes the project's loop brace, as Ctrl+L does on
  the selected clip. There is no new state, and it costs the song its loop and
  an undo step each time.

Under all three a range plays on repeat. Playing it once and stopping at its end
would need a stop point in the engine, so it is not planned.

**LB: where the clip's loop brace sits (specimen).**

- **A (rec), a band under the ruler.** The ruler grows from 30 to 37 pt, and
  its bottom 10 pt become the brace's band, as on the arrangement's strip. The
  band shows the thin mark of the clip's window until the clip loops. The rest
  of the ruler stays click and scrub.
- **B, over the file time.** The ruler stays 30 pt, and the brace is drawn over
  the row of file times, which it covers while the clip loops.

Under both:

- A click on the band turns the loop on or off. Turned on, the loop is the clip's
  length, or as much of it as the file holds. Every frame stays the same, and a
  clip that ran past the end of its file now repeats where it was silent.
- Dragging the end sets how long the loop is, and dragging the start sets where
  it begins in the file with the end staying put. The file does not move and the
  clip stays where it is on the arrangement, so a clip can start part way through
  its loop. The clip's start grip marks where, and a small flag on the band
  repeats it (the "start position" of §1).
- What is heard: every frame from the clip's start up to its first repeat stays
  the same. The repeats change, since that is what was asked for.
- Envelope points stay on the audio they were drawn over. Points outside the loop
  are kept and not heard, and come back if the loop grows over them.
- Turning the loop off keeps the frame the clip starts on. The file now carries on
  past the old loop's end instead of repeating, so a clip longer than one turn
  sounds different from there, and it is shortened to what the file holds.

**LS: the loop's start and the clip's start.** The model has no stretch that plays
once before the loop, so a clip cannot start before its loop does.

- **A (rec), it stops there.** The brace's start stops at the clip's start grip,
  and the chip says why. To loop from later, trim the clip's start first, which
  moves the clip on the arrangement, or slip the file. Nothing heard changes
  unasked and the file never moves under the hand.
- **B, it pushes the start along.** Past the grip, the clip's first frame goes with
  the brace. The clip stays on the arrangement and now starts on a later frame, so
  the file slides in the view during the drag and everything after it in the clip
  shifts. One gesture is shorter, and it changes what plays at every beat.

**ZC: snap to zero crossings.** Stereo channels rarely cross zero together, so
this reduces the jump at a cut and cannot promise none.

- **A (rec), a small correction.** A toggle in the header, off by default and
  remembered in the settings. An edge is first placed by the grid or the hand,
  then moves within 5 ms to the frame where the louder channel is nearest zero,
  so it stays on the beat to the ear with a smaller jump. If nothing there is
  better than where it stands, or the stretch is silent, it stays. It applies to
  trim edges, range edges and the cursor; fades and slip follow the hand. Alt
  bypasses both grid and crossing.
- **B, instead of the grid.** While it is on the grid is ignored, and the edge
  goes to the best frame near the hand. This suits material with no beat, and
  edges drift from the bars.

**DR: Draw with no envelope showing.** The header has two pills, Gain and Pan,
which show one envelope at a time, in this editor only (the arrangement's E
stays its own). B switches between Pointer and Draw.

- **A (rec).** Choosing Draw with no pill lit lights Gain, so the pencil always
  works.
- **B.** Draw stays disabled until a pill is lit, with a tooltip saying so. This
  is one step longer, and nothing is shown that was not asked for.

**What `edit::set_clip_loop` does to each field (D21).** O is the loop's origin (D27)
and `s` is `seconds_at`. `start` and `offset` never change, and fades change only
where a loop off shortens the clip. Takes' passes move with the same seconds
(`takes::advance`).

| Edit | `loop_length` | `loop_phase` | `audio_phase_seconds` | `length` | Envelopes |
|---|---|---|---|---|---|
| Loop on | `length`, capped to what the file holds | 0 | same | same | same |
| End to E | E − O | start − O | same | same | re-timed, d = 0 |
| Start to O′ | old end − O′ | start − O′ | + s(O′) − s(O) | same | re-timed, d = s(O′) − s(O) |
| Loop off | none | 0 | + s(start) − s(O) | capped to what the file holds from the start frame | re-timed, d = s(start) − s(O) |

**Re-timing.** Envelope points are in ticks from the stored clock C = `start −
loop_phase` (`lanes.rs`, `lane_bake::bake_from`), and O can differ from C. Across a
tempo change the same ticks are different seconds: at 120 BPM to beat 4 and 60 BPM
after, a clip at beat 8 with phase 8 has C at beat 0 and O at beat 8, and a point one
beat from C sounds half a second in, where one beat from O would sound a second in.
So every edit that writes a new clock C′ (O, O′ or the clip's start) re-times its
points to stay on the same audio: `t′ = ticks_at(s(C′) + s(C + t) − s(C) − d) − C′`,
where d is how many seconds the loop's first frame moved. Under one tempo this is
the plain shift. A point before the new first frame is kept with its negative
position, as a trim leaves it.

Tested through `lanes::engine_clips` and the engine's read (in `lumen-app`, which
sees both crates), on processed audio and not only frame indices, with gain and pan
envelopes that move, at phase 0, inside a turn and past a turn, with a tempo change
and a ramp, on a reversed clip and on one with takes:

1. Loop on: every frame up to the file's end is the same.
2. Start or end moved: the frames from the clip's start up to the earlier of the
   old and new first repeat are the same, and the file's frame at every beat is
   the same in the editor.
3. Loop off: the frames up to the first repeat are the same.
4. Loop on, then off: the clip equals the original exactly.
5. A point drawn at a beat in the editor is heard at that beat.

### 9.5 Risks

1. **Sharing the gestures touches the arrangement (D10).** Its handle and trim
   code has run since M3. The change only moves where the view comes from, and
   the arrangement's E2E (`fades`, `crossfades`, `clips`) guards it.
2. **Loop clip's override (LC A) must not leak.** Export, record and saving read
   the project's loop, and the disk's read-ahead for the loop's start must
   follow the override. A test covers each.
3. **The header's width (D24).** At 150% and 200% in the smallest window the left
   column folds away, so an open clip's properties are one step further until S3
   gives that width back.
4. **The arrangement may draw a phased clip's envelope in the wrong place.** It
   draws from the clip's start (`auto_envelope.rs`), and the engine bakes from
   `start − loop_phase` (`lanes.rs`). S2b's check 5 settles this for the editor. If
   the arrangement is wrong, it goes in `docs/KNOWN_ISSUES.md`, with a fix on its
   own branch.
5. **A disk read and a quick hand (D23).** On a file played from disk a very quick
   drag can end on the grid and not a crossing. That is the rule, and it is what
   the screen showed at release.
6. **Re-timing is exact at the points (§9.3).** Between two points, a segment that a
   tempo change crossed can change shape when its clock moves to a place with other
   tempos, since a line in ticks is not a line in seconds. Under one tempo nothing
   changes, and the tests hold the points exact and the rest within a stated
   tolerance. Making it exact would mean adding points the user did not draw.
7. **Edge scroll differs between the editor and the arrangement (D29).** CLAUDE.md
   §5 asks for the same drag behaviour in every editor, and §6.1 for edge scroll
   when dragging. The arrangement's clip drags do not have it (`docs/PROGRESS.md`
   records this row as partial), so the two differ until that row is done. It is not
   part of S2.
