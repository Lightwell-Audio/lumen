# Milestone 7 — Automation, Envelopes & Advanced Editing: plan

**Status:** Plan for the owner's review, 2026-10-19. **Not approved and not
started.** No code has been written. M5 and M6 are built but not signed off
(reports in `docs/PROGRESS.md`; the owner's manual runs are in progress in
another thread), so this plan only becomes work when the owner approves it.

**How this plan was made.** Three read-only explorations of the engine and
time base, the project model and edit operations, and the app interface and
test harness. Nothing was built or run. Every file pointer below comes from
those reports and from reading the draft against `CLAUDE.md` §6.5, §6.6 and
§9; each slice re-reads its own area before it starts. Choices that the code
settles are recorded as decisions (§3). Only real preference calls are left to
the owner (§4).

**Goal (ROADMAP §7, CLAUDE.md §6.5 and §6.6).** Everything that has a value can
be automated, recorded and mapped to a controller. Clips carry envelopes. The
editing tools of a professional workstation (split, join, consolidate, ripple,
crop, bounce, freeze) work on clips and time ranges.

**Exit criterion.** A user can automate a track's volume and a hosted plugin's
filter, record a fader move in Touch and Latch, map a controller knob to a
parameter, split and consolidate clips, bounce a track in place, save and
reopen, and hear the same result.

## 1. What the code gives us

| Area | Fact (pointer) | Consequence |
|---|---|---|
| Engine values | Every continuous value is a block target plus a 20 ms glide (`mixer/smooth.rs`). In `Plan::process` each node fills a stack array `gain[CHUNK]` (256 frames) per block (`mixer/plan.rs`). | An automation lane fills that array instead. No allocation. |
| Position in the mixer | `Mixer::render` knows the chunk's timeline sample (`part_cx.start`, `mixer/mod.rs`) but does not pass it to `plan.process`. | The one signature change in the audio path. |
| UI to audio | `rtrb` queues of `Box<T>`; retired boxes return on a second queue and are freed by `collect_garbage()` on the UI side (`engine.rs`, `mixer/mod.rs`, `clips.rs`). | A lane travels inside `NodeSpec`/`Plan` as an `Arc<[Point]>`, like `note_list` in `midi/mod.rs`. |
| Plugin parameters | The wire already carries sample-accurate parameter queues (`ParamQueue` in `Process`, shared region version 4, `Instance::process_into`). `Link::submit` passes `&[]` and `Hosted::submit` has no parameter argument. Today parameters go over the control channel with no sample offset. | Sample-accurate plugin automation needs plumbing, not a new protocol. Region limits are 64 queues and 1,024 points per block. |
| Built-in devices | `Device` in the mixer spec has only a test delay and `Hosted`. `Instrument` has no parameter interface. | Built-in device parameters have nothing to automate until M8. M7 leaves the target arm ready. |
| Tempo | `Project.tempo: Vec<TempoPoint>` supports many constant segments through the whole engine. There are no ramps. Only point 0 is editable (`Document::set_tempo`). | A tempo lane over steps is a view plus edit methods. Ramps would touch `seconds_at` everywhere. |
| Time signature | `Project.time_signature` is one scalar. The core `MeterMap`, grid, rulers, metronome and canvas already take a map. The scalar is assumed in the model, validation, `history.rs`, `transport::timeline_of`, count-in, SMF import and export. | The work is the model, the format, validation and edit commands. The renderers are ready. |
| Rows | A lane under a track needs a new `RowKind` and touches about 15 match sites; the GPU row table has one slot per track index; `Arrangement::rows()` is rebuilt for every hit test (`arrangement/rows.rs`, `clips.rs`). Sends do not add rows, they make the header taller. | Lane rows are cross-cutting. They get their own slice and a preparatory cleanup. |
| Point editing | Reusable gesture logic lives in `note_editor/lane/` (pure `gesture.rs`) and `edit/events.rs`, but it is keyed on integer MIDI values and clip-local ticks. No point simplification exists anywhere. Undo merging per gesture is `Drag{base, merge}` in `document/lanes.rs`. | A float-valued parallel model is needed. Generalise the gesture module, add a simplifier. |
| Curves | `lumen_core::curve::Curve` is a Bézier from (0,0) to (1,1) with `at`, `table`, `handle`; its header names automation as its next user. | Segment shapes reuse it. |
| MIDI in | `lumen-midi` gives one `rtrb` consumer, handed once to `LiveFeed` on the audio thread. The app never sees CC messages (`app/hardware.rs`). The card's "Learn" button is not MIDI learn; it adds the next plugin control touched in a plugin window to the strip. | MIDI learn needs a second tap with timestamps. |
| Clip envelopes | MIDI clips already carry controller events that loop with the clip (`midi_play.rs`, test `notes_and_events_reach_the_engine_sorted_with_their_loop`). Audio clips have gain but no pan or polarity (`ClipContent::Audio{gain_db}`; pan only on `Track`). | MIDI clip envelopes need a check, not a build. Audio gain and pan envelopes are new. |
| Clip edits | `slice`, `clear`, `overwrite`, `trim`, `slip`, `delete_time` (ripple), `insert_time`, copy, paste, duplicate exist. Missing for clips: split, join, crop, consolidate, unloop, reverse, normalize, nudge, polarity, select invert and its variants. Only MIDI notes have split, glue, nudge and reverse. | Most of the editing list is new work, mostly pure functions plus commands. |
| Crossfades | Overlaps are resolved by `overwrite` (clips never overlap). The engine declicks moves (5 ms) and gives every clip edge a 2 ms fade. | An overlap crossfade needs a model decision (§4, X1). |
| Tools and keys | No global tool state; the piano roll has `Tool{Pointer, Draw}`. Plain keys in use include B, L, Q, M, F, X, W, H, Z, 0. A, E, J, S, V are free. Ctrl+E and Ctrl+J are note commands and become clip commands by widening their availability. | The tool model is new state with a key map to pitch. |
| Offline | No production offline renderer, but the pattern exists (`Engine::process` driven directly in `tests/mixer.rs`; `Lanes::update` builds an engine from a document). The plugin host has no offline mode: its process mode is real time and `Guard` turns a late block into silence on a wall-clock deadline. No audio file writer exists (decode and resample only). | Consolidate needs a writer and a worker. Plugin tracks need an offline host mode, which is unproven. |

## 2. Scope and shape

CLAUDE.md §9 lists "Automation and envelopes" (step 7) and "Editing power
tools" (step 8) as separate steps. ROADMAP §7 joins them. They share almost
nothing: automation changes the engine, the model and the lane interface;
editing and rendering change the clip functions, the command table and add an
offline renderer. This plan covers both as two parts, **M7 (automation and
envelopes)** and **M7b (editing and render)**, and asks the owner to choose
whether M7b is its own milestone (S1, §4). M8 keeps its number either way.

## 3. Decisions the evidence settles

Each becomes an ADR when its slice starts. These are not owner preference
calls; the owner may overrule any of them.

**D1. The data shape, named first.**

```
// lumen-core/src/automation.rs  (pure, no I/O)
Point { at: Ticks, value: f32, shape: Shape }        // shape of the segment that leaves this point
Shape { Step, Linear, Curve(lumen_core::curve::Curve) }
Lane  { points: Vec<Point> }                         // sorted, unique times
Lane::value_at(Ticks) -> Option<f32>
Lane::simplify(tolerance) -> Lane                    // for freehand and recording

// lumen-project/src/model.rs
Target { Volume, Pan, Trim, Mute, Send{to: Id}, Device{device: Id, param: u32} }
AutomationLane { target: Target, lane: Lane, enabled: bool }
Track.automation: Vec<AutomationLane>                // the master and returns are tracks too
Project.meter: Vec<MeterPoint { at: Ticks, signature: TimeSignature }>   // replaces the scalar
```

Values are stored in the target's own units (dB for volume, trim and sends,
−1 to 1 for pan, 0 or 1 for mute, 0 to 1 normalised for plugin parameters) and
interpolated in those units, so a linear volume segment is linear in dB.
`Target` has one place that gives each target's range, default, unit and
display mapping.

**D2. Lanes belong to the track that owns the target.** A deleted track takes
its lanes with it. Deleting, moving or copying a device carries its lanes in
the same undo step (`move_device`, `copy_device`, `remove_device` cascade). A
loaded file with a lane whose target does not exist is dropped on validation
with a note, never a crash. Tempo and meter are project-level.

**D3. Time is ticks in the model and samples in the engine.** The UI side
bakes a lane into sample positions when it builds a plan, with the current
tempo map and sample rate. The audio thread evaluates a pure function of the
timeline sample, so loop wraps, tails and scrubs re-read the same values. A
tempo edit rebuilds the plan. Test: a tempo change while playing keeps the
automated value continuous (the timeline and the plan swap on separate
queues; the 5 ms plan crossfade must cover the gap, to be proved in A0).

**D4. Sample-exact points, bounded curve error.** Points land on their exact
sample. Inside a segment the engine evaluates at most every 32 frames and
interpolates linearly between, which keeps the curve error inaudible and the
cost at eight evaluations per 256-frame chunk per lane. The 32 is a starting
value to be measured in A0 (§6). An automated parameter is not passed through
the 20 ms glide (that would lag it); jumps from locate and loop wrap are
crossfaded as the mixer already does.

**D5. The controls show the lane's value from the same function.** The
interface calls `Lane::value_at` at the playhead; it does not read it back
from the engine.

**D6. Plugin automation sends sample-positioned points** through the existing
`ParamQueue` wire: the lane's points inside a block plus curve subdivisions.
The change is `Hosted::submit` gaining a parameter argument and `Link::submit`
filling it. A block that would exceed the region's room is thinned and
counted, as notes are. An automated plugin parameter is not also sent over the
control channel. While a lane drives a parameter, the project's value overlay
(`Device.params`) holds the value at rest, and the interaction with
`hosting/parameters.rs` is the first thing A3 settles in an ADR.

**D7. Override is session state.** A moved automated control sets an override
for that target; the plan is built without that lane until the control's
re-enable is pressed or the project is reopened. It is not saved with the
project.

**D8. MIDI learn taps the live feed, and mapping happens in the app.**
`LiveFeed` copies controller messages, with their driver timestamps, into a
bounded queue the interface drains each frame; overflow is counted. A mapped
move becomes a normal edit with a gesture merge key (one undo step per move)
or a recorded point. This keeps the audio thread free of project knowledge.
The cost is one frame of latency for controller-to-parameter moves, which
recording corrects by using the message timestamp.

**D9. Tempo and time signature lanes are views over the model.** The tempo lane
edits `Project.tempo` as steps. The time-signature lane edits `Project.meter`.
Format v22 migrates the scalar signature to a one-point map.

**D10. One render core.** Consolidate, bounce and render selection use one
device-free render driver in a worker thread (the pattern `Lanes::update` and
the mixer tests already use) and a hand-written WAV writer (16, 24 and 32-bit
float, no new dependency, no licence question). Output is written beside the
project's media and registered like an imported file, so Save copies it.
FLAC waits for M9's export, where its dependency is decided.

**D11. Plugin tracks in bounce and freeze are decided by a spike**, not by
opinion: render the test plugins offline through a separate host process per
plugin and compare against a real-time render. If hosts can render offline
with a repeatable result, they do. If not, plugin tracks bounce by capturing
the live engine (real time, with progress and cancel), and the plan records
that deviation from the quality bar.

## 6. Validation and records

- Gates before each commit: `cargo fmt --all`, workspace clippy with
  `-D warnings`, `cargo test --workspace`. Before pushing: the macOS
  cross-clippy; the WSL mirror and the performance gate for engine and project
  changes (it fails at +2%; new scenarios and any baseline update get their
  reason in the ADR). Real-time paths run under the allocation guard and
  RealtimeSanitizer in CI.
- End of every slice (ADR-0029): the E2E suite and the six smoke tests pass, and
  new E2E scenarios cover each delivered workflow, driven by accessible names
  and keys. E2E waits for what the engine answers, never a fixed time.
- Format: every new persisted field bumps the version with a migration and a
  frozen golden. `history::unchanged` lists every new field.
- Measure: automation cost per lane per block in the audio callback (D4's 32
  frames is tuned here), frame time with 200 tracks and visible lanes at
  100, 150 and 200% scale in both themes, idle CPU, plugin parameter points per
  block against the region's room.
- Specimens come first for visual choices (L1, K1, and small ones for the
  override state and the mapping list), rendered for the owner to choose from.
  Screenshots need GPU or software Vulkan; a bare container cannot render them.
- Manual tests (owner, Windows): MT-AUTO-1 to 8 for A0 to A8 and MT-EDIT-1 to
  5 for E0 to E5. Steps are written in `docs/manual-tests/M7.md` when each
  slice lands, not in advance.
- Records per slice: PROGRESS (rows in §6.5, §6.6 and §7), DECISIONS (one ADR
  per slice, the D-items above), ARCHITECTURE, KNOWN_ISSUES, the handoff in
  `CLAUDE.md`.
- Documentation follows the owner's naming rule: no third-party product names
  as references or examples; anonymous labels for external plugin records.

## 7. Risks

1. **Tempo change while playing.** The timeline and the plan swap on separate
   queues, and lanes are baked against a tempo map. A0 must prove the crossfade
   covers the gap, or carry one tempo epoch in both.
2. **Lane rows are cross-cutting.** About 15 `RowKind` sites and a GPU slot
   table keyed by track index. A1's cleanup comes first so the lane row is one
   addition.
3. **Plugin parameter room.** 64 queues and 1,024 points per block. A project
   that automates many parameters on one plugin could exceed it; thinning is
   counted and shown, and the region version bumps only if A3 measures a need.
4. **Recorded timing.** Controller and plugin-gesture timestamps cross a
   thread or a process before reaching the app. A4 measures their accuracy
   before it promises sample-accurate recording.
5. **Offline plugin rendering is unproven** (D11). If it fails, bounce and
   freeze of plugin tracks deviate from "offline equals real time" and the
   owner decides (F1).
6. **Overlap crossfades and pitch envelopes** are [M] items that this plan
   proposes to defer (X1 A, P1 A). They stay in `docs/PROGRESS.md` as open and
   need the owner's approval to be deferred.
7. **Size.** This is the largest milestone so far. S1 A is the main mitigation.
8. **Cannot be verified in the cloud container:** real controllers, installed
   plugins, the Windows editor window, anything on macOS. Those are the owner's
   manual runs and are named as unverified in each slice's report.

## 8. Alternatives rejected

- **Lanes in a project-level list keyed by target.** Dangling targets and
  cascade logic on every delete; per-track ownership (D2) removes the class.
- **Lane points in samples.** A tempo edit would move every point; ticks follow
  the music.
- **Values stored normalised for every target.** Hides dB-linear behaviour and
  makes the file unreadable by a person (CLAUDE.md asks for a friendly format).
- **Mapping controllers inside the engine.** Needs project knowledge on the
  audio thread; the tap (D8) keeps the engine unaware of mappings.
- **One value per block for plugins.** Cheaper but not sample-accurate, and the
  wire already supports points.
- **A new encoder dependency now.** A hand-written WAV writer settles M7b; the
  FLAC decision belongs to M9 with the export design.
