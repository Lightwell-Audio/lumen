# Milestone 5 — MIDI & Piano Roll: plan

**Status:** Approved 2026-10-10. Owner choices (§4): C1 A (built-in synth
and MIDI out), C2 A plus a way to pull the piano roll out into its own
window, C3 A, C4 A, C5 A (default taken, not asked). Slices 0 and 1 built 2026-10-10 (ADR-0044, ADR-0045; MT-MIDI-1 and MT-MIDI-2 wait for the owner). Slice 2 built 2026-10-11 (ADR-0046; MT-MIDI-3 waits).

**Goal (ROADMAP §5):** make Lumen a usable MIDI production environment:
MIDI devices in and out, MIDI tracks that play and monitor, recording,
the piano roll with velocity and controller lanes, quantize and its
related tools, Standard MIDI Files and MIDI learn.

**Exit criterion:** a user can record a MIDI performance, edit it in the
piano roll, quantize it, play it back and save and reopen it without
changing its musical content.

Requirements covered: CLAUDE.md §6.3 (MIDI, except MIDI effects [S] and
MPE [L]), the MIDI half of §6.9 (MIDI devices), the §7 "MIDI" and
"Recording" MIDI rows, and the computer keyboard as MIDI input.

## 1. Starting point (inspected 2026-10-10)

| Item | Finding |
|---|---|
| Model | `TrackKind::Midi` exists, and `ClipContent::Midi { notes }` stores notes as `[start, length, pitch, velocity]` in ticks (`PPQ` 1,411,200, ADR-0009). There are no controller events, program changes or per-note release velocity. MIDI tracks can be added; they play nothing. |
| Engine | The mixer graph (ADR-0035) runs a node per track, fed by audio clips. There is no MIDI event path, no instrument node and no note tracking. `Engine` already names "MIDI all-notes-off" as joining its stop handling. |
| Devices | No MIDI device layer and no MIDI dependency. Audio devices (M2) have hot-plug handling to follow. |
| Instruments | None: VST3 hosting is M6, the built-in synth and sampler M8. **Nothing can sound a note yet** (choice C1). |
| App | M4.5's widgets (switch, segmented, value slider, empty state, menus, motion) are ready for the piano roll. The detail panel has a Clip tab, greyed until now. The editing grid, snapping, selection, drags and undo (M3) are shared code the piano roll reuses. |
| Gates | Instruction-count gate (+2%), frame-time benchmark by hand (stress project: 200 tracks, 20,000 clips; the 100,000-note part of the quality bar is still unmeasured), real-time safety under the allocation guard. |

## 2. Risk register

| ID | Risk | Impact if late | Addressed by |
|---|---|---|---|
| R1 | Notes hang: a note-on whose note-off is lost on stop, jump, loop, mute, edit, plan swap or device change. | A stuck note; trust lost | Slice 1: one note tracker per instrument input, flushed on every one of those events, with an E2E scenario for each and a panic command |
| R2 | MIDI timing jitters: events land on block edges instead of their sample. | Sloppy playback and recordings | Slice 1: events carry a sample offset within the block; golden renders check note starts to the sample. Slice 6: input timestamps from the driver, corrected by the input latency |
| R3 | The piano roll misses the frame budget with 100,000 notes. | Fails the quality bar | Slice 3: notes drawn on the GPU as the clip bodies are (ADR-0026), a 100,000-note stress clip in `--bench-frames` from the first piano-roll slice |
| R4 | The computer keyboard's letters fight existing shortcuts (H, W, X, Z, M). | Keys do the wrong thing | Choice C3: a mode that takes the letters while on, shown in the transport, Esc or its toggle to leave |
| R5 | A device layer that blocks the UI (enumeration, a port that hangs on open). | Freezes | Slice 0: enumeration and opening off the UI thread, as the audio device probe does |
| R6 | Format change for controllers and program changes breaks old projects. | Lost work | Slice 0: format v11 with a migration and golden fixture; notes keep their compact form |
| R7 | Quantize loses the performance. | Can't undo a feel | Slice 5: quantize is an undoable edit; recorded timing kept alongside (the [S] "restore recorded timing" if cheap; otherwise recorded for later) |

## 3. Slices

Every slice ends with E2E scenarios for what it delivers, the smoke
tests, and a manual test (MT-MIDI-*). New visuals (the piano roll, lanes,
note colours, the quantize popover) are shown as rendered specimens before
building, and behaviour variants pitched with a recommendation.

### Slice 0 — MIDI devices and the model (format v11)
- A MIDI device layer (midir, MIT; WinMM on Windows, CoreMIDI, ALSA):
  inputs and outputs listed with switches for Track and Remote, hot-plug,
  opened off the UI thread. A MIDI page in the settings window.
- Format v11: controller, pitch-bend, pressure and program events in MIDI
  clips beside the notes, with a migration and a golden fixture.
- **Pass:** devices appear and disappear with hot-plug (E2E on a virtual
  test device); the format round-trips; old projects open unchanged.

### Slice 1 — Hearing MIDI: the event path and an instrument
- MIDI events through the mixer graph: a MIDI track's node takes events
  with sample offsets, feeds its instrument, and the instrument's audio
  carries on as an audio track's does (volume, sends, groups).
- The instrument chosen in C1, plus "MIDI To" for external hardware.
- Notes never hang (R1): one tracker per instrument input, flushed on
  stop, jump, loop, mute, edit, plan swap and device loss; Panic.
- Sustain, pitch bend, aftertouch and program/bank change pass through.
- **Pass:** golden renders (note starts to the sample, sustain holds, a
  loop wrap releases), every hang case as an E2E scenario, zero heap
  operations while playing.

#### Slice 1 plan (2026-10-10)

**Owner choices, asked before building** (owner-decisions table, "Hearing
MIDI"), all as recommended:
- **S1 Warm poly** is the default sound: two saws ±7 cents, a 12 dB
  low-pass at 2.4 kHz with a little velocity to cutoff, A 5 ms, D 300 ms,
  S 70 %, R 250 ms, 16 voices, the oldest stolen.
- **E1 presets in a menu** until the device chain (M6/M8): Poly, Keys,
  Bass, Pluck, Pad, from the track's right-click menu ("Instrument ▸") and
  the palette, saved with the project as the track's built-in device. No
  knobs yet.
- **T1 one or the other**: a MIDI track plays its instrument *or* a MIDI
  output port and channel ("MIDI To ▸"), as in Ableton. Choosing a port
  silences the instrument, which stays on the track for switching back.
- **H1 chase notes and controllers**: Play or a jump inside a held note
  starts it at once; the latest sustain, pitch bend, pressure, controllers
  and program before the position are applied first.

**Defaults taken (standard behaviour, recorded in the ADR):**
- Stop, a jump, a loop wrap, a clip mute, an edit that removes or moves a
  sounding note, an instrument or MIDI To change, a port vanishing and
  Panic all **release** notes (note-off; the synth's release tail rings
  out). Panic also cuts the tails at once and sends All Notes Off and All
  Sound Off (CC 123, 120) on every channel of every MIDI To port in use.
- Track mute and solo act on the instrument's audio (the mixer), as in
  Ableton: the synth keeps receiving notes, so unmuting mid-note is
  heard. A **MIDI To** track that is muted or silenced by solo sends
  nothing, and releases what it was sounding.
- Tempo changes move note ends with the music (ends are kept in ticks).
- Scrubbing plays no MIDI.
- The synth listens on every channel; pitch bend ±2 semitones; CC 64
  sustain; CC 1 and channel pressure open the filter a little; program
  changes 0–4 choose the five presets; bank select passes through to MIDI
  To ports and is ignored by the synth.
- New MIDI tracks get the synth on Poly. MIDI tracks in older projects
  have no instrument ("Instrument ▸ None") and stay silent until one is
  chosen (they could hold no notes before format v11, so nothing that
  sounded goes quiet).

**Built in four parts, each ending green and committed:**

- **1a The event path (engine).** A short MIDI message type both sides
  share (in `lumen-core`, so the engine stays on core and rt). MIDI clips
  reach the engine as their own list beside the audio clips (built on the
  UI side by a pure, tested `engine_midi_clips`, swapped whole through a
  queue, old lists returned to be freed), with loop repeats. Each block,
  every MIDI track gets its events with sample offsets into a
  fixed-capacity buffer on its node; ends come from one note tracker per
  instrument input. Chase on Play and jumps. Every release case above.
  The engine's Panic and stop reach the sources. Tested with a probe
  instrument that writes an impulse per note-on and records what it was
  sent: note starts to the sample at several tempos and rates, across
  tempo changes, loop wraps and block edges; every note-on has its off.
- **1b The synth and the model (format v12).** Built-in devices get a
  crate, `lumen-devices` (pure, real-time-safe DSP on `lumen-core`, grown
  by M8); the engine's layering rule is amended to allow it (ADR).
  Anti-aliased oscillators, a state-variable filter, ADSR, sample-accurate
  sub-blocks split at event offsets, voice stealing with a short fade, the
  five presets. A node's instrument renders into its bus ahead of trim,
  so volume, pan, sends, groups, solo, cue, meters and delay compensation
  apply unchanged. Voices carry across plan swaps by node id; a removed
  or changed instrument releases and crossfades with the plan. Format
  v12: the instrument is a built-in device on the track with a stable id
  (never the product name in the file) and its preset; the track's MIDI
  To (port name and channel, remembered while unplugged). Migration,
  golden fixture, validation, `history::unchanged`. `Document` methods
  (one undo step each) and the menus: "Instrument ▸" and "MIDI To ▸"
  (ports, then channel) built with `widgets::submenu` and `menu_toggle`;
  palette commands for the five presets and "MIDI To: Instrument".
- **1c MIDI To.** Events for a MIDI To track leave the engine through a
  lock-free queue stamped in device samples; an app-side sender maps them
  to wall-clock time (with the output latency and the routing's delay
  compensation, so hardware lines up with what is heard) and sends them
  on time through `lumen-midi`. Port loss drops them, changing the port
  releases on the old one. Tested on the fake backend: every note-on has
  its off, order and spacing kept, timing within 2 ms of plan.
- **1d Panic, close and records.** Panic as a palette command (no default
  key) as well as the audio panel's button. E2E scenarios for hearing a
  MIDI track, each preset, each release case, chase, MIDI To on the fake
  device, and Panic; `tests/projects/midi-demo.lumen` (chords, a held pad
  for chase, sustain, pitch bend, a loop brace) for the owner's manual test
  **MT-MIDI-2**, since notes cannot be drawn until slice 3. A perf
  scenario `engine_synth_64` (64 MIDI tracks playing chords), its baseline
  and the measured share of a 128-frame block at 48 kHz; the allocation
  guard over playing MIDI. ADR-0045, PROGRESS, ARCHITECTURE, KNOWN_ISSUES
  and CLAUDE.md §12.

No new visuals: the slice only adds menu rows built from existing
widgets. If something visual turns out to be needed, it is mocked up for
the owner first.

### Slice 2 — Playing live: monitoring, thru and the computer keyboard
- "MIDI From" per track (all inputs, a device, a channel) and monitoring
  In / Auto / Off, as audio tracks will have it: an armed or selected MIDI
  track plays what comes in (MIDI thru).
- The computer keyboard as a MIDI keyboard (C3), with octave and velocity
  keys and an indicator in the transport.
- **MIDI activity light and quick toggle** (owner, 2026-10-10): a MIDI chip
  in the transport bar beside the audio status. It flashes (a defined light
  level, faded out) when an enabled input sends a note, controller or
  clock message, rests dim when inputs are open but quiet, and is grey
  with none on. Clicking it opens a popover listing every input and
  output with Track and Remote switches and a link to the MIDI settings,
  as the audio status opens the audio panel. Option to pitch: a small
  light on a track's header when its input is active. Specimens of the
  chip and popover first.
- **Pass:** E2E plays the keyboard into a track and hears it; E2E sends
  a note from the virtual device and sees the light flash, then toggles
  the port from the popover; a manual
  test with the owner's MIDI controller, if one is available (§5).

#### Slice 2 plan (2026-10-11)

**Owner choices, asked before building** (specimens on the "MIDI: Playing
Live" design canvas, an A and a B board for each). **The owner chose every
recommendation (L A, J A, C B, K A, H B, R A) and Ctrl+Shift+K** (owner-decisions
table, "Playing live"):

| # | Question | A | B | Recommendation |
|---|---|---|---|---|
| L | Which MIDI tracks play what comes in? | **The selected MIDI track listens** without being armed (a hollow arm ring shows it), plus every armed track (Ableton's auto-arm) | Only armed tracks listen (Cubase, Logic) | **A**: one click to play a sound, as Ableton users expect; arm keeps meaning "record" in slice 6 |
| J | Live timing | **Steady**: each message is placed at its driver timestamp, one buffer later (2.7 ms at 128 / 48 kHz), so the spacing is exactly as played | At once: at the start of the next buffer, 0 to one buffer late, so the spacing wobbles by up to a buffer | **A**: what Ableton and Cubase do; recording in slice 6 uses the same stamps, so what is heard is what is kept |
| C | The MIDI chip and its popover | A word, "MIDI", with one light; the popover lists ports with Track and Remote switches | A DIN glyph with in and out lights; the popover's rows each show their own traffic, with Track and Remote pills, and unplugged ports dimmed | **B**: it answers "is my keyboard reaching Lumen?" per port, which is the question when nothing sounds; the out light confirms MIDI To |
| K | The computer keyboard's indicator | A lit keycap button and a readout (`C3–C4 · vel 100`) | The button and a one-octave keyboard in the bar showing the keys pressed | **A**: quiet chrome, and the info line already teaches the letters; B costs 150 pt of a bar that is full at 960 pt |
| H | A light on track headers | None: the chip is the only light | A light by the name of each listening MIDI track, flashing on each note it gets | **B**: shows which track hears you, the owner's own suggestion; nothing lights on tracks that do not listen |
| R | Where MIDI From and Monitor are set | The track's right-click menu (From, To and Monitor together) and two rows on the mixer strip | On the header of tall tracks, as Ableton's I/O section, with an "I/O" button on short rows | **A**: headers stay calm; the mixer shows many tracks' routing at once |

The toggle key for the computer keyboard (C3): **Ctrl+Shift+K**
(rebindable). Ableton uses M, which Lumen gives to Set locator (slice 5 of
M3); taking it would change a key the owner has been using.

**Defaults taken (standard behaviour, recorded in the ADR):**
- MIDI From: All inputs (every input switched on for Track, and the
  computer keyboard) and all channels, as Ableton. A device's port is
  remembered by name while unplugged, as MIDI To is.
- Monitor: Auto (the track listens when it is selected or armed, per L),
  In (always listens), Off (never). Format v13 stores `monitor` on every
  track kind, since audio tracks get it in M9; audio tracks do not show it
  until then.
- MIDI thru follows the track's MIDI To: what comes in plays its instrument,
  or leaves on its port and channel (rechannelled to the track's channel).
- Live notes never hang: one tracker per track for live notes, apart from
  the clip notes. Monitoring ending (selection moves, Monitor off, the
  track's From or To changing, a port unplugged, the track deleted), the
  computer keyboard mode ending, the window losing focus (for the computer
  keyboard) and Panic all release what was played. Stop and jumps do not
  (a held key keeps sounding, as in every DAW). The pedal is released with
  the notes.
- A live note and a clip note on the same pitch both sound (the synth
  takes a second voice); each source lets go of its own.
- The computer keyboard follows Ableton: A to K white keys from C, W E T Y
  U black keys, Z and X octave (C-2 to C8, starting at C3), C and V
  velocity (1, 20, 40 … 120, 127, starting at 100). Key repeats are
  ignored. While on, only these letters are taken: Ctrl chords, Space, Esc
  (which leaves the mode), the arrows and Tab keep working. Text fields
  take keys first. The mode is not saved with the project.
- The activity light flashes for note, controller, pitch bend, pressure
  and program messages; clock (slice 7) and active sensing do not flash it
  (active sensing would keep it lit). Lights use the light layer's BEAM
  level, fading over `motion::NOTE`.

**Built in five parts, each ending green and committed:**
- **2a The live path (engine).** Input messages carry the driver stamp
  and the time they arrived; the app maps them to device frames with the
  stream clock (the inverse of MIDI To's mapping) and sends them to the
  engine on a lock-free queue. Each block the engine places them at their
  frame (J) on every listening track: into the instrument beside the clip
  events, or out to the track's MIDI To port. The listening set comes from
  the app with the clip lists. Live trackers and every release case above.
  Engine tests with the probe instrument: frames to the sample, every
  note-on has its off, the allocation guard over live input.
- **2b The model and the menus (format v13).** `Track::midi_from`
  (port name or all, channel or all) and `Track::monitor`; migration,
  golden fixture, validation, `history::unchanged`. `Document::set_midi_from`
  and `set_monitor` (one undo step each); the menus and the strip rows (R).
- **2c The computer keyboard.** The mode, its keys, octave and velocity,
  the transport indicator (K) and the info line; the keyboard as an input
  named "Computer keyboard" in MIDI From.
- **2d The chip, the popover and header lights** (C, H). Activity counted
  per port in the device layer's callback (an atomic per port, read each
  frame while the window is shown); repaint only while a light fades.
- **2e Close.** E2E: the keyboard plays a track and is heard; a note from
  the fake device flashes the chip and the header light; the popover
  switches a port; every release case; L's selection rule. MT-MIDI-3 with
  the owner's controller (or loopMIDI). ADR-0046, PROGRESS, ARCHITECTURE,
  KNOWN_ISSUES and CLAUDE.md §12.

### Slice 3 — MIDI clips and the piano roll
- MIDI clips in the arrangement: create one (double-click an empty MIDI
  lane, or a command), see its notes drawn on the clip body, and every M3
  clip edit (move, trim, loop-extend, split, duplicate, mute, colour).
- The piano roll (C2): draw, select, marquee, move, resize, split, glue,
  mute, duplicate, nudge, transpose, legato; note audition while editing;
  zoom and snap shared with the arrangement; notes on the GPU.
- **Pass:** E2E for every edit and its undo; `--bench-frames` with a
  100,000-note clip at p99 inside the 120 fps target.

### Slice 4 — Velocity and controller lanes
- A velocity lane (drag a stem, draw across stems, box-select), and lanes
  for CC, pitch bend and pressure, with pencil, line and curve tools.
  Curves reuse `lumen_core::curve` (the fades' free curves, ADR-0031).
- **Pass:** E2E draws each lane and plays it back; golden renders for
  pitch bend and CC timing.

### Slice 5 — Quantize and its tools
- Quantize: grid from whole note to 1/128 with triplet, dotted and custom
  values; start, end, start and end, or length; strength, swing,
  sensitivity window and iterative mode. Q applies the last settings;
  Shift+Q opens the options popover with a live preview (C5).
- Humanize (timing and velocity), legato, fixed length, transpose,
  scale-constrain and reverse, as commands on the selected notes or clips.
- **Pass:** unit tests for every mode against hand-worked cases; E2E Q and
  Shift+Q; one undo step each.

### Slice 6 — Recording MIDI
- Record, overdub and replace (C4), count-in, punch in and out, recording
  on several armed tracks at once, crash-safe capture (an in-progress
  recording survives a crash through autosave).
- Input timing: driver timestamps, corrected by the input latency, so
  recorded notes land where they were played.
- **Pass:** E2E records from the virtual device and checks note positions
  to the sample; the owner's manual test with a controller.

### Slice 7 — Files, learn and clock
- Standard MIDI File import and export (clips and tracks, type 0 and 1,
  tempo and time-signature maps).
- MIDI learn for any parameter (mixer controls now, plugin parameters
  when M6 arrives), with a mapping list; MIDI clock out.
- **Pass:** SMF round-trips its notes, controllers and tempo map (golden
  files); E2E learns a fader from the virtual device.

### Slice 8 — Close
- The exit walkthrough as E2E (record a part, edit it, quantize, play,
  save and reopen with identical content) and its manual test; the
  `lumen-review` review and its fixes; the report.

## 5. Testing limits

- No physical MIDI controller has been listed for the owner's machine.
  E2E drives a virtual device; manual tests need a controller (or a
  virtual port such as loopMIDI) to check real timing.
- Hardware "MIDI To" needs an external instrument, or the OS synth.
- macOS and Linux MIDI by cross-target clippy and CI only.

## 6. Not in this milestone

- MIDI effects (arpeggiator, chord, scale, velocity, note length) [S] →
  M8 with the built-in devices.
- Drum maps, the drum editor and the step sequencer → M8.
- Loop recording into takes and Capture MIDI [S] → M9.
- Scale highlighting, fold, ghost notes, multi-clip editing, step input
  [S] → after the core piano roll, if time allows in slice 3 or 4;
  otherwise M10.
- MPE and MIDI 2.0 [L].
