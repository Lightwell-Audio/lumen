# M9 R6 — Disk streaming and the peak cache: plan

**Status:** Built, 2026-10-28 (ADR-0108; MT-STREAM-1 pending). The owner
chose **L A, M B, C A, D A, S B** on 2026-10-27 (§4; DECISIONS, owner table).
R6 is one slice. Audio is kept in memory automatically, with no per-clip
switch and no format change. One change from §2 and §5 step 3, made while
sizing the pool: the disk thread reads the playhead's whole read-ahead
before the places playback can jump to, so continuous playback is never
cut short by many markers (ADR-0108, item 4). A second model reviewed the
branch on 2026-10-28; its findings and the fixes are at the end of
ADR-0108 (renders fail on an unreadable page, a real-time export reads its
streamed files into memory first, a ready start replaces a held one, the
cache trim counts only what it removed).
Branch: `m9-s6-disk-streaming`, cut from `origin/main` at `a91d1989` (after
PR #73). The owner chose R5 A on 2026-10-24: streaming comes after recording
and export, as a switch you turn on yourself until a soak at 64 and 128 frames
passes, and then it becomes the default.

**Goal (CLAUDE.md §6.2, §4).** A large session plays smoothly from disk with
seamless loops and immediate seeking. Memory no longer grows with the length
of the project's audio. A project that was opened before shows its waveforms
at once. Nothing a user hears or edits changes because streaming is on.

## 1. What the code gives us

| Area | Fact (pointer) | Consequence |
|---|---|---|
| Playback | The clip player reads `clip.audio.channels[side][frame]` directly (`lumen-engine/src/clips.rs:447`). `ClipAudio` is the whole file at the device rate, in memory, shared by `Arc`. | The audio thread needs a second way to read audio: a slot that a disk thread keeps filled ahead of the playhead. The `Source` interface stays the same. |
| Loading | `lumen_media::load` decodes the whole file with symphonia and converts it to the device rate with rubato's FFT resampler. Then it builds peaks on the same thread (`app/media.rs`). | A project opens only as fast as it can decode and convert every file, on every open. Opening a large project a second time costs the same as the first time. |
| Other readers of the audio | Twelve app modules read `ClipAudio` from memory: bounce, freeze, join (`consolidate.rs`, `render_audio.rs`), export (`export_render.rs`), normalize, reversed copies (`media/twins.rs`), deep-zoom samples (`arrangement/samples.rs`), `clip_flags_render.rs`, `lanes.rs`, and others. | Every one of them must read through one reader, which blocks when it is used off the audio thread. Otherwise streaming would make them silent or wrong. |
| Offline render | `render_source` drives the same clip player without a device (bounce, freeze, join, export). | An offline render can wait for the disk. It reads on the render's own thread, so its output is the same as with everything in memory. Offline and real-time output stay equal, which the golden renders check. |
| Recorded takes | 32-bit float WAV at the device rate, in `Recordings` and `Samples/Recorded` (ADR-0102). | A take streams from its own file. It needs no conversion. |
| Peaks | Built in memory at load: signed 8-bit, seven levels, about 5 MB per 5 minutes of stereo (ADR-0027). The atlas never reclaims them after a rate change (KNOWN_ISSUES, M3 4c). | The disk cache stores this same structure. The atlas reclaim is fixed here. |
| Status | The transport's status chip shows CPU and dropouts (`transport/status.rs`, `dropouts.rs`). | The disk read load and the underrun count go in the same place. |
| Known issues routed here | Export holds its decoded render in RAM, and WAV export stops at the RIFF limit (ADR-0107). A reversed clip holds a second copy of its audio (ADR-0093). | These are proposed as R6b (§4, S). |

## 2. Shape

When streaming is on, every audio file plays from a **stream file**: a file
the disk thread can read at any frame without decoding.

- **A WAV or AIFF file in PCM or float at the device rate** is its own stream
  file. This covers recorded takes, renders, and most imported studio files.
- **Any other file** (a different rate, FLAC, MP3, Ogg) is converted once, in
  the background, to a 32-bit float WAV at the device rate in the cache (§4,
  C). The file's peaks are written beside it.

A **disk thread** keeps, for each clip that can play in the next few seconds,
a ring of audio ahead of where the audio thread will read. The audio thread
only copies from the rings and posts where it is (atomics). It never waits. If
a ring is empty, the clip is silent from that point and fades back in, and the
underrun is counted and shown.

**Prefetch:**
- The disk thread keeps the region after the loop start resident for every
  clip there, so a loop wrap is always seamless.
- It keeps the region after every locator and marker resident.
- It reloads around the playhead after each locate.

On a locate to anywhere else, the playhead waits until the audio is ready, for
at most 150 ms (L A).

**Memory is automatic (M B).** A file shorter than about 30 s stays in memory
and plays as it does today; measurement settles the exact number. One-shots
and drum hits therefore never touch the disk thread. The user has nothing to
set.

## 3. Decisions the evidence settles

| # | Decision | Why |
|---|---|---|
| S1 | **Stream files are read with plain positioned reads on the disk thread. Memory maps are not used.** | A memory-mapped read on the audio thread can page-fault, and a page fault is blocking I/O (hard rule 1). |
| S2 | **One disk thread with a pool of slots** of fixed size, allocated when the engine starts. Read-ahead is about 2 s per slot, settled by measurement. The pool grows only off the audio thread, and only between clip lists. | No allocation on the audio thread. The size is bounded and known: about 0.75 MB per stereo slot at 48 kHz. |
| S3 | **The disk thread plans from the same clip list the engine plays**, with the playhead and the loop region published by the engine. | One source of truth. The thread never guesses what the engine will play next. |
| S4 | **Offline readers block, and the audio thread never does.** The engine's clip audio becomes `Memory(Arc<ClipAudio>)` or `Stream(slot)`. Offline renders and the other app readers use a blocking reader over the same stream file. | Renders stay identical to real time and need no read-ahead tuning. |
| S5 | **Cache entries are keyed by the file's path, size, modified time and rate.** A changed file is converted again and never served stale. | The same rule holds whether the source was imported, recorded or relinked. |
| S6 | **The switch is "Play audio from disk"** in the audio settings, off by default (R5 A). The default flips in this slice only if MT-STREAM-1 and the automated soak pass. | The owner's R5 A. |
| S7 | **A device-rate change** converts the files that need it again in the background, and their clips stay silent until then, as today (ADR-0019). Peaks of the old rate leave the atlas. | Same behaviour as today, and it closes the KNOWN_ISSUES row about the atlas. |
| S8 | **The soak has two parts.** An automated part runs in CI: the fake backend and a disk thread with injected delays play 64 streamed tracks with loops and locates, and count the underruns. A manual part runs on the owner's machine at 64 and 128 frames for 30 minutes (MT-STREAM-1). | The quality bar (§4) asks for no dropouts at 64 and 128 frames. Only real hardware can prove that. |

## 4. Choices for the owner

Answer by label, for example "L A, M A, C A, D A, S A".

### L — What you hear on Play or a locate before the audio is read

On an SSD the read takes about 5 to 20 ms. On a slow or busy disk it can take
longer.

- **A (recommended). The playhead waits until the audio is ready**, for at
  most 150 ms, and then starts anyway. MIDI, the metronome and the clips all
  start together. While playing, a click in the ruler holds at the new place
  for the same short moment. On an SSD you will not notice the wait. Nothing
  starts late or out of time.
- **B. Never wait.** The transport moves at once. A streamed clip whose audio
  is not read yet is silent and fades in when it arrives, so the first beat of
  a drum loop after a locate can be missing while MIDI already plays.

### M — Keeping audio in memory

- **A (recommended). Automatic, plus a per-clip switch.**
  - Short files stay in memory automatically.
  - The clip menu and the clip card get **Keep in memory**, which holds only
    the part of the file the clip plays, for a clip that must never wait.
  - The clip is marked with a small chip.
  - Saved with the project (format v33).
- **B. Automatic only.** No control and no format change. A clip that must
  never wait cannot be pinned.
- **C. Per file, in the Project media tab.** It holds whole files, so it
  takes more memory than A.

### C — Where converted audio and peaks are kept

- **A (recommended). Lumen's cache folder** (`%LOCALAPPDATA%\Lumen\Cache`),
  with a size limit (default 20 GB). When the folder is over its limit, the
  oldest entries are cleared, never those the open project uses. Projects
  stay small and portable. A project moved to another machine converts its
  files there once. Choosing the folder and a Clear button come with R7's
  Preferences.
- **B. Inside the project folder** (`Cache/`). The cache travels with the
  project, so it opens at once on another machine. Projects grow by a float
  copy of every converted file (about 23 MB a minute of stereo), and Save a
  copy and Collect and save must skip the folder.

### D — The disk indicator

- **A (recommended). In the status chip and its panel, beside CPU.**
  - The panel gets a Disk row: read load, and underruns since start (with
    Reset).
  - After an underrun, the chip turns amber as it does after a dropout, with
    a tooltip that says what happened and what helps.
  - Nothing new appears in the bar while all is well.
- **B. A separate disk meter in the transport bar**, always shown when
  streaming is on. I would show you rendered specimens before building it.

### S — How the slice is cut

- **A (recommended). Two slices.**
  - **R6** is streaming: the reader, the disk thread, prefetch, L, M, D, the
    switch, the soak and MT-STREAM-1.
  - **R6b** is the caches and the rest: the peak cache on disk, the cache
    limit and its clearing, export and normalize in blocks with RF64 beyond
    4 GiB, reversed copies as stream files, and the atlas reclaim.

  R6 already converts files into the cache, and R6b adds the limit and the
  peaks. Each slice ends with a usable, tested step.
- **B. One slice** with all of it. One manual test, but the riskiest
  real-time change in M9 would share a branch with unrelated file work.

## 5. Work (one slice, S B)

1. **Reader and stream files.** `lumen-media`:
   - a stream-file reader that works on any frame range (WAV PCM and float,
     AIFF);
   - the background conversion to a cache file;
   - the cache key (S5).

   Tests: read anywhere, read at the end of a file, convert, a file that
   changes after it was cached.
2. **The engine's slots.** In `lumen-engine`:
   - `ClipSource::{Memory, Stream}`;
   - the slot pool;
   - the audio thread's copy, and silence with a fade on an underrun;
   - the published playhead, and L's wait in the transport.

   Under the allocation guard and RTSan. Golden test: a streamed project
   renders bit-identical to the same project in memory.
3. **The disk thread.**
   - It plans from the clip list (S3).
   - It reads ahead and prefetches loops and locators.
   - Measurement and tests run with injected slow reads (underruns are
     counted and never block).
4. **The app.**
   - The library opens stream files instead of decoding when streaming is on.
   - The twelve readers go through the blocking reader (S4).
   - The automatic memory rule (M B).
   - D A: the Disk row in the status panel, and the amber chip after an
     underrun.
   - The S6 setting.
5. **The peak cache and the cache's limit** (formerly R6b).
   - Peaks are written beside each cache entry. A file whose peaks are cached
     shows its waveform on open without being decoded.
   - The 20 GB limit: the oldest entries are cleared first, and never one the
     open project uses (C A).
   - The atlas reclaims the peaks of the old rate after a rate change, which
     closes the KNOWN_ISSUES row.
6. **Files without whole-file RAM** (formerly R6b).
   - Export encodes and measures loudness in blocks.
   - WAV export writes RF64 beyond 4 GiB.
   - Normalize scans through the reader.
   - Reversed copies become stream files.

   This closes the two KNOWN_ISSUES rows routed to R6.
7. **Soak and gates.**
   - The automated soak (S8). Perf-gate benches for the slot copy and the
     disk thread's plan.
   - Memory measured on the stress project with streaming off and on.
   - Open time measured on the stress project, with a cold and a warm cache.
   - E2E scenarios:
     - play, loop and locate with streaming on;
     - a short file stays in memory;
     - an injected underrun shows in the chip;
     - bounce and export are equal with streaming on and off;
     - a reopened project shows its waveforms from the cache;
     - a changed source file is converted again.
8. **Records.**
   - ADR-0108.
   - ARCHITECTURE, PROGRESS, KNOWN_ISSUES, and the handoff in CLAUDE.md §12.
   - MT-STREAM-1 in `docs/manual-tests/M9.md`: Focusrite, ASIO at 64 and 128
     frames, a 64-track project, 30 minutes with loops, locates and editing,
     counted underruns and dropouts.

## 6. Risks

1. **Underruns on the owner's disk at 64 frames.** The read-ahead is sized in
   seconds, not buffers, and the switch stays off until MT-STREAM-1 passes.
2. **The disk thread's plan disagrees with the engine** (a clip moved under
   the playhead, a loop changed while playing). Mitigation: the plan reads the
   same clip list, and the E2E scenarios edit while playing.
3. **Twelve readers move to a new API.** Any one that is missed plays silence
   or renders wrong with streaming on. The golden test that compares streaming
   on and off covers bounce, freeze, join and export.
4. **Slice size.** With S B, this branch carries the riskiest real-time change
   in M9 together with the file work. The work is committed in the order of §5,
   so each part is tested before the next starts.
5. **Without a per-clip switch (M B)**, a clip on a very slow disk cannot be
   pinned in memory. If MT-STREAM-1 shows underruns, the automatic rule is
   widened (for example, a file that underruns stays in memory) rather than
   adding a control.
