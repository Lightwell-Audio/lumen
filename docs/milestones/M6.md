# Milestone 6 — VST3 Hosting & Device System: draft plan

**Status:** Started 2026-10-15 at the owner's instruction ("start
milestone 6"). The owner has not yet signed off M5; its closeout items stay
open and are tracked in PROGRESS and M5.md (see §1). Slice 0 is under way:
its code is built (parts 1 to 3); the first Windows measurements are recorded
in MT-VST-0; the architecture ADR remains open. Slice 1 (plugin discovery)
started 2026-10-16 on `m6-s1-plugin-scan`; see its plan below. Based on `main`
at `72d875f`.

**Goal:** load a real VST3 instrument and effects from the browser, play
and edit through a usable device chain, save and reopen their sound, and
survive a plugin crash or hang without losing the project or stopping
unrelated audio.

**Scope:** Windows VST3 hosting, as already decided by the owner
(DECISIONS, 2026-10-06). macOS/Linux keep building and testing the shared
code; native hosting there remains the unscheduled stretch goal. The
roadmap's isolation work moves to the beginning: every production plugin
runs in a child process from its first usable slice. Full automation and
MIDI learn are M7; this milestone supplies their parameter/event interface.

## 1. Starting point and entry gate

- M1 has scanner, IPC and real-plugin host prototypes in
  `prototypes/{vst3-scan,isolation-ipc,plugin-host}`. A third-party instrument was processed
  and restored after a child-process crash. These are evidence, not an
  integrated production host. `docs/PLUGIN_COMPATIBILITY.md` distinguishes
  scanning from processing, state and editor compatibility.
- M4 has routing, sidechain taps and delay compensation, tested with a
  synthetic delay. The graph's buses are stereo. Real plugin bus layouts,
  latency changes and multi-output routing still need implementation.
- M5 has sample-offset MIDI events, live input, the fixed-preset built-in
  synth and MIDI To. The device chain must preserve those projects and
  the existing instrument-versus-hardware-output behavior.
- The detail panel, browser shell, commands, undo/history, versioned
  project format (currently v15), atomic saves and recovery exist.
- The project model already stores device IDs, VST3 class references,
  bypass and opaque state. Reuse and extend that scaffolding. The engine
  currently has a separate in-process instrument interface and synthetic
  audio effects; a shared chain adapter is still needed. Keep VST3/COM,
  process management and disk work outside the engine, preserving its
  dependencies on core, RT and devices.

Before implementation, reconcile M5's recorded closeout: MT-MIDI-7 to 9,
the imported-file and native-editor rechecks, remaining platform/perf
checks and the milestone report. Record actual results; do not turn a
pending manual check into a pass. M4.5's pending manual checks stay visible
too. Planning M6 does not assert that M5 is complete.
Also reconcile ADR-0005's stale section status ("Proposed") with its
accepted index/owner decision and recorded prototype results; the M6
signalling/grouping details remain subject to fresh measurements.

## 2. Risks to settle first

| Risk | Experiment and decision gate |
|---|---|
| Waking child processes misses short-buffer deadlines | Repeat M1's event, spin and hybrid experiments with real processing at 64/128/512 frames, 44.1/48/96 kHz, 1/8/16 hosts, warm and idle/Balanced states and CPU contention. Measure round-trip p50/p99/p99.9/max, misses, callback time and idle CPU. M1's event p99 varied from about 20 to 242 µs; its best run is not a guarantee. Choose signalling and process grouping from the results. |
| An OS wait conflicts with the RT no-blocking rule | Resolve ADR-0005's proposed callback wait versus the architecture skill's rule before integration. Prototype bounded polling with worker-side signalling and compare its CPU cost. Record the RT contract and allocation/lock/blocking checks in an ADR; do not silently exempt the callback or add a buffer. |
| A late child writes into reused memory | Versioned IPC, block sequence and configuration generation; reject stale results. Inject late completion, crashes during writes, malformed counts and restart races. Reconfiguration and resource retirement occur off the callback. |
| Plugin state capture hangs or races a save | Exercise component and controller state while processing and editing. Background capture with a timeout, immutable last-good snapshots and generation checks; a save must disclose stale state or failure rather than claim a fresh snapshot. |
| Plugin editors freeze focus or Lumen | Prototype a child-owned top-level editor, resize callbacks, typing, shortcuts, close/reopen, monitor/DPI changes and a hung editor. No cross-process child-window parenting. |
| Dynamic latency and buses invalidate the graph | Test latency/bus-change notifications during playback; rebuild off the callback and swap at a boundary. Compare impulses through dry, group, return and sidechain paths. Include compensated scrubbing (KNOWN_ISSUES). |

Target: retain the existing +2% instruction gate for existing scenarios;
add isolated-host scenarios and explicit baselines. At 128 frames/48 kHz,
the whole 64-track callback should stay below half its 2.667 ms period
(1.333 ms), measured separately from IPC. Arbitrary third-party DSP cannot
be promised that budget: use a documented representative workload and
report its plugin count, presets and machine. No steady-state misses in
that workload; fault injection must leave unrelated paths running. Report
tail latency and missed deadlines, not only averages.

### Slice 1 plan: plugin discovery (branch `m6-s1-plugin-scan`)

The owner started slice 1 on 2026-10-16 while slice 0's architecture gate
(the audio-path ADR) is still open: nothing here touches the audio path.
Owner choices so far: scan **at startup in the background**; a plugin that
crashes or hangs during a scan is **blocked with its reason and retried only
when its file changes or the user presses Retry**; the browser layout is
chosen from rendered specimens before any interface is built.

**What exists.** `lumen_plugin_host::Module::load` and `classes()` read a
module's factory in a host process; `client::HostProcess` runs one with
deadlines and says how it ended; `prototypes/vst3-scan` found 40 modules on
Windows in 10.4 s with four scan processes, in both module layouts, and
isolated a crash, a hang and a missing factory. The project model already
names a plugin by `Device::Vst3 { class_id }`. The browser panel is an empty
state.

**Design.**
- *The scan child.* A `scan` mode of the `lumen-plugin-host` binary loads one
  module and prints one bounded, versioned report (factory vendor, URL, every
  class with its category, sub-categories, version and SDK version). One
  process per module, so a failure costs one module. The parent owns the
  deadline and kills on expiry.
- *A new crate, `lumen-plugin-catalog`*, with no COM and no UI: `discover`
  (standard folders per platform plus the user's folders; both bundle and
  single-file layouts; symlinks followed with a loop guard and a depth limit),
  `scan` (a pool of child processes, a deadline per module, cancel, progress
  events, every outcome classified: scanned, failed with a message, crashed
  with the exit code, timed out, no binary for this platform, malformed
  report), `cache` (versioned JSON in the cache folder, keyed by path, size
  and modification time; written atomically; a damaged or newer-version cache
  is discarded and rebuilt, never fatal), `blocklist` (reason, when, and the
  file stamp at the time, so a changed file is retried on its own; Retry and
  unblock are explicit), `catalog` (merging cache, blocklist and built-in
  devices; kind from sub-categories; search, filters, vendor and category
  grouping; favorites and recents applied from settings).
- *The app.* `app/plugins.rs` owns a scan worker thread and a channel polled
  each frame (nothing blocks the UI); a startup scan reads the cache first, so
  known plugins appear at once, then checks only new or changed files and
  drops removed ones. The settings file gets a `plugins` section (custom
  folders, favorites, recents, scan at startup) as an added section with
  defaults, so no settings version change. The Devices tab of the browser
  shows the catalog in the chosen layout, with the designed empty,
  scanning, blocked and host-missing states.
- *Commands.* Rescan plugins, Rescan all plugins (ignore the cache), Add plugin
  folder…, Focus browser search (Ctrl+F), Toggle favorite; each in the palette
  with a tooltip and an accessible name.
- *Finding the host.* The scan child is `lumen-plugin-host` beside the Lumen
  executable. When it is missing, the browser says so and names the build
  command. Packaging resolves this in M10 (recorded in KNOWN_ISSUES).

**Not in this slice, and why.**
- Adding a plugin to a track (double-click, drag): slice 2.
- The `moduleinfo.json` fast path (ADR-0005): the measured cold scan of 40
  modules took 10.4 s in the background and the cache makes later starts
  instant, so the fast path is not needed for the pass condition. It also
  would list unverified metadata. Revisit if a cold scan is a complaint.
- Audition, tags beyond favorites, per-plugin scan history: later.
- Built-in effects: only the synth exists. The specimens show a built-in
  utility effect as a placeholder; it arrives with M8's built-in devices.

**Tests.** Unit tests of discovery (layouts, symlink loop, depth, a missing
folder), the cache (round trip, key change, damaged file, newer version,
atomic write), the blocklist (retry on change) and catalog queries. The scan
runs against `lumen-test-plugin` copies with faults chosen per spawn through
`LUMEN_TEST_PLUGIN_FAULT`: a good module, a crash, a hang past the deadline, a
missing factory, malformed metadata and cancel mid-scan. App E2E drives a
startup scan, a rescan after adding a module, a blocked module and its Retry,
favorites and recents surviving a restart, and search, all by accessible
names, with a test host folder rather than the machine's plugins. Windows:
the manual script MT-VST-1 scans the machine's installed plugins and records
counts, times and anything blocked in `docs/PLUGIN_COMPATIBILITY.md`.

**Pass condition (from the table above).** Cold scan, unchanged cached
startup, changed or missing binaries, crash or hang, malformed metadata and
cancel are tested; plugin work does not block the UI.

### Slice 2 plan: the first complete device workflow (branch `m6-s2-device-chain`)

Started 2026-10-16 from `main` after slices 0 and 1 merged. **The owner chose
D1 to D9 on 2026-10-16 (below; recorded in the owner-decisions table of
`docs/DECISIONS.md`). Nothing is built.** Per the owner's rule, the card and
placeholder specimens are rendered before the interface is built.

**What exists.** `Device { id, plugin: PluginRef, bypass, state }` is already
persisted per track (`PluginRef::Vst3 { class_id, name, vendor }` or
`Builtin`); the built-in synth is the first `Device` on a MIDI track and
`Track::instrument()` finds it (format v12). The engine's mixer node has a
`devices` list but its only device is the synthetic latent delay
(`mixer::spec::Device`), and the instrument runs through the separate
in-process `Instrument` trait in `lumen-devices`. The Devices tab of the detail
panel is a placeholder. The host (ADR-0066/0067) and the catalog (slice 1) are
built; ADR-0069 fixes the callback contract (event wake-up, one deadline of
three quarters of the period, one process per instance, silence after three
missed blocks).

**Design.**
- *One chain.* A track's `devices` is the whole chain, in signal order. The
  synth stays a device in it; a VST3 instrument is a device in the same list.
  The track's instrument is the first instrument device; MIDI To keeps its
  current meaning (a track plays its instrument or an output port, never both).
- *Engine side, behind a trait.* The engine may depend only on core, rt and
  `lumen-devices`, so the host path is reached through a small trait in
  `lumen-devices` ("a hosted processor": submit a block, wait against a shared
  deadline, report latency and tail, say whether it has ended) that the
  app-side hosting code implements over `lumen_plugin_host::shm::BlockLink`.
  No COM, process or file code enters the engine. The plan swap, delay lines
  and compensation (ADR-0041) take the latency a host reports. This is the
  ADR-0069 decision-2 path: submit to every host, run the engine's own work,
  then wait on each host's event against the one deadline.
- *App side.* A hosting manager (its own module tree, beside `plugins/`) starts
  one `lumen-plugin-host` process per VST3 device off the UI thread, attaches
  it through shared memory, and hands the engine the processor on a lock-free
  queue; retired processors go back to be freed off the audio thread. A device
  is `loading`, `ready`, `failed` (crashed, hung or refused) or `missing` (not
  in the catalog); the card shows which.
- *Model and format.* A persisted-change version bump (v16 to v17) with a
  migration and a frozen golden fixture. What it adds is for the owner's
  decision below; the migration must leave sound and routing identical. The
  `missing` and `failed` states are derived at run time, never saved.
- *Edits.* `Document::{add_device, remove_device, set_device_bypass}`, each one
  undo step with a label; adding an instrument over the synth is one step that
  keeps the replaced device's state in the history. Unsupported combinations
  (an instrument on an audio track, an effect before an instrument) are
  refused with a reason.
- *Interface (chosen 2026-10-16 from the "Lumen Device Chain Specimens"
  canvas: variant C with C2's kind treatment and C4's tray and cables).*
  Wide cards (200 pt wide, 284 pt tall with the artwork band): power (bypass),
  name and vendor, a kind badge, a strip of three chosen parameters (filled in
  slice 3; slice 2 draws the strip's frame), and a footer with the signal type
  and latency. The header and footer bands use the `header` colour. An
  instrument has a track-colour stripe on its header and a keyboard glyph and
  reads "MIDI → audio"; an effect has a sliders glyph and reads "audio →
  audio". A generated artwork band, 96 pt tall, tops the card (a monogram on a
  gradient in one of the 12 clip colours, chosen from the class ID so it never
  changes, plus the kind glyph) and fades into the header at its bottom; the
  picture goes greyscale and dim when the device is bypassed; a preference
  turns the band off. The chain sits in a sunk tray (`well`, with the lip) and
  the cards have the `border_strong` edge and a soft shadow, so they stand out
  of it. A cable joins each pair of devices, with a port at each card edge; the
  chain starts at a chip for the track's MIDI (a dotted cable into an
  instrument) and ends at one for the track's output. The cables follow the
  light levels: unlit when nothing sounds, a Beam (a 2 pt accent line, a 1 pt
  `core` inside, the halo and the faint cast) while audio plays through the
  chain; a bypassed, failed or missing device keeps its cables lit, because
  signal still passes. In the light theme the glow shrinks to ink. Loading,
  failed and missing cards swap the parameter strip for their message and
  button (Reload, Rescan plugins). The browser's double-click adds to the
  selected compatible track, and drag shows a line and a "+" at the drop point
  while neighbours stay put. Editor button, preset menu, reorder and copy
  arrive in slices 3 to 5.
- *Commands.* Add device to selected track, Remove device, Toggle device
  bypass; each in the palette with a tooltip and an accessible name.

**Owner choices (decided 2026-10-16).** All nine were taken as recommended,
except D5, where the owner asked for both the selected-card rule and drag.

### Slice 2b sub-plan: the engine's host path (draft, 2026-10-16)

**Goal.** The engine can play a hosted instrument and hosted effects to ADR-0069's
contract, tested with fake hosts. No process, no shared memory and no
interface yet: 2c connects the real links, 2d the cards. This is the risky part
of the slice, so it comes first and is measured before anything is built on it.

**What exists.** `Instrument::render(rate, events, left, right)` is
synchronous and adds into the buses; `MidiPlayer::run_track` gathers a track's
events and renders its instrument in one call. The mixer runs each node in
order (`Plan::process`): trim and polarity, devices (`lines.run(device.line)`,
today only a synthetic delay), mute, sends, fader, pan. `Mixer::render` calls
`tracks.render` first (clips, then MIDI, through `Layered`), then the plan.
`lumen_plugin_host::shm::BlockLink` offers `submit`, `poll` and `wait(deadline)`
and is allocation-free on Lumen's side. A callback's block may be rendered in
several parts (a loop wrap or a jump splits it).

**Design.**
1. **One contract in `lumen-devices`** (`hosted.rs`), so the engine stays
   below the host crate: `Hosted` has `submit(frames, input, events)` (never
   blocks; says whether the host took the block), `collect(deadline, out)`
   (waits at most until `deadline`; answers `Ready { latency, tail, restart }`,
   `Late` or `Gone`), `latency()`, `tail()` and `ended()`. The app's hosting
   code (2c) implements it over `BlockLink`; tests implement it with fakes.
2. **One deadline for the whole callback**, three quarters of the period from
   its start (ADR-0069), carried in `RenderContext::deadline`. The clock is
   read once per callback, and only when the source says a host is attached
   (`Source::hosted()`), so a project with no plugins costs what it did.
3. **Hosted instruments, in two phases.** `TrackSource` gets `begin(cx)`:
   `Layered` calls the MIDI player's `begin` before the clips render. `begin`
   gathers each track's events and submits the hosted instruments; `render`
   then collects them (after the clips have rendered, which is the work the
   hosts overlap with) and adds their output to the track buses. Built-in
   instruments keep their one-call `render`. A hosted instrument's `active()` is
   approximated from the last event and the reported tail, capped.
4. **Hosted effects, in the mixer.** A new `Device::Hosted { host, latency }`
   in the routing. The mixer owns a fixed-size pool of attached hosts, keyed by
   device id and filled by messages from the UI thread (`MixerHandle::attach`
   and `detach`; a retired host goes back to be freed off the audio thread). The
   plan refers to a host by id, so attaching or losing one never swaps a plan.
   Scheduling: before the node loop, each node that no other node feeds applies
   its input gain and **submits its first hosted device**; the loop then waits
   for that device where it reaches it. Independent tracks therefore run
   their effects concurrently. A second hosted device on one node, and a node
   fed by other nodes (a group), submit and wait in place: they serialise.
5. **Failure and fallback.** A host that misses the deadline contributes
   silence (an instrument) or the unprocessed input (an effect) for that block
   and is counted; about a second of late audio in a row (three blocks
   until 2026-10-17, ADR-0072), or an ended process, make it `failed`. A failed or absent effect takes the **delay line the plan keeps
   for its reported latency**, so timing never shifts (the owner's D1 and D7),
   with a 5 ms crossfade at each change. A failed instrument is silent. A
   bypassed device is not submitted and takes the same fallback. The plan
   builds that line for every hosted device, so the fallback needs no
   allocation.
6. **Latency news.** `collect` carries the host's latency. The mixer records a
   change per host id; `MixerHandle` lets the app read it, rebuild the routing
   and swap the plan, which ADR-0041 already does for latent devices.

**Tests (all deterministic, Linux and Windows).**
- Fake hosts that answer after a chosen time on a worker thread: with 64
  effects each taking *d*, the callback takes about *d*, not 64 × *d* (asserted
  with a wide margin, as a ratio, not a clock number).
- Events reach a hosted instrument at their exact frame; stop, jump, loop wrap
  and mute release notes (the host receives the note-offs).
- An effect's output is sample-exact against a fake that adds a constant; bypass
  is sample-exact pass-through at the reported latency, before and after a
  crossfade.
- A late, ended, refusing and recovering host: silence or fallback, the counts,
  no click beyond the 5 ms crossfade, and the other tracks untouched.
- A host that reports a new latency swaps the plan with the impulse arriving at
  the new delay (the existing compensation harness).
- All of it inside `rt_section` under the allocation guard, and added to the
  `rtsan` CI job. The existing performance scenarios stay within the +2% gate;
  a new scenario times 64 fake hosts.

**Not in 2b.** Processes, shared memory, restarts and the real `BlockLink`
adapter (2c); the cards and the browser attach (2d); failed and missing
states in the interface (2e); effect tails after a stop (the engine renders
nothing while stopped, so a reverb tail is cut at Stop; recorded in
KNOWN_ISSUES, built with real tails in slice 6); sidechain inputs and extra
outputs (slice 6).

**Choices (the owner took B1, B2 and B3 as recommended, 2026-10-16;
the "Recommendation" column is what was chosen).**
| # | Choice | Recommendation | Alternative |
|---|---|---|---|
| B1 | Chains of two or more hosted effects on one track, and effects on a group, **serialise** in 2b | Accept it and measure in 2f: it affects only those cases, and 64 tracks with one effect each still overlap | Build a general dependency scheduler now: more engine change before any real plugin has run |
| B2 | An effect's **tail is cut at Stop** until slice 6 | Accept it and record it | Keep the mixer running while stopped for hosted tails: touches the stopped path every project uses |

### Slice 2c sub-plan: the hosting manager (approved, 2026-10-16)

**Goal.** A project device that names a VST3 class runs in its own
`lumen-plugin-host` process, loaded in the background, and is heard through
2b's engine path: an instrument on a MIDI track and an effect on any track.
Failures, a host that ended and a plugin that reports a new latency reach the
engine and the app through the `Guard`s 2b built. There is still no card and no
browser attach (2d): 2c is driven by `Document::add_device` from tests, and it
is the first time a real process is on the audio path, so it is where ADR-0069's
numbers meet the app.

**What exists.** `HostProcess` (spawn, `load`, `configure`, `attach`, `state`,
`set_state`, `quit`, `has_ended`) and `BlockLink` (`submit`, `poll`, `wait`,
`copy_output`) in `lumen-plugin-host`; `Hosted`, `Guard`, `HostedInstrument` in
`lumen-devices`; `MixerHandle::{attach_host, detach_host}`; the catalog, which
finds a class ID's module (`lumen-plugin-catalog`); the scan worker as the model
for a background thread polled each frame. **Nothing in the app creates a
`Guard` yet**, and `PluginRef::Vst3` holds a class ID, not a path.

**Design.**
1. **A new crate, `lumen-hosting`** (depends on `lumen-plugin-host`,
   `lumen-devices` and `lumen-core`; no UI types), so the engine stays below the
   host crate and the manager is tested against `lumen-test-plugin` in real child
   processes without the interface. It holds:
   - `Link`, the `Hosted` adapter over `BlockLink`. `submit` copies the input,
     turns Lumen's MIDI messages into the host's events, and calls
     `BlockLink::submit`; `Busy` or a block that does not fit is `Refused::Busy`
     (a miss). `collect` calls `BlockLink::wait(deadline)`: a `Done` answer is
     copied out (a mono output to both sides, non-finite samples already silenced
     by `copy_output`) and becomes `Reply::Ready` with the answer's latency and
     restart flag and the tail read at configure; a failed, stale or invalid
     answer, or no answer, is `Reply::Late`. `ended()` reads an atomic.
   - `Process`, one **control thread per host** that owns its `HostProcess`:
     it runs the load sequence, answers state and quit requests with deadlines,
     and between requests looks at `has_ended` every 10 ms and sets the atomic
     `Link::ended` reads, so the callback never makes a system call to ask. A
     blocked write or a hung plugin blocks only that thread.
   - `Manager`, the set of devices by id. `want(device, class, path, state, kind)`
     starts a load; `drop(device)` ends the process; `reload(device)` starts a
     new one. Up to four loads at a time (as the scanner does), each step with a
     deadline: spawn and `Load` 20 s, `SetState` 10 s, `Configure` 5 s, `Attach`
     2 s. `poll()` hands back what finished: `Ready { link, latency, tail, name }`
     or `Failed { reason }`, in words that say what to do.
2. **The load sequence** is `Load(path, class)`, then `SetState` when the device
   has saved state, then `Configure` (sample rate; the largest block the protocol
   allows, 8,192 frames, so no device buffer can outgrow it; 2 outputs, and 2
   inputs for an effect, none for an instrument), then `Attach` with
   `Wake::EVENT` on both sides, the setting ADR-0069's runs support (inside the
   budget to 100 µs of plugin work per track; the spin variants missed at 200 µs).
   The setting is one constant, re-measured in MT-VST-2. A plugin that refuses
   the 2-channel layout fails with that reason (other layouts are slice 6).
3. **The app's bridge, `hosting.rs` in `lumen-app`**, derives from the project
   which devices want a host (a plugin device whose class the catalog finds,
   not blocked), asks the manager, and on `poll`:
   - an **effect** becomes `Guard::new(link, latency)`, sent with
     `mixer.attach_host(device_id, guard)`; the routing always names the device
     (`Device::Hosted { host: device_id, latency }`) so a loading, failed or
     missing effect plays the 2b fallback line at its last known latency (D1,
     D7) and the attach changes nothing in the plan;
   - an **instrument** is `HostedInstrument::new(guard)` in the track list built
     after the attach, and a placeholder in every other list (2b);
   - **bypass** is `Status::set_bypass`, fed from `set_device_bypass`; it never
     touches the routing;
   - **latency news** (`Status::take_news`) rebuilds the routing with the new
     latency (ADR-0070); a **restart request** reconfigures that host (a new
     generation) off the audio thread;
   - **failed** (`Status::failed`) makes the device's state `failed` with a
     reason for 2e's card; nothing restarts by itself (D8). `reload` starts a new
     process and attaches a new guard in place of the failed one.
4. **A new engine means new links.** A changed device, rate or buffer rebuilds
   the engine and with it the mixer's host pool and the player's instruments, so
   the bridge keeps each host's process and makes a fresh `Link` (a second
   `Attach`, which the host already supports) for the new engine, after
   `Configure` at the new rate. The processes outlive the engine; they end with
   the device, the project, or Lumen (the job object on Windows and the
   parent-death signal on Linux already do the last).
5. **Closing the skip hazard in 2b.** The player keeps only the newest of the
   track lists waiting for it and frees the others. A skipped list that carried
   a real hosted instrument would free the only handle to a running host. The
   fix is in the engine: when a list is skipped, a hosted instrument in it moves
   into the newer list's placeholder for the same track (the same swap `carry`
   already makes for a kept list). A test sends two lists in one block with the
   real instrument in the first.
6. **Events.** 2c carries what the host protocol can carry today: note-on and
   note-off, with their velocity and channel (choice C1). Everything else the
   engine sends is dropped at the adapter and counted in `Status`.
7. **Where the saved latency and tail come from** (choice C2): the host reports
   them at load and with each answer; D9 saves the last known values so a project
   opened again plays at the right delay before the plugin has loaded.

**Tests.**
- `lumen-hosting` against `lumen-test-plugin` in real host processes (Windows
  and Linux): load an instrument and an effect and render blocks through `Link`,
  sample for sample against the plugin's known output; state sent at load comes
  back; the load sequence fails with a reason for a missing file, a class that is
  not there, a plugin that crashes or hangs at load, at configure and in a
  block; a host killed mid-session sets `ended` within the next check and the
  guard fails it; a hung host misses three deadlines in a row and fails; four
  loads at once; `drop` and `reload` leave no process behind (counted); events
  other than notes are dropped and counted; a block longer than the region is a
  refusal, not a crash.
- The adapter under the allocation guard (`submit`, `collect`, `ended`) and added
  to the `rtsan` job.
- App: with the test plugin, `Document::add_device` for an instrument on a MIDI
  track and an effect on an audio track, then play through the real engine on the
  test device and compare with the plugin's output; bypass; remove (the process
  ends); undo (a new process); save and reopen (loads in the background, plays
  from the fallback until ready, latency news swaps without a step); a device,
  rate or buffer change keeps every device playing; a crashing plugin falls back
  or goes silent as D1 and D2 say, and Reload brings it back; a plugin missing
  from the catalog stays `missing` with its state intact through a save.
- The existing performance scenarios stay within the gate (the adapter is not in
  the engine's crate); a loopback timing run of the adapter, 64 hosts, joins

**Not in 2c.** Cards, the browser's attach and the commands (2d); the failed and
missing cards (2e); the editor, parameters and generic controls (slices 3 and 4);
capturing state from a running plugin and checkpoints (slice 5; nothing can

(slice 6).

**Choices (the owner took C1, C2 and C3 as recommended, 2026-10-16; the

| # | Choice | Recommendation | Alternative |
|---|---|---|---|
| C1 | **MIDI other than notes** (controllers, pitch bend, pressure, program) for a plugin instrument | Notes only in 2c; the rest is dropped and counted. The host protocol has no way to carry it yet, and it belongs with parameters (slice 3), where the host maps it through the plugin's own controller mapping. **Owner choices (2026-10-17).**

| # | Choice | Decision |

The editor button and the strip arrive in slice 4, the preset menu in slice 5; the slice table's rows 3 to 5 say so |
| E2 | Copying a device to another track | **Alt-drag** a card onto another track's header or tray copies it; a plain drag reorders or moves; the same is in the card's menu ("Copy to track") and on Ctrl+C and Ctrl+V for the chosen card |

**Goal.** A producer can shape a chain without leaving the Devices tab:
fold a card, drag it to a new place in its chain or onto another track, copy
it, and see the plugin's own picture on the card. Every gesture is one undo
step, a refused one says why, and nothing audible jumps while the song plays.

**What is built.**
1. *Model edits* (`document/devices.rs`): `move_device(track, device, to_track,
   slot)` and `copy_device(track, device, to_track, slot)`, one undo step each.
   A copy gets a new device id and the source's saved state (until slice 4 the
   project's saved state is what the host runs, so the copy is faithful; slice
   4 must capture live state before a copy). Refusals: an effect before the
   instrument, an instrument onto a track that is not MIDI, a missing track or
   device, the master where it takes no device. A moved or copied instrument
   replaces the one on the target (D4), as one step.
2. *The master and the other chain owners.* Today an edit to the master is
   refused ("takes devices in a later update"). Check first whether the
   master and the mixer's node for it can carry `Device::Hosted` as tracks
   do; if they can, the Devices tab shows the master's chain and the refusal
   goes; if the engine needs more, that is split off and the master keeps its
   refusal with an honest message. Group and return chains already follow the
   track rules.
3. *Reorder and move in the tray.* Dragging a card shows the same gap line and
   plus the browser drag shows (`chain/view.rs` drop mark), over its own tray
   and over other tracks' headers; the arrow keys move between cards
   (KNOWN_ISSUES, 2d), and Alt+Left and Alt+Right move the chosen card one
   place. Commands `devices.move_left`, `devices.move_right`,
   `devices.copy`, `devices.paste`, `devices.duplicate` (at the end of
   `Command` and `ALL`).
4. *Collapse.* A card folds to a narrow rail (name, power button, state) and
   opens again; the chain's folded cards are a view setting, kept per
   device in the project's saved view, not an edit (no undo step, no format
   bump if the view section can carry it; if not, v18).
5. *Engine and hosting.* A reorder or move is a routing change: the hosts keep
   their processes (keyed by device id), the plan swap lines the paths up
   (ADR-0041), and a device moved to another track keeps its host. A copy
   starts a new host from the saved state. Playing edits must not hang
   notes or step the sound: tests below.
6. *Plugin snapshot pictures* (the plan's own part). The scan child returns
   bounded PNG bytes from the bundle's `Contents/Resources/Snapshots/`
   (scan-report version bump, size limits on both sides); the app decodes off
   the UI thread, caches thumbnails by file stamp, and the card's artwork band
   shows the picture in place of the generated monogram; a module with none
   keeps the monogram.
7. *Cleanups from KNOWN_ISSUES (2d):* the footer reading "0.0 ms" for a
   built-in synth; a track in a folded group still shows its chain when
   selected. The empty parameter strip's frame goes with E1 (the card frees
   the room until slice 4 puts the strip back).

**Not in this slice.** Parameter strip contents, parameter controls, the
editor button and non-note MIDI for plugin instruments (they ride with
parameters in slice 4; KNOWN_ISSUES entry updated), the preset menu (slice 5),
latency and tails of real plugins (slice 6).

**Tests.**
- Project/document: move and copy within a track, across tracks, onto the
  master, instrument rules, ids unique after a copy, state copied byte for
  byte, one undo and redo restore the exact previous chains, refusals.
- Engine/hosting: a reorder under playback keeps hosts and gives no step
  (sample compare against the same chain built in the new order); a move
  between tracks keeps the process; a copy starts a distinct process; an
  instrument replaced during a held note releases it; allocation guard and
  RealtimeSanitizer over the new plan swaps.
- E2E by accessible names: drag-reorder, Alt-drag copy to another track,
  keyboard move and copy, collapse and expand, a refused drop and its message,
  undo and redo of each, save and reopen with a copy and a folded card.
- Scan: snapshot bytes bounded and versioned, a corrupt or oversized picture
  ignored, none present; the card's two faces; cards in both themes at 100,
  150 and 200%.
- Gates as slice 2: workspace clippy and tests, macOS cross-clippy, WSL
  performance gate (a project edit and routing path change), E2E and smoke.
- **MT-VST-3 (Windows, owner):** rearrange a chain of real plugins while the
  song plays, copy a device to another track and compare the sound, fold and
  reopen, look at the pictures.

**Parts (commits on this branch).** 3a model edits and tests; 3b engine and
hosting under playback (where the risk is); 3c interface (drag, keyboard,
collapse, commands); 3d master chain if the engine allows it; 3e snapshot
pictures; 3f walkthrough, MT-VST-3 and the report.

### Slice 4 plan: parameters and native editors (branch `m6-s4-parameters-editors`, draft 2026-10-17)

Cut from `main` (slices 0 to 3 and the fixes after them are merged).

**Starting point (read from the code, 2026-10-17).**
- The host lists a plugin's parameters (id, title, units, step count, default),
  capped, with no current value, no text, no flags and no groups.
- Blocks already carry parameter queues with sample offsets through the shared
  region (`ParamQueue`), but Lumen's `Link` sends notes only: controllers, bend,
  pressure and program change are dropped and counted (KNOWN_ISSUES, 2c).
- The host's component handler collects `performEdit`, but nothing reads the
  list, `beginEdit` and `endEdit` are dropped, and the processor never hears an
  edit made in the plugin's own window.
- Editors exist only in the Windows spike (`lumen-editor-spike`); the
  production host opens none. ADR-0067 "Editors" fixed the window policy
  (unowned top-level windows, on top only while Lumen or an editor is in front,
  no shortcuts forwarded, a hung editor flagged for the user to end).
- Undo is whole-project snapshots (ADR-0024), so an edit that is not in the
  project model cannot be undone. The test plugin has two parameters and an
  editor behind a switch.

**Owner choices to make (recommendation first).**

| # | Choice | Options |
|---|---|---|
| P1 | What a parameter edit is, for undo and saving | **A (recommended): the project holds the values.** A device keeps a small overlay of the parameter values set since its state was captured (`Device.params`, format v19); a gesture, from Lumen's controls or from the plugin's own window, is one undo step on that overlay (begin to end, merged); the bridge pushes the model's values to the host on undo and redo. M7's automation and MIDI learn write the same overlay. Changes made inside a plugin that are not parameters (loading a patch, a sample) are not undoable; they mark the device dirty and its state is captured at save (stale state is disclosed, never hidden). **B: a snapshot of the plugin's state per gesture.** Everything undoable, but each step stores the whole state (megabytes for a sampler) and restoring one resets the plugin's voices. **C: not undoable**, dirty only: simplest, and breaks "everything is undoable" |
| P2 | How the card's parameter strip is chosen | **A (recommended): click a slot, pick from a searchable list**, and a Learn button: touch a control in the plugin's window and it takes the next free slot. **B:** the list only. **C:** Learn only. Eight slots, two rows of four, the value shown in the plugin's own text ("2.4 kHz") |
| P3 | Where the full parameter list lives | **A (recommended): a panel opened from the card** ("All parameters"), searchable, grouped by the plugin's own units, rows drawn only when in view, so hundreds stay quick. **B:** a tab in the detail panel next to Devices. **C:** a floating window |
| P4 | Where an editor's place and size are remembered | **A (recommended): per plugin, in the app's settings** (it opens where it was last, whatever the project). **B:** per device in the project, so a project reopens its windows. No format change for A; B would be in v19 |

**Owner's answers (2026-10-17): P1 A, P2 A, P3 A, P4 A**, all as recommended.
The project holds the values (format v19); the strip is chosen from a list or
by Learn; the full list is a panel opened from the card; an editor's place and
size are remembered per plugin in the app's settings.

Decided without asking (they follow earlier decisions or the plugin standard):
editors open from the card and never on adding a device (section 4 proposals);
the window policy is ADR-0067's; non-note MIDI goes to a plugin through its own
controller mapping (`IMidiMapping`: CC, bend, pressure and program change become
parameter points at the event's sample offset) with the legacy event as the
fallback and a count of what neither takes; a plugin with no editor keeps the
generic controls; a hung editor is flagged and the user ends the plugin.

**What is built (parts, as commits on this branch).**
- *4a Host: parameters, values, text, edits.* The list gains flags (hidden,
  read-only, program, can-automate), unit names, current value and the plugin's
  text for a value (`getParamStringByValue`); long lists come in pages (up to
  4,096 parameters, 256 a page); `SetParam` reaches the controller and the
  processor; the handler keeps `beginEdit`/`performEdit`/`endEdit` in order
  (bounded, coalesced within a block), applies each edit to the processor's
  next input queue (the host's duty, missing today), and the host reports them
  to Lumen; output parameter changes from the processor are collected.
- *4b Non-note MIDI for plugin instruments.* `EventKind` gains controller, bend,
  pressure and program change; the host maps them through `IMidiMapping`.
- *4c The link and the engine.* Parameter points from a fixed-size
  single-producer queue (Lumen's controls, editor edits, later automation) ride
  the next block with sample offsets; nothing allocates or locks on the
  callback (allocation guard and RealtimeSanitizer cover it).
- *4d The model.* Per P1: `Device.params`, `Device.shown` (the strip's
  choice, a view like folded cards, no undo step), `Document::set_device_param`
  (gesture-merged), format v19 with an identity migration and a frozen golden.
  The bridge reconciles the overlay with the host both ways.
- *4e The interface.* The card's strip (compact sliders with the plugin's text,
  double-click resets to default, wheel and fine adjust as every control),
  P3's panel, the editor button with its states (closed, open, not responding),
  commands `devices.editor`, `devices.parameters`, `devices.learn` at the end of
  `Command` and `ALL`; accessible names ("Cutoff, parameter of Pad, 40 percent").
  Specimens of the strip and the panel first (the visual options after P2 and
  P3 are answered).
- *4f The editor.* The spike's window code moves into the host proper
  (Windows): requests to open and close with a scale and a place, answers for
  opened, resized, closed and not responding; the window pump runs on the host's
  main thread and the control loop answers from a reader thread with a deadline,
  as the spike did. Closed when the device is removed, fails or moves to
  another track. macOS and Linux show "editor not available here" and keep the
  generic controls.
- *4g Dirty state and save.* A parameter gesture or a plugin-side change marks
  the device dirty; a save asks each dirty host for its state with a two-second
  deadline and stamps it (as latency is stamped); on failure the previous state
  is saved and the card says so. Background checkpoints and damaged-preset
  handling stay in slice 5.
- *4h The test plugin and tests.* The test plugin gains `many_params=N`, flags
  and units, a controller mapping, a program parameter and an editor whose
  controls call `beginEdit`/`performEdit`/`endEdit`.

**Not in this slice.** The preset menu and preset files (slice 5), checkpoints
and safe mode (5), buses, multi-out, sidechain and dynamic latency (6),
automation lanes, MIDI learn and the parameter right-click menu's automation
entries (M7), macOS and Linux editors.

**Tests.**
- Host: parameter list pages, flags and text against the test plugin; an edit
  from the plugin's window reaches the processor in the next block at the right
  offset; a hostile list (huge count, bad strings, duplicate ids) is bounded.
- Engine and link: points at sample offsets land on the right sample (golden
  render, block-size invariance); mapped and unmapped controllers; queue full
  counted, not blocked; allocation guard and RealtimeSanitizer.
- Project and document: the overlay, gesture merge to one undo step, undo and
  redo restore exact values, v18 to v19 identity migration, frozen golden.
- E2E by accessible names: strip choice and Learn, a slider drag is one undo
  step and is heard, undo and redo are heard, reset to default, 1,000 parameters
  scroll with frame times recorded, search, the editor button's states with the
  test plugin's editor, a hung editor flagged and ended, save during an edit
  keeps the value, a save with a stalled host discloses stale state, cards in
  both themes at 100, 150 and 200%.
- Gates as slice 3, plus the WSL performance gate (the engine path changes).
- **MT-VST-4 (Windows, owner):** open each real plugin's editor, type into it,
  confirm no Lumen shortcut fires; move a control in the editor and in Lumen and
  hear both; undo and redo them; save and reopen; one plugin with hundreds of
  parameters; a second monitor of another scale.

### Slice 5 plan: presets and resilient state (branch `m6-s5-presets-state`, draft 2026-10-17)

Cut from `main` after PR #33 merged slice 4. MT-VST-4 results are the owner's
and are not assumed here.

**Starting point (read from the code, 2026-10-17).**
- A device holds the component state, the controller state (v17), the plugin's
  version, the last reported latency and tail, and the parameter overlay (v19).
  The host reads and sets state with a deadline (`HostProcess::state`,
  `set_state`); a save reads every running plugin first (ADR "A save reads every
  running plugin"). The edit controller's own state is not read yet.
- The host reads the plugin's unit groups (`IUnitInfo`) for parameters only. It
  does not list program lists, load a program, or read or write preset files.
- A failed or hung host shows a card with a manual Reload; there is no record of
  how often a plugin has failed, and no checkpoint between saves other than
  autosave.
- There is no safe mode anywhere in the code. A project that names a missing
  plugin keeps its state and shows the missing card (slice 2).
- Program change and key pressure are not sent to plugin instruments
  (KNOWN_ISSUES, slice 4).

**Owner choices to make (recommendation first).**

| # | Choice | Options |
|---|---|---|
| R1 | What the card's preset menu lists | **A (recommended): both sources in one menu.** The plugin's own program list (its factory patches, by the standard's program-list interface) and preset files found in the standard user and system folders for that plugin, searchable, with Save as… writing a preset file into the user folder. **B:** the plugin's program list only (no files). **C:** files only |
| R2 | What loading a preset is, for undo | **A (recommended): one undo step that replaces the device's saved state.** Undo restores the state held before, so the project snapshot already carries it (ADR-0024); the parameter overlay is cleared by a load and returns on undo. **B:** not undoable, with a confirmation first (breaks "nothing blocks" and "everything is undoable") |
| R3 | Checkpoints | **A (recommended): a background checkpoint of each changed plugin's state about every 30 seconds while it rests**, written beside the autosave and kept as the device's last-good state, so a crash or hang reloads from it and a project recovered after a crash has them. **B:** only at save and autosave (up to a few minutes stale) |
| R4 | Restart after a crash or hang | **A (recommended): never automatic.** The card names the failure and keeps Reload; a plugin that has failed three times in two minutes says so and Reload asks it to start from the last-good state (a second button, "Reload without state", starts it clean and leaves the saved state in the project until you save). **B:** one automatic restart, then manual |
| R5 | How safe mode starts and what it does | **A (recommended): three ways in** (a `--safe-mode` flag, holding Shift while starting, and a banner offer after a start that did not finish loading plugins last time). In safe mode no plugin binary is scanned, loaded or hosted; every plugin card shows "Safe mode, not loaded" with its state kept and saved unchanged; "Leave safe mode" loads them on the spot. **B:** the flag and Shift only, no automatic offer |

## 4. Behavior proposals for discussion

These are recommendations, not recorded owner decisions. Visual variants
for the chain and browser will be rendered before their implementation.

| Choice | Recommendation | Alternative / consequence |
|---|---|---|
| Process boundary | Start by measuring one process per instance: a failure affects one device. Select it only if the workload meets the budget. | One process per chain reduces IPC but a failure affects every device in that chain. Per-vendor grouping also couples unrelated tracks. |
| Crash/hang fallback | Silence a failed instrument; bypass a failed effect with compensation preserved and a short transition. Show the failure on its card with explicit Reload. Measure loudness/transition behavior before deciding. | Silence the affected chain: simpler and avoids a sudden dry signal, but takes that track away. Never feed stale blocks. |
| Adding a device | Browser double-click adds to the selected compatible track; drag shows an insertion preview. Replacing an instrument is one explicit undoable operation. | Always create a track: predictable but slower when building an existing chain. |
| Opening editors | Keep the arrangement in view; open a native editor from the card, with generic controls always available. | Automatically open on insertion: faster to reach the plugin, but can cover the arrangement. |
| Bypass | Preserve plugin/chain latency while bypassed to avoid a timing jump; distinguish power-off if later needed. | Remove latency on bypass: lower delay, but requires graph rebuilding and changes phase relationships. |

Parameter edits from the generic UI should be undoable as one gesture.
Slice 0/4 must determine how native-editor gestures and opaque state-only
changes can meet the same promise; unsupported notification behavior is
reported per plugin, not described as universal undo support.

  retain the recorded VST/ASIO trademark and distribution checks. This

  streaming/export remain M9. CLAP, racks and non-Windows hosting stay out.
