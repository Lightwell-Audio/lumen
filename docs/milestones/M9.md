# Milestone 9 — Recording, Media, Export & Production Workflow: plan

**Status:** Choices made 2026-10-24: the owner took every recommendation (§4).
Slice R0 starts next; nothing else is built.
Delivery order was set by the owner on 2026-10-23: M9 comes before M8 because
audio recording matters more than drum maps. The milestone number and scope
(ROADMAP §9) are unchanged.

**How this plan was made.** The roadmap, the M7b audit, KNOWN_ISSUES and a
direct read of the device layer, the engine's render path and the project
model. Nothing was built or run; each slice re-reads its own area before it
starts. Choices the code settles are in §3. Only preference calls go to the
owner (§4).

**Goal (ROADMAP §9, CLAUDE.md §6.2, §6.9, §6.10).** Lumen is practical for a
whole song: audio comes in and is recorded safely, a large session plays from
disk, a project is managed (copy, template, revert, collect, relink, purge),
and the result is exported.

**Exit criterion (ROADMAP).** A complete song can be created, recorded, saved,
recovered, reopened and exported without manual intervention outside Lumen.

Requirements covered: CLAUDE.md §6.2 (recording, import), §6.9 (device
selector: input), §6.10 (projects, media, export), and the matching rows of §7
(Recording, Browser and media, Project management, Export, Preferences,
System).

## 1. What the code gives us

| Area | Fact (pointer) | Consequence |
|---|---|---|
| Input reaches the callback, then stops | `Block.inputs` is filled by the ASIO backend (`asio/mod.rs`); the WASAPI and cpal backends pass `&[]` and WASAPI refuses a configuration that asks for input (`wasapi.rs:231`). The engine never reads `Block.inputs`. | R1 builds the whole input path in the engine; WASAPI and cpal input are new. ASIO is the proven path and the owner's hardware. |
| Model | `Track.armed`, `Track.monitor` (`In`/`Auto`/`Off`, v13) exist and are saved. There is no input routing on a track, no recorded-take data, no input offset. | One format bump for input routing; recording itself adds clips and media, which the format already has. |
| WAV writer | `lumen_media::wav::Writer` (`create`, `write`, `finish`) writes 32-bit float WAV atomically. | The recording writer builds on it; it needs a header that stays valid if the process dies, and a size beyond 4 GiB. |
| Disk work | No streaming reader, no read-ahead thread, no peak cache. Clips are decoded to memory at load; peaks are built at load (ADR-0019, ADR-0027). | Streaming and the peak cache are new machinery, which the recording writer shares in part (the disk thread and its queues). |
| Offline render | `lumen_engine::render_source` drives a `Source` (the mixer with tracks, devices and plugin hosts) without a device and gives the sink the left and right slices; it follows delay compensation, adds a tail until the signal is below `QUIET_LEVEL`, and reports cancel and host failure (M7b E4, ADR-0096/0097). Bounce, freeze and consolidate already use it. | Export is `render_source` of the whole project plus a file writer, sample-rate conversion, dither and normalize. The hard part (offline plugins) is settled. |
| Loudness | `lumen_core::loudness` gives gated LUFS and 4× true peak (BS.1770-4, ADR-0040). | The post-export loudness report needs no new DSP. |
| Codecs | `symphonia` decodes WAV, AIFF, FLAC, MP3, Ogg. Nothing encodes FLAC. | A FLAC encoder is a new dependency and a licensing check (§4, X2). |
| Media paths | `Media.path` is relative, `/`-separated; save copies imported audio into the project; unreferenced media can sit in `Project.media`; rendered files live in `Renders` and are copied to `Samples/Rendered` on Save. | Collect and save, relink and the media pool extend what Save already does. Purge handles the render leftovers in KNOWN_ISSUES. |
| Preferences today | Theme, interface size, Reduce motion and copy-imported-audio live in the app menu; audio and MIDI settings have their own windows; autosave, recovery, recent projects and backups are done (M3 slice 3). | The Preferences window gathers them; no setting is lost. |
| Open items before recording | The audit's M2 and M3 (`is_current` of consolidate checks only selected clips; normalize applies peaks by clip id without checking the window) are rated "before recording work". KNOWN_ISSUES also lists: edits to a track being recorded are lost at the next commit (M5 slice 6). | Slice R0 fixes them first; recording starts on a sound base. |

## 2. Scope and shape

Nine slices (§5). The owner's priority is audio recording, so the order is
**input → record → project → export → streaming → workflow → icons**, with the
render-consistency fixes first. Everything is a vertical slice with a manual
test.

Deliberately **not** in M9, by the roadmap and CLAUDE.md §8: MP3 and AAC
export (L), comping lanes (S, later), warp (S), MIDI clock in. Capture MIDI
and loop-recording takes are [S] and are pitched in §4 (R3).

## 3. Decisions the evidence settles

Each becomes an ADR when its slice starts. The owner may overrule any.

| # | Decision | Why |
|---|---|---|
| D1 | **Recorded files are 32-bit float WAV at the device rate, one file per take, one channel per armed input** (stereo inputs become one stereo file). | Float cannot clip in the file; the device rate avoids converting on the audio path; the existing writer already does it. A project converts on import like any file. |
| D2 | **The audio thread only copies input into a ring; a disk thread writes.** The capture ring is sized for several seconds, an overrun is counted and shown, never blocked on. | Hard rule 1. The same thread, queues and file-ownership rules carry the read-ahead for streaming (R6). |
| D3 | **Crash-safe means the file is valid at every moment.** The header is rewritten about once a second and on stop; a recovery pass on open finds unfinished takes in the project's `Recordings` folder, repairs their header from the file's length, and offers them as clips. | A crash costs at most the last second of audio. Uses RF64 beyond 4 GiB. |
| D4 | **Drift between separate input and output devices is corrected with rubato's `Slip`** (ADR already recorded 2026-10-06). ASIO is one device with one clock and needs none. | Owner decision of 2026-10-06. |
| D5 | **Export is `render_source` of the project through a sink** that converts, dithers and writes. Real-time export is a second sink that plays through the live engine and records its own master (needed when an offline render of a plugin is not trusted). Both produce the same file for a project with no plugin that is real-time-only. | The offline renderer exists and is proven by bounce and freeze. Offline equals real time is a quality-bar item and gets a golden test. |
| D6 | **Project sample rate** is stored in the project (a new field, format bump). Export, bounce and consolidate render at it; playback still converts to the device rate. | Closes the KNOWN_ISSUES note that a consolidated file is at the device's rate. |
| D7 | **No modal dialogs.** Export and the Preferences window are ordinary windows; progress and cancel live in the task area. Revert and "Save as template" are named commands in the palette. | CLAUDE.md §2. |
| D8 | **The macOS and Linux input backends are compile-only** until hardware exists (owner decision 2026-10-06). WASAPI input is built and tested on the owner's Windows machine. | Cannot verify elsewhere in the cloud container. |

## 4. Choices for the owner

For each: the options, what the user would hear or see, and a recommendation.
Answer by label (for example "R1 A, R3 B, X2 A").

### R1 — Where an audio track gets its input
- **A (recommended).** An **In chip on the track header** (next to the arm
  button) opens a popover listing the device's input pairs and mono inputs by
  their friendly names ("Input 1", "Inputs 1+2"); the mixer strip shows the
  same control. Arming an unrouted track picks the first free input.
- **B.** Only in the mixer strip. Quieter headers, but an extra step to record.

### R2 — Monitoring while recording
- **A (recommended).** Default **Auto**, as the model already stores it: you
  hear the input while a track is armed and the transport is stopped or
  recording; on playback without record you hear the clips. Effects on the
  track are in the monitoring path; the latency is the device's, shown in the
  status popover, with no extra buffering.
- **B.** Default **In** (always hear the input on an armed track). Simpler,
  but double-sounding when you play back over a take you are replacing.

### R3 — Loop recording and Capture MIDI (both [S] items)
- **A (recommended).** Loop passes are cut into clips; the **last pass plays**
  and earlier passes are kept in the file and reached from a **Takes** menu on
  the clip (swap, or "extract to a new track"). No new overlap in the model.
  Capture MIDI is built with it: with any MIDI track listening, the last few
  minutes of played notes can be turned into a clip with one command.
- **B.** Both deferred to a later milestone (with comping), and a loop
  records as one long clip.
- **C.** Full take lanes with comping in M9. Larger than the milestone; would
  need the overlap rule changed.

### R4 — Latency offset
- **A (recommended).** The take is moved earlier by the driver's reported
  input plus output latency automatically; a **manual offset in ms** (global,
  in Preferences › Audio) corrects drivers that misreport; a **loopback
  helper** in the audio panel measures the round trip with a cable from an
  output to an input and offers the number.
- **B.** The offset is **per track** as well as global. More control, more UI;
  the model has a "track delay offset" [S] row it could share.

### R5 — Disk streaming: when
- **A (recommended).** **After recording and export (slice R6)**, as an
  opt-in per-session mode until a soak at 64 and 128 frames passes, then the
  default. Memory stays the default meanwhile. Reason: streaming is the
  riskiest real-time change; the owner's priority is recording.
- **B.** Together with the recording slices (the owner's 2026-10-06 wording
  "built together"). Fewer rewrites of the disk thread, but the first
  recording build arrives later and carries both risks.

### X1 — The Export window
- **A (recommended).** A **floating window** (Ctrl/Cmd+Shift+E, palette):
  scope (project, loop, selection), master or stems (per track, group,
  return), format, bit depth, rate, dither, normalize, tails, offline or
  real-time. A live loudness read-out after the export.
- **B.** A **tab in the detail panel**, always on screen with the mixer.

### X2 — FLAC
- **A (recommended).** A pure-Rust encoder (candidate: `flacenc`, Apache-2.0),
  checked for licence and quality when R5 starts.
- **B.** The reference library through a binding (BSD, but a C build on every
  platform and installer).
- **C.** WAV only in M9; FLAC with M10.

### X3 — Tap tempo and project settings
- **A (recommended).** Tap tempo is a **button beside the tempo field and a
  key**: it averages the last four taps and resets after two seconds of
  silence. **Project settings** (rate, tempo, meter, notes, default track
  colours) is a window opened from the app menu and the palette.
- **B.** Tap tempo inside the tempo popover only.


### Owner's choices (2026-10-24)

R1 A (In chip on the header), R2 A (Auto monitoring), R3 A (Takes menu and
Capture MIDI), R4 A (global offset and loopback helper), R5 A (streaming after

### I1 — App and file icons

## 6. Gates

- Before each commit: `cargo fmt --all`, workspace clippy with `-D warnings`,
  `cargo test --workspace`. Before pushing: macOS cross-clippy; WSL mirror and
  the performance gate for engine and project changes (+2% fails).
- Real-time paths (the capture copy, the monitor path, the disk reader's
  hand-off) run under the allocation guard and RealtimeSanitizer in CI.
- End of every slice (ADR-0029): the E2E suite and the smoke tests pass; each
  slice adds E2E scenarios by names and keys. Recording scenarios use the fake
  backend with a scripted input.
- Format: each new persisted field bumps the version with a migration and a
  frozen golden (D6 and R1 each bump).
- Honest testing: ASIO and WASAPI input, round-trip latency, drift and
  monitoring through effects need the owner's Focusrite; the cloud container
  and CI verify the logic, the formats and the fake-backend paths only.
- Manual tests are written into `docs/manual-tests/M9.md` when each slice
  lands. Documentation follows the owner's naming rule.

## 7. Risks

1. **Input latency and drift are unmeasured on real hardware.** ADR-0069's
   trial (monitoring through an effect) waits on R1; its result may change the
   callback's design.
2. **WASAPI shared mode adds its own buffering**; the round trip may exceed
   what ASIO gives. The status popover shows the real figure; the guidance is
   to use ASIO.
3. **Streaming underruns** at small buffers with slow disks. Mitigated by R5's
   opt-in period, a read-ahead sized in seconds, and a visible underrun counter.
4. **Offline equals real time** for plugins that behave differently offline;
   real-time export is the fallback (D5).
5. **A crash while a take is open** is the one case the whole milestone exists
   for; the test kills the process mid-take and reopens (MT-REC-2).
6. **Scope.** M9 is the largest milestone so far. If it runs long, the cut line
   is R7 and R8 (workflow and icons), which can become their own milestone
   without breaking the exit criterion's record-and-export core.
7. **Licences to flag:** the FLAC encoder (X2) and the ASIO SDK agreement
   (still open with the owner) before any distribution.

## 8. Alternatives rejected

- **Recording through the live clip player's memory path.** Unbounded memory
  for a long take, and a crash loses everything.
- **One file for all armed inputs.** Cheaper to write, but a take then cannot
  be moved between tracks without a split.
- **Streaming first.** Delays the owner's priority and doubles the real-time
  risk in the first build.
