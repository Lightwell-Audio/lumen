## 1. Decisions the evidence settled

| # | Decision |
|---|---|
| D1 | Recorded files are 32-bit float WAV at the device rate, one file per take per armed track. A stereo input is one stereo file |
| D2 | The audio thread only copies input into a ring, and a disk thread writes. An overrun is counted and padded, and the audio thread never blocks |
| D3 | A take file is valid at every moment: its header is rewritten about once a second, and a sidecar drives recovery |
| D4 | Drift between separate input and output devices is corrected with rubato's `Slip`. ASIO needs none |
| D5 | Export is `render_source` of the project through a converting, dithering writer. Real-time export is driven by the device and gives the same file |
| D6 | Renders follow the project sample rate (R4, P1 A). `Project.sample_rate` already existed, so this needed no new field |
| D7 | No modal dialogs. Export, Project settings and the media pool are ordinary windows or panes, and progress and cancel live in the task area |
| D8 | macOS and Linux input are compile-only until hardware exists (owner, 2026-10-06) |

**Build (with the recommendations):**

1. **Icons.** The rasteriser in `brand.rs` and the mark's constants move to
   a small crate, `lumen-brand`, with no dependencies but `png`. The app
   uses it for the window icon, and `lumen-app`'s `build.rs` (a
   build-dependency) uses it on Windows. It writes `lumen.ico` and
   `lumen-project.ico` into `OUT_DIR` at 16, 20, 24, 32, 40, 48, 64, 96 and
   256 px, with 256 px stored as PNG. Where the mark is 40 px or less
   (`mark::COMPACT`, icons of 55 px and under) it takes the transport mark's
   compact form (thicker strokes, two reflections). This is new for the
   icon: the window icon has no compact form today. They are embedded
   as icon resources 1 (app) and 2 (project) through `embed-resource`
   (MIT/Apache-2.0; rc.exe from the Windows SDK, or llvm-rc). No icon
   binaries are checked in, so the icons cannot drift from the drawing.
   The file icon's drawing is added beside the app icon's. macOS and Linux
   keep the window icon. Their bundle and `.desktop` icons come with the
   M10 packages.
2. **Single instance** (`instance.rs`, all platforms). Two Lumens on one
   settings file never both run.
   - **The key** is the user plus the settings file's identity: its folder
     made canonical (made first if missing), its file name, and on Windows
     both lowercased. Equivalent paths therefore give one key, and a run
     with its own `--settings` is its own instance.
   - **Ownership is a lock, taken first.** Before settings are written,
     audio opens or autosave starts, a start takes `Lumen-<key>.instance`,
     a lock file in the settings folder (`File::try_lock`, as the autosave
     locks do). The holder is the instance. The system releases the lock
     when a process ends, however it ends, so a free lock proves the old
     one is gone, and two starts at once elect exactly one. The file only
     proves ownership: on Windows the lock also bars other processes from
     reading it, so nothing is read from it. The holder creates its
     endpoint straight after taking the lock, before anything else
     starts.
   - **The endpoint:** on Windows a named pipe, `\\.\pipe\Lumen-<key>`,
     created with `FILE_FLAG_FIRST_PIPE_INSTANCE`,
     `PIPE_REJECT_REMOTE_CLIENTS` and a security descriptor for the current
     user only. On Linux a socket in `$XDG_RUNTIME_DIR` (or the settings
     folder), on macOS in the settings folder, in a `0700` folder, and the
     peer's user id is checked. Only the lock holder removes a stale socket.
     The implementation uses `windows-sys` and std's Unix sockets, with no
     new crate.
   - **A later start** finds the lock held and does not touch settings,
     audio or autosave. It connects. On Windows it learns the holder's
     process id from the pipe (`GetNamedPipeServerProcessId`) and calls
     `AllowSetForegroundWindow` for it before it sends its request.
     - **Requests** are of two kinds: Open (an absolute file path) and
       Show (no file: only come to the front).
     - **Replies** are Accepted or Rejected with a reason. The later start
       exits 0 only after Accepted.
     - **A rejection** (busy, a file that is not a project) opens its small
       window, saying why, with Try again and Close. The request is never
       dropped without a word.
   - **Retrying.** For up to 10 s the later start alternates between
     connecting and taking the lock again. This covers a holder that is
     still starting, and one that closes or crashes meanwhile. If it gets
     the lock, the old instance is gone, and it starts normally as the
     instance, opening its file.
   - **Focus is best effort:** Windows can refuse it, and the holder then
     flashes its taskbar button.
   - **A holder that does not answer** in 10 s (hung, or closing) is not
     replaced, because its lock proves it is alive. The later start shows a
     small window of its own, with no audio and no settings written:
     "Lumen is already running but is not answering. Your work in it is
     safe." It has Try again (which runs the same retry, lock included) and
     Close. It never starts a second engine. The window reads the settings
     for its theme and scale only, and falls back to the defaults.
   - **The holder's listener** runs on its own thread, one connection at a
     time, with 2 s read and write timeouts. A request is at most 64 KiB.
     Requests are queued for the UI thread (at most 8; more are Rejected as
     busy). The UI thread wakes the window (`request_repaint`), restores and
     focuses it (`ViewportCommand::Minimized(false)`, `Focus`), and handles
     an Open.
3. **Opening a handed-over or dropped project** goes through `request`
   (`app/projects.rs`), the path File › Open already takes. It gains a
   guard that File › Open, New and templates get too. Today they do not
   wait for a take or an export:
   - **The same project already open:** it only comes to the front.
   - **While recording:** nothing is replaced. A notice that wraps in full
     says "Night Drive.lumen opens when recording stops", with "Stop and
     open" and Cancel. A later request replaces the waiting one.
     - "Stop and open" stops the transport, then waits for the engine's
       answer, the MIDI and automation commits, and the audio takes'
       files (`audio_takes_finishing()` false and the clips placed).
     - Only then does it go on as below. The take is now an unsaved change,
       so the Save / Don't save / Cancel prompt appears.
     - A take is never deleted because the document changed while it
       closed: the replacement cannot start before the take is placed.
   - **While exporting** (`audio_export::busy()`, offline or real time):
     the notice says "… opens when the export is done", with Cancel only.
     The export's own Cancel stays in the task area, and the open goes on
     once the export has finished or stopped and closed its file.
   - **While a copy or collect runs:** as today (`copy_blocks`).
   - **Otherwise** it goes on as File › Open (SI A): unsaved changes go
     through the existing prompt.
   - **Every continuation is guarded.** The save prompt is not modal, so a
     recording can start behind it or while the save runs. The guard
     therefore also sits in `proceed`, which "Don't save" and the end of a
     save call directly (`after_save`). New, templates and Open are all
     covered there. When it holds a continuation, the chosen action waits
     in the notice above. The save prompt is not asked again unless the
     recording added a take, which the earlier choice did not cover.
   - **Checked again on arrival.** Opening reads the file on a worker
     (`files::open`). When it arrives, the guards are checked again before
     `replace_document`. A recording started meanwhile turns the open back
     into the waiting notice.
   - **Drops.** A drop that holds a `.lumen` opens the first one. Other
     files in the same drop are not added, and a notice says how many were
     left out. A `.lumen` among audio files never imports as media.
4. **Association (FA A, Windows).** Values go under
   `HKCU\Software\Classes`:
   - `.lumen` → `Lumen.Project`, plus `OpenWithProgids`;
   - `Lumen.Project` with its friendly type name ("Lumen project"),
     `DefaultIcon` = `"<exe>",-2` and `shell\open\command` =
     `"<exe>" "%1"`;
   - `Applications\lumen.exe` with `SupportedTypes`.

   Then `SHChangeNotify(SHCNE_ASSOCCHANGED)`.
   - **Who owns it:** the copy whose path, made canonical, is in
     `Lumen.Project`'s open command.
   - **Turning the switch off** happens only when this copy owns it. It
     then removes `Lumen.Project`, the `Lumen.Project` value under
     `.lumen\OpenWithProgids` and `Applications\lumen.exe` if it names this
     copy. It clears `.lumen`'s default value only while that value is
     `Lumen.Project`. It never deletes the `.lumen` key or another
     program's values (the platform's registration guidance).
   - **When another copy owns it,** the switch is off and the row names that
     copy with "Use this copy", which writes the keys for this copy.
   - **When the person chose another program** in Windows' "Open with"

     says so and links to the system's Default apps page. If that choice

   - **Writes go through a `Hive` trait.** Tests use a map, and a failed

   - The product name and ProgID come from `lumen_core::product_name!()`.

## 4. Built slices

### R2 — Audio recording

- **Capture.** `InputPlayer` capture routes push chunks into a preallocated
  SPSC ring that holds 8 s of 32 channels. A full ring drops the chunk, counts
  an overrun, and the gap is padded so the take stays aligned.
- **Writing.** A worker writes one take file per track into `Recordings`.
  Save copies it to `Samples/Recorded`.
- **Placement.** At Stop, each take is placed at the first heard sample, less
  the input and output latency and the manual offset
  (`AudioSettings.record_offset_ms`).
- **Undo.** `Document::record_audio_take` is one undo step, and it replaces
  what the take covers.
- **Recovery.** A sidecar `<take>.take.json` lets recovery repair the take and
  put it back with the session's autosave.
- **Format.** There is no format change.
- **CI.** The macOS CI follow-up on PR #63 led to ADR-0103: callback-side
  polling within the audio deadline.

### R2b — The loopback helper

- **Card.** Measure… beside the recording offset unfolds a card in the
  Latency section. It has Cable from (an open output pair) and to (an open
  input), a strip of the returned clicks, the result, and Use +x ms. The
  command "Measure recording latency…" opens it.
- **Measurement.** It runs after the engine in the device callback
  (`lumen_engine::loopback`): five 256-step clicks at −12 dBFS, 0.3 s apart,
  with everything else silenced, while the input is kept beside them.
  Output and input count the same callback frames, so the delay found is the
  shift recording needs.
- **Analysis**, off the audio thread: each click is cross-correlated over
  0 to 250 ms. All five must agree within 2 frames. Silence, noise and
  disagreement are refused, each with what to check.
- **Offset.** Use sets (measured − reported) as the recording offset and
  remembers the driver, device, rate and buffer. A hand-typed offset forgets
  them. A different setup shows a hint to measure again, and a result
  measured before the device, rate or buffer changed is not offered.
- **Tests.** Unit tests cover the analysis (delays, noise, a polarity flip,
  silence, disagreement) and the player. The allocation guard covers the
  audio side. Five E2E scenarios use a cable scripted on the fake device.
- **Format.** There is no project format change. The settings gain
  `offset_measured`, an added field.

### R3 — Takes and Capture MIDI

**Model.** `Clip.takes: Option<Takes { active, count, others }>` (format
v31). A pass is one of:

- `Pass::Audio { offset, audio_phase_seconds }`, a window on the same file;
- `Pass::Midi { notes, events }`.

The clip's own content is the active pass, so the engine sees an ordinary
clip.

**Takes menu and chip.** The Takes menu and an n/m chip work with the
commands:

- `clip.take_next` and `clip.take_previous`;
- `clip.take_keep`;
- `clip.take_extract` (audio only).

**Edits and takes.** Split, trim and slip carry the other passes with the
cut. Reverse, unloop and MIDI join settle the clip: it keeps the take it
plays and says so in a notice.

**Capture MIDI.** Shift+F9 runs it. The engine tags messages
`Heard::{Recording, Playing, Stopped}`. The app keeps the last 10 minutes,
at most 20,000 messages, in memory only. Its switch is in the record menu.
A capture uses Overdub placement and is one undo step.

**Loop takes.** After the owner's runs, one model replaced four separate
fixes (ADR-0104, last section):

- `record_span` fixes what a take replaces.
- `loop_passes::cut` cuts every pass by one rule.

### R4 — Project lifecycle

- **Save a copy** is self-contained: every file is copied in, and the open
  document is untouched.
- **Collect and save** copies under temporary names and writes the project
  file last. Esc stops it with nothing changed, and it never deletes a
  source. Neither is an undo step.
- **Templates** live in `Documents/Lumen/Templates/<Name>/` and are opened with
  New from template. They are not renamed or deleted inside Lumen.
- **Revert** works as chosen in P2.
- **Project settings** covers rate, pan law, crossfades, new-track colour and
  notes. Format v32 adds the notes and the colour. Tempo and meter stay out of
  this window.
- **Rates.** A new project takes the device's rate. Join, bounce and freeze
  render at the project rate, decoding again only when it differs from the
  device's rate.
- **After MT-PROJ-1 run 1:**
  - projects and templates moved to `Documents\Lumen` (`Launch::user_dir`);
  - the app menu was grouped (ADR-0105 item 5b).

### R5 — Export

**Window and scope.** The Export window opens with Ctrl/Cmd+Shift+E. It
exports:

- the project, the loop or the selection;
- the master or stems for tracks, groups and returns.

**Formats and processing:**

- WAV 16, 24 and 32-bit float, and FLAC 16 and 24 (pure-Rust encoder, licence
  checked);
- rate conversion, TPDF dither for integer files, peak normalize and tails;
- offline or device-driven real time;
- progress, cancel and a loudness report.

**Behaviour.** Export never changes the project or its history. A cancelled
or failed export leaves an existing file in place. Export choices are session
state, so there is no format change.

  workflows) and the 6 smoke tests passed.
- **Encoding:** 5 tests cover every format and depth, conversion,
  normalization, saturation, deterministic dither, a partial FLAC frame and
  cancel.
- **Callback golden:** 11,234 frames are identical to the offline render,
  including compensation and a trimmed tail. There are zero heap operations
  under the allocation guard.
- **Linux:** 3,174 passed and 1 failed: the existing `lumen-plugin-host`

- **Instruction gates:** all 13 passed. The largest change is project

- **After merging with R4b:** 3,217 Windows tests (723 E2E) and the smoke

Not run: real ASIO or WASAPI capture, external plugins, a long soak.

### R6 — Disk streaming and the peak cache

**Stream files.** A WAV, RF64 or AIFF file in PCM or float at the device
rate plays from where it is, with positioned reads; memory maps are not used,
since a page fault on the audio side is blocking I/O. Any other file is
converted once, in the background, to a 32-bit float WAV in the cache, bit
for bit what loading it into memory gives. A cache entry is keyed by the
source's path, size, modified time and rate, so a changed file is converted
again. Peaks are kept beside each entry, so a reopened project shows its
waveforms without decoding.

**The audio thread** reads a fixed pool of 4,096-frame pages (96 MB,
allocated when streaming starts) and never waits. A clip whose next 40 ms
are not in memory glides out and counts one underrun. With its pages in, a
streamed clip renders bit-identical to the same clip in memory.

**The disk thread** plans from the clip list the engine plays, in this
order: the cue of a start, the next half second at the playhead, the rest of
two seconds ahead (wrapped into a playing loop), then the starts of the song
and the loop and each marker. Offline renders (bounce, join, freeze, export)
read their pages on the render thread, so they equal real time.

**Starts** (L A) are held until the next 140 ms at the new place are read,
for at most 150 ms. **Feedback** (D A): a Disk row ("12% · 0 late") and a
"Disk late" chip.

**Files without whole-file memory.** Export reads and measures loudness in
blocks; WAV writes RF64 past 4 GiB; reversed long files become stream files;
the atlas reclaims the old rate's peaks.

**Measured** (Windows 11, release, 64 stereo files of two minutes): opening
at 48 kHz took 0.67 s and 3,085 MB in memory; from disk it took 0.25 s and
170 MB, and 0.03 s with a warm cache.

**Soak.** 64 streamed tracks in real time at 128 frames, from a fake disk
with stalls, with loops and locates; it runs in CI's test step and asserts
zero late reads. Its CI failures (2026-10-29) were the disk thread's: a slow
plan, a writer scan per page, a cue cleared before the playhead moved, and
too small a margin after a start. All four were fixed in the product
(ADR-0109).

## 5. Gates

- **Usual gates:**
  - fmt;
  - workspace clippy with `-D warnings`;
  - workspace tests;
  - E2E and smoke tests;
  - macOS cross-clippy.
- **Engine and project changes** also run the WSL mirror and the performance
  gate, which fails at +2%.
- **Real-time paths** run under the allocation guard and RealtimeSanitizer:
  - the capture copy;
  - the monitor path;
  - the disk reader's hand-off.
- **E2E recording scenarios** use the fake backend with a scripted ramp input.
- **Persisted fields:** each new one bumps the format, with a migration and a
  frozen golden.
- **Owner's hardware:** ASIO and WASAPI input, round-trip latency, drift and
  monitoring through effects need the owner's Focusrite. The cloud container
  verifies the logic and the fake-backend paths only.

## 6. Open risks

1. **Latency is unmeasured on real hardware.** R2b measures the round trip
   through a cable; its first run on the Focusrite is MT-REC-5.
2. **Streaming underruns** can happen at small buffers on slow disks. R6
   mitigates this with a read-ahead sized in seconds, files under 30 s kept
   in memory and a visible underrun counter. Without a per-clip switch (M B),
   a clip cannot be pinned in memory: if underruns show, the automatic rule
   is widened rather than adding a control.
3. **Offline and real-time output can differ** for plugins that behave
   differently offline. Real-time export is the fallback.
4. **Licences:** the ASIO SDK agreement is still open with the owner and must
   be settled before any distribution.

## 7. Alternatives rejected

- **Recording through the clip player's memory path:** a long take needs
  unbounded memory, and a crash loses it all.
- **One file for all armed inputs:** a take could then not move between
  tracks.
- **Streaming first:** it delays the owner's priority and doubles the
  real-time risk.
- **Revert as one undo step back to the saved state:** changes made inside a
  plugin's window would survive it.
- **Clear that erases files for good:** it cannot be undone, which breaks
  priority 1.
- **Streaming that never waits on a start** (L B): the first beat of a drum
  loop could be missing while MIDI already plays.
- **One ring per streamed clip:** loops and markers would need rings of
  their own, and a clip list change would allocate.
- **Converted copies inside the project folder** (C B): projects grow by a
  float copy of every converted file.
- **R6 and R6b as two slices** (S A): the owner chose one slice.
