# M6 · VST3 hosting and the device system — Manual Tests

### MT-VST-0 · Audio-path measurements (Windows, and time)
Slice 0 of M6 (ADR-0067). **Status: corrected full run recorded; decision
gate remains open.** The numbers that decide the
wake-up mechanism, whether the audio callback may wait on the operating
system, and the process-grouping policy are Windows numbers; the harness that
produces them was built and tested on Linux only. Nothing in the plan is
claimed until this has been run and the results are recorded here.

Before you start: close heavy programs (browsers, other audio software),
plug the machine in, and note the power plan the harness prints. Use a
PowerShell window in the repository root. A cold build is needed once:

```powershell
cargo build --release -p lumen-plugin-host -p lumen-test-plugin
```

1. **Does it run?** (about 20 seconds)
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --quick
   ```
   Expected: two scenarios (event, spin), each with no `did not run`, `heap
   operations in Lumen's loop: 0`, `divergent 0`. If the note "no audio
   scheduling class for this thread" appears, check whether MMCSS is being
   registered repeatedly on the same thread. Retain the successful handle
   until that thread exits.
2. **The grid** (about 20 minutes; leave the machine alone):
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --csv m6-grid-mmcss-fixed.csv
   ```
   This is 1, 8 and 16 hosts at 64, 128 and 512 frames, five wake-up
   settings (`event`, `spin`, `hybrid150`, `event/spin`, `hybrid150/spin`:
   the host's wake-up, then Lumen's), with the plugin idle and doing 200 µs of
   work per block, at 48 kHz. Keep the console output as well as the CSV.
3. **A busy machine.** Replace 8 with your number of logical CPUs (the harness
   prints it):
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --hosts 8 --frames 128 --load 200 --contention 8 --csv m6-busy-mmcss-fixed.csv
   ```
4. **Other rates and a cold start.**
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --hosts 8 --frames 64,128 --rate 44100,96000 --load 200 --csv m6-rates-mmcss-fixed.csv
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --hosts 8 --frames 128 --cold 10 --seconds 5
   ```
5. **Power plans.** Repeat step 2 (or just `--hosts 8 --frames 128`) once in
   *Balanced* and once in *High performance*, naming the CSVs differently.
   The harness prints the active plan at the top.
6. **A host that crashes or hangs** (host 0 of 8; the others must carry on):
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --fault crash --hosts 8 --frames 128 --load 200
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --fault hang --hosts 8 --frames 128 --load 200
   ```
   Expected: `fault in host 0 seen after 3 or 4 block(s)`, crash reported as
   an exception code (for example `0xc0000005`), hang as "still running ...
   would be killed", `misses in the other hosts: 0`, and a replacement time.
7. **Hosts end with Lumen** (the job object, never run on Windows before).
   Start a long run, and while it is running end `lumen-host-bench.exe` from
   Task Manager (Details tab, End task):
   ```powershell
   cargo run --release -p lumen-plugin-host --bin lumen-host-bench -- --hosts 4 --frames 128 --seconds 120 --wake event
   Get-Process lumen-plugin-host -ErrorAction SilentlyContinue
   ```
   Expected: the second command (run after ending the harness) lists no
   process, within a second or so. Do the same with `--fault hang` and end the
   harness before it finishes, to see a hung host go too.
8. **Tests.** `cargo test --release -p lumen-plugin-host` passes on Windows (it runs the
   same tests as Linux against the real loader and processes). Record any
   failure with its output; this exercises the Windows file mapping, events,
   timers and job object used by the host. Confirm the benchmark's MMCSS
   scheduling note is absent before treating its timing data as representative.

**What to send back:** the console output and CSVs, the machine (CPU model,
logical CPUs, Windows version), the power plans, and anything that looked
wrong. What the numbers have to show for the plan to go on is in
`docs/milestones/M6.md` §2 (round-trip p50/p99/p99.9/max, misses, idle CPU
across the grid) and §2's budget (the whole 64-track callback under half its
period at 128 frames and 48 kHz; the harness measures only the transport and
a trivial plugin, so it bounds that budget from below).

## Run 3 · 2026-10-15 · Heap fix and 64 hosts (branch `m6-s0-audio-path`)

**Machine:** same as run 2 (Windows 11 Home 10.0.22631, AMD Ryzen 7 7700X, 16
logical CPUs), Balanced power plan, **in ordinary use during the run** (the
Claude desktop app and an editor were open; nothing was closed first, unlike
the earlier runs). One run per scenario, 10 s each.

**The two heap operations (fixed).** Cause, found by reading and reproduced
by a test: when a host stops answering, the loop asks whether its process has
ended, and `HostProcess::ended` words a crash as a `String`
(`exception 0xc0000005`): one allocation and, when the value drops, one free.
Hangs never allocate (the process is still running), which is why only crash
runs showed it. The loop now asks `HostProcess::has_ended`, which allocates
nothing; `ended` stays for the descriptive answer, off the audio thread.
`shm_rt::noticing_a_crashed_host_does_not_allocate` runs the whole crash as
the loop sees it under the allocation guard: with `has_ended` made to call
`ended` it fails with exactly 2 heap operations (the benchmark's count), with
the fix it passes. In the benchmark, `--fault crash` and `--fault hang`
(8 hosts, 128 frames, 200 µs) now report **0 heap operations in every
scenario** and the crash run exits 0. **RTSan:** the crash test and the existing audio-path test pass under
RealtimeSanitizer on Linux (WSL, debug and release; `try_wait` is a
non-blocking `waitpid` and is not flagged). The step is now in CI's `rtsan`
job. Not run under RTSan on macOS.

**The 64-track budget.** 64 host processes (one per track, so the per-instance
policy at its largest), 128 frames at 48 kHz (period 2.667 ms, half-period
budget 1.333 ms), each plugin doing the stated busy work per block. Block time
is submit to every answer in, the whole of Lumen's side of the IPC; the
engine's own mixing of 64 routed tracks (about 1% of a block, ADR-0035, and
not run here) is separate and small beside it.

| Wake-up | Plugin work per block | p50 | p99 | p99.9 | max | Misses | Stale |
|---|---|---|---|---|---|---|---|
| event | 0 µs | 104 | 140 | 255 | 388 | 0 | 0 |
| event/spin | 0 µs | 94 | 135 | 165 | 372 | 0 | 0 |
| event | 50 µs | 286 | 452 | 556 | 590 | 0 | 0 |
| event/spin | 50 µs | 293 | 468 | 549 | 568 | 0 | 0 |
| event | 100 µs | 496 | 633 | 749 | 878 | 0 | 0 |
| event/spin | 100 µs | 540 | 867 | 1101 | 1200 | 0 | 0 |
| event | 200 µs | 888 | 1162 | 1664 | 1680 | 0 | 0 |
| event/spin | 200 µs | 1039 | 1458 | 1861 | 2010 | **40** | 30 |

Times in µs. Every scenario: zero heap operations, zero failed or divergent
blocks, zero idle host CPU. ([Data](../../m6-budget-64.csv).)

What this says, and no more: up to 100 µs of plugin work per track (64 tracks,
about 2.4 cores of work), both modes finish every measured block, even the
slowest, inside the half-period budget (largest max 1.2 ms) with no missed
deadline. At 200 µs per track (64 × 200 µs is 12.8 ms of work
per 2.667 ms block, about 4.8 cores of a 16-thread machine) `event` has its
p99 under the budget (1.16 ms) but its p99.9 and max above it, still inside
the 2 ms deadline with no misses, and `event/spin` fails (p99 1.46 ms, 40
missed deadlines). The loop is limited by the work and the cores, not the
signalling, and spinning on Lumen's side adds a thread competing with the
hosts for them. This is one run on a machine that was in use, with a
synthetic busy loop as the plugin; it is not a statement about real plugins,
fewer cores, or process-per-chain (unmeasured). The half-period target is met
at p99 for `event` up to 200 µs per track and not at its tail; the owner
decides the representative workload and whether a tail above it is acceptable
(ADR to follow).

**Process grouping, modelled.** Process-per-chain is not built, so this models
it: the same 64 tracks as N host processes, each doing the work of 64/N tracks
in one thread per block (the test plugin's `process_slow` load scaled to
match), one link and one wake-up per process, `event` wake-up, 128 frames, 48
kHz, 10 s each, same machine in use. It measures what grouping changes for the
loop (work serialised inside a process, fewer wake-ups) and nothing else: no
real chain code, no memory or start-up cost, no per-instance overhead.
Times in µs. ([Data](../../m6-chain-model.csv).)

| Plugin work per track | Processes × tracks each | p50 | p99 | p99.9 | max | Misses |
|---|---|---|---|---|---|---|
| 100 µs | 64 × 1 | 498 | 656 | 917 | 1192 | 0 |
| 100 µs | 16 × 4 | 444 | 832 | 855 | 933 | 0 |
| 100 µs | 8 × 8 | 832 | 1141 | 1207 | 1630 | 0 |
| 100 µs | 4 × 16 | 1613 | 1636 | 1660 | 1694 | 0 |
| 100 µs | 2 × 32 | infeasible | | | | |
| 200 µs | 64 × 1 | 894 | 1254 | 1671 | 2018 | 14 |
| 200 µs | 16 × 4 | 839 | 1627 | 1757 | 2434 | 10 |
| 200 µs | 8 × 8 | 1618 | 1704 | 1839 | 1856 | 0 |
| 200 µs | 4 × 16, 2 × 32 | infeasible | | | | |

"Infeasible": one host would need more than a whole period (2.667 ms) of work
per block (3.2 ms and more); the harness declared those hosts dead during
warm-up, so their rows read 0 µs and are not results. What the rest says: a
process's block time cannot be lower than the work it serialises, so grouping
past about four tracks per process costs more than it saves; 8 × 8 at 100 µs
is already at p99 1.14 ms, and 4 × 16 is over the 1.333 ms half-period budget
at its median. 16 × 4 is about the same as 64 × 1 at 100 µs (better median,
worse p99) and no better at 200 µs. Grouping buys nothing visible in the
loop on this machine, and it gives up isolation (one crash takes a chain's
tracks with it). The 64 × 1 row at 200 µs had 14 misses here and none in the
run above: at that load the result varies between runs, which is itself the
finding. Not measured: process memory and start-up for 64 hosts (the idle
CPU was zero).

Same machine as run 2, in ordinary use. All three window relationships pass

A hung editor (the plugin's window thread stops answering 1.5 s after
attach):

| Window relationship | Heartbeat notices | System marks it hung | Lumen's loop, longest stall | Moving or minimizing Lumen's window | Ending the host and reopening |
|---|---|---|---|---|---|
| A: none (unowned) | 0.62 s | 5.0 s | 31 ms | 2 ms / 10 ms | 35 ms |
| B: owned by Lumen's window | 0.61 s | 5.0 s | 31 ms, **then blocked until the host was killed** | **blocked** (more than 8 s each; 16 s in all) | 54 ms |

Destroying the owner window while its editor was hung took 1 ms in B. So B
fails exactly where ADR-0005 predicted: windows are tied across processes,

system's `IsHungAppWindow` takes five seconds, so Lumen should use its own.

### MT-VST-2 · Devices on tracks, interface steps (Windows, owner) — slice 2d

Run `cargo build --release -p lumen-plugin-host`, then Lumen from the
repository root. The measurements ADR-0069 asks for (the whole callback at 64
and 128 frames, recording with monitoring through an effect) are added to this
test when slice 2f closes; these are the steps for what 2d built.

1. Open the browser's Devices list. Select a MIDI track, double-click an
   instrument plugin. **Expect:** the detail panel opens on Devices, tall
   enough to show the card's picture; the instrument replaced the synth; its
   card shows "starting…" and then its signal ("MIDI → audio") and latency.
2. Play a note (computer keyboard or MIDI). **Expect:** you hear the plugin.
   While the song plays the cables carry a bright line; stopped, they are dim.
3. Select an audio track and double-click an effect. **Expect:** it is added at
   the end; with a card chosen first, it lands after that card. Undo removes it
   in one step; redo brings it back.
4. With no track selected (or an audio track selected), double-click an
   instrument. **Expect:** a new MIDI track holds it; one undo removes track
   and device together.
5. Drag an effect from the browser over the chain. **Expect:** a blue line and

#### Run 1 — 2026-10-17, owner (Windows; plugins labelled for this run)

RP-5 is a large instrument, RP-6 an amp effect, RP-7 a sampler instrument.

- **RP-5 failed while loading** ("could not set the plugin up: the plugin's
  window is not responding"); Reload loaded it. **RP-6 failed the same way at
  first, then as "stopped answering, and its host was ended"** with fast block
  timings; Reload worked.
- **RP-7 failed with "the plugin host broke the protocol: expected
  Configured"** and once with "did not answer while trying to open the audio
  link", around changing instruments in its own window.
- With a plugin's window in front the computer keyboard played nothing.
- Two overlapping editors fought over which was in front.
- Each open editor had its own taskbar button.

**Causes and fixes (ADR-0076, "MT-VST-4 run 1"):** every restart a plugin
asked for set it up again, including "parameter values changed", which these
plugins send when a patch loads, so setups came while their main thread was
busy; a window request the host gave up on made every later request, the setup
too, answer "not responding"; a late answer was read as the next request's
("expected Configured"); a slow call to the plugin's controller (making its
editor) held the lock its audio thread needs for every block. Now only reload,
bus and latency restarts set a plugin up again; only window requests are
answered "not responding" (after five seconds, not 600 ms) and the rest wait
their turn; late answers are dropped; the controller is called without the
audio lock. The editor is owned by a hidden window of its host (no taskbar
button, no minimize) and changes its stacking only when Lumen comes to or
leaves the front. The note keys are taken from a plugin's window while the
computer keyboard is on (the owner's choice: they play through Lumen, every
other key stays the plugin's). Steps 17 to 22 re-check.
