# Lumen documentation

The owner requires product-neutral documentation. Apply this to plans,
specifications, design notes, decisions, reports, manuals, compatibility
records, READMEs and repository instructions.

- Do not name third-party software products, plugins or vendors as design
  references, comparisons, endorsements or examples. Describe the actual
  behavior, workflow, appearance or requirement instead.
- Use generic descriptions for external test software. When several tested
  plugins need distinct records, use consistent anonymous IDs across the
  documents, preserving results, counts, versions and measurements. Do not
  invent a real identity or claim that anonymous results prove broad
  compatibility. Say when anonymization limits reproducibility.
- Retain technical names needed for accuracy: platforms, languages,
  tools, dependencies, APIs, protocols, file formats, actual commands,
  paths, code/test identifiers, and hardware/device identities. Naming a
  dependency to explain an engineering choice is allowed; using a product
  to describe Lumen's personality or expected behavior is not.
- Preserve copyright notices, license texts, required trademark notices,
  attribution and their source links. Do not anonymize legal obligations.
- Preserve requirements and historical outcomes. Paraphrase old product
  comparisons into concrete behavior; do not present edited quotations as
  verbatim. Avoid vague substitutes such as "the reference app" when the
  behavior can be stated directly.

Before finishing, search edited documentation for third-party product
names and comparison phrases. Inspect each match in context; a blanket
replacement can corrupt commands, attribution or technical identifiers.
Check grammar, links/heading references and consistency of anonymous IDs.
This is an editorial rule, not a claim that mentioning a name is unlawful.
